# Очистка hMailServer через CLI

Новый CLI `hmail-cleaner` запускается на том же Windows-сервере, что и
hMailServer. Цель — Windows Server 2016 / 1607 x64 и схема MySQL 5.7.21
из предоставленного DDL. Точную версию сервера программа показывает через
`SELECT VERSION()`. Версия `mysql --version` относится к клиенту.

Переносимое ядро находится в `crates/core`, MySQL/файлы/Windows SCM — в
`crates/adapters`, CLI — в `crates/cli`. Будущее окно использует тот же core.
Старый Tauri/Vue не перенесён на новый механизм и пока содержит прежнее поведение.

## Запуск на сервере

Скопируй standalone `hmail-cleaner.exe` на сервер. Для его запуска Rust,
mise, Bun, WebView2 и отдельный VC runtime не нужны при сборке `build:windows`.
Сборку и реальный запуск на Server 2016 нужно проверять отдельно.

Создай приватный файл конфигурации по `examples/cleaner.env.example` и заполни
`DATABASE_URL`. Нужны SELECT на пяти используемых таблицах и DELETE на
`hm_messages`, `hm_message_metadata`, `hm_messagerecipients`; аккаунт и база
должны соответствовать именно этой установке hMailServer. Перед удалением
файлов clean проверяет права SQL нулевыми DELETE внутри откатываемой транзакции.
Используй подключение к локальной MySQL; настройку TLS URL подбирай под сервер.
Системная переменная DATABASE_URL имеет приоритет над явно указанным env-файлом.
Старые `.env` автоматически не читаются, пароль не передаётся аргументом CLI.

Сначала посмотри выборку за календарный месяц:

```powershell
.\hmail-cleaner.exe preview --older-than 1mo --data-dir "D:\hmailserver\data" --hmail-ini "D:\hmailserver\Bin\hMailServer.ini" --env-file "C:\private\cleaner.env"
```

Затем останови службу и выполни очистку с теми же параметрами:

```powershell
Stop-Service hMailServer
.\hmail-cleaner.exe clean --older-than 1mo --data-dir "D:\hmailserver\data" --hmail-ini "D:\hmailserver\Bin\hMailServer.ini" --env-file "C:\private\cleaner.env"
$cleanupExit = $LASTEXITCODE
Start-Service hMailServer
Write-Host "Cleanup exit: $cleanupExit"
```

Если фактическое имя службы отличается, укажи `--service-name`. Программа
сверяет существующий DataFolder с `[Directories] DataFolder` указанного INI,
проверяет STOPPED перед запуском и перед каждой порцией. Держи службу
остановленной на всё время очистки; не запускай других писателей/операций
переноса Data. Advisory lock исключает второй экземпляр cleaner для той же БД,
но не останавливает hMailServer или другие SQL-клиенты.

`preview` читает БД и проверяет правила путей; он не открывает каждый EML,
не оценивает размер файлов и не гарантирует отсутствие будущих ошибок доступа.
Его выборка не является сохранённым планом: clean вычисляет свой cutoff заново.
Для абсолютно одинаковой границы обеих команд используй `--before`.

## Период и параметры

- `--older-than 30d`, `1mo`, `1y`: дни, календарные месяцы и годы; конец месяца
  ограничивается последним днём получившегося месяца.
- `--before 2026-09-07` или `--before 2026-09-07T12:00:00`: явная граница,
  строго `messagecreatetime < cutoff`. Ровно на границе письмо сохраняется.
- Даты — локальное время сервера, как hMailServer DATETIME. При preview на
  другом компьютере с иной часовой зоной используй явно заданный `--before`.
- `--batch-size`: 1000 по умолчанию, 1–10000.
- `--workers`: 2 по умолчанию, 1–8. Для HDD больше работников может замедлять
  удаление; 2 — исходная настройка, скорость нужно измерять на фактическом диске.
- `--json`: NDJSON, по одному событию на строку. Обычный прогресс ограничен
  интервалом 250 мс, конкретные ошибки и итог выводятся всегда.

## Алгоритм и повтор

БД выбирает старые доставленные сообщения всех аккаунтов и их IMAP-папок.
Очередь (`messagetype != 2`), публичные сообщения (`messageaccountid <= 0`),
новые сообщения, аккаунты и логические IMAP-папки сохраняются.
Путь вычисляется из accountaddress и имени GUID:
`Data/domain/account/первые-два-символа-GUID/{GUID}.eml`. Логическая IMAP-папка
не создаёт дополнительного слоя на диске. Старые абсолютные пути разрешены
только внутри Data. Повреждённые пути, links/reparse points и повторяющийся
basename GUID блокируются и попадают в отчёт. Дубликаты блокируются
консервативно даже в разных аккаунтах, чтобы не удалить файл другой ссылки.

Нет полного рекурсивного обхода файлов. Один SQL-снимок фиксирует верхний ID,
справочники владельцев и список дубликатов; далее идут порции по PRIMARY KEY.
Файловые работники получают только точные выбранные пути, группируют их по
родителю и проверяют стабильные родительские каталоги один раз на группу.
Память для писем и результатов ограничена порцией; справочники и набор
повторяющихся имён остаются на время запуска. Запрос дубликатов один раз
просматривает hm_messages и на большой базе тоже требует времени.

Сначала удаляются EML. Уже отсутствующий EML тоже допускает очистку строки.
Ошибка доступа/пути/I/O сохраняет строку и даёт partial. Затем в одной
InnoDB-транзакции удаляются только разрешённые ID из metadata, recipients и
hm_messages. Текущие поля сообщения повторно сверяются под FOR UPDATE.
После подтверждённого COMMIT и проверки отсутствия строк удаляются только
пустые затронутые физические папки и пустые родители до Data. Data сохраняется;
непустые и посторонние ранее пустые папки остаются. Используется remove_dir,
который не удаляет содержимое и учитывает скрытые файлы/подкаталоги.

Файлы и MySQL не образуют общей транзакции. Если SQL откатился после удаления
файлов, повтор той же очистки удалит оставшиеся строки как AlreadyAbsent.
При потере подтверждения COMMIT новые порции не запускаются, итог не считается
успехом. Повтор обрабатывает то, что фактически осталось в БД. Пустая папка,
оставшаяся после фактически committed, но неподтверждённого шага, может остаться:
полного поиска таких папок нет. Возврата файлов, карантина и отдельного resume нет.
Файлы без строк БД вообще не выбираются этим алгоритмом.

Ctrl+C во время clean просит остановку: начатые работники и допустимый SQL-шаг
заканчиваются, следующая порция не начинается. Не завершай процесс принудительно,
если хочешь получить точную сводку этой порции. Автоматического ALTER/OPTIMIZE
нет: логическое удаление строк не гарантирует уменьшение файлов InnoDB на диске.

| Код | Результат |
| --- | --- |
| 0 | Выполнено без отмеченных ошибок |
| 1 | Partial, ошибка backend/вывода или неизвестный результат COMMIT |
| 2 | Ошибка аргументов, конфигурации или preflight |
| 130 | Остановка clean по Ctrl+C после начатой порции |

## Разработка и сборка

`mise.toml` закрепляет Rust 1.98.1; `Cargo.lock` — зависимости. Проверено с mise
2026.10.3. MySQL fixture закреплён до 5.7.21 и digest. Серверу mise не нужен.

```sh
mise install
mise run check
mise run build
mise run test:db
mise run db:down
```

Для тестов на Mac сначала запусти отдельный Colima-профиль:

```sh
colima start --profile hmail-cleanup --activate=false --template=false --cpus 2 --memory 2 --disk 20 --mount none --ssh-config=false
mise run test:db
mise run db:down
colima stop --profile hmail-cleanup
```

Тестовый URL читается только из HMAIL_TEST_DATABASE_URL: loopback:13306,
bootstrap database mysql, уникальная БД создаётся и удаляется fixture.
Тесты не используют production DATABASE_URL. На ARM Mac используется linux/amd64
образ MySQL; `user: mysql` обходит старый gosu, несовместимый с эмуляцией.
По умолчанию Docker context — `colima-hmail-cleanup`; для Docker Desktop/CI
задай HMAIL_TEST_DOCKER_CONTEXT=default. Colima-профиль создаётся отдельно,
mise не переключает глобальный Docker context.

На Windows с Visual Studio Build Tools + Windows SDK: `mise run build:windows`.
Задача задаёт static CRT только для этой сборки. На Mac `mise run build`
создаёт локальный диагностический CLI; production clean на Mac блокируется.
Cross-build возможен через cargo-xwin + clang/LLD/Windows SDK либо официальный
Docker-образ cargo-xwin. Он проверяет сборку EXE, а не работу на Server 2016.

Workflow `.github/workflows/cleanup-cli.yml` подготовлен для ручного запуска:
macOS проверки, Linux MySQL fixture, native Windows проверки и EXE artifact.
Он не подключается к рабочей почте и не запускается автоматически через push.

- Mac: форматирование и Clippy пройдены; 51 переносимый тест прошёл; release CLI собран.
- MySQL: 14 интеграционных тестов прошли на отдельной MySQL 5.7.21, включая

- CLI preview: проверен с настоящей тестовой БД и NDJSON; строки и файлы сохранены.
  Production clean на Mac отказал с кодом 2 до подключения к БД.
- Windows: через cargo-xwin 0.23.1 собраны x64 MSVC release EXE и Windows-бинарники
  тестов. `dist/cli/hmail-cleaner.exe` — локальный артефакт; в Git не добавляется.
  Импорты EXE — системные Windows DLL, без отдельного VC runtime. Линкер сообщил
  LNK4099 для отсутствующих сторонних CRT PDB: это отладочные символы,
  а не недостающая runtime DLL.
- Native Windows/Server 2016: запуск ещё не выполнялся. Подготовленный CI
  тоже ещё не запускался и не заменяет проверку непосредственно на 1607.
