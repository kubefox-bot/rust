# Итоговый review очистки hMailServer

Ветка `update`, база `94836e5`. Независимый read-only review ревизии
`d8636a7` выполнен через Superpowers requesting-code-review.
Найдено два Important/P2, оба исправлены одной серией RED→GREEN:

1. Нулевая/недекодируемая дата MySQL останавливала всю выборку. Теперь ошибка
   содержимого строки становится RowFailure, курсор продвигается, последующие
   нормальные сообщения обрабатываются. Ошибка SQL-запроса остаётся фатальной.
   Регрессия проверена на MySQL 5.7.21 с нулевой датой и следующим нормальным ID.
2. Ошибка закрытия соединения затирала первоначальную ошибку, включая
   неопределённый COMMIT. Теперь первоначальные status/stage/error/summary
   сохраняются, ошибка закрытия добавляется. Если исходный результат успешен,
   close error делает итог неуспешным. Проверены COMMIT uncertainty, cancellation,
   preflight failure и успешный результат с последующим close failure.

`messense/cargo-xwin:0.23.1@sha256:9856b895265d4966f212228ba64802cf89337e2a2a537aa2533c1b8784cbc81b`.

## Решения, принятые в ходе исполнения

Перечень в порядке принятия; это все Ruling из ledger исполнения.

1. Работать в свежем checkout этой задачи на запрошенной ветке update.
   Дополнительный worktree не даёт изоляции от отсутствующих сторонних изменений.
   Цена ошибки: при появлении параллельных пользовательских правок их нужно сохранить.
2. Удалять только пустые затронутые каталоги и родителей после подтверждённого SQL,
   сохраняя Data. Это соответствует алгоритму без полного обхода.
   Цена: посторонние ранее пустые каталоги остаются.
3. Разбор абсолютных путей оставить приватным в core/paths.
   Windows/Unix prefix validation — отдельная ответственность.
   Цена: один дополнительный приватный модуль, публичный API сохранён.
4. CommitUncertain хранит исходную причину сбоя для отчёта.
   Цена: дополнительное поле нового внутреннего контракта.
5. Worker scheduling и сверку DataFolder вынести в отдельные приватные модули.
   Конкурентность и INI — разные границы.
   Цена: два приватных модуля сверх перечня filenames плана.
6. Ограничение workers и join failures проверять на приватной границе scheduler
   настоящими blocking jobs, поскольку файловые тайминги ненадёжны для подсчёта.
   Цена: интеграция filesystem зависит от этого протестированного scheduler.
7. Разделить progress/errors, batch resolution, outcome validation и workflow
   внутри владельца cleanup. Неполные/посторонние file outcomes блокируют SQL.
   Цена: несколько приватных модулей нового core.
8. Добавить откатываемый probe SELECT/DELETE без совпадающих строк перед файлами.
   Это выявляет недостаточные SQL-права; preview остаётся SELECT-only.
   Цена: шесть дополнительных statements; clean требует DELETE даже при пустой выборке.
9. Сохранить ручное offline-окно без других писателей, как согласовано.
   SCM-проверки не создают полной изоляции.
   Цена нарушения: сторонние писатели могут гоняться с файловыми/SQL-операциями.
10. Принадлежность DATABASE_URL, INI и службы одной установке проверяет оператор;
    это явно записано в инструкции.
    Цена неправильного выбора: валидная чужая БД может потерять выбранные строки.
11. Прямое удаление без карантина, восстановления и журнала — явное решение пользователя.
    Цена: программа не может восстановить удалённые файлы.
12. Сохранить DB-selected scope: orphan-файлы, queue, Public и посторонние пустые
    каталоги не выбираются. Неизвестный COMMIT может оставить пустой каталог.
    Цена: для них нужна отдельная очистка, если она потребуется.
13. Старые GUI и tracked env не менять: согласован новый CLI/core, миграция секретов
    не разрешена и не выполнялась.
    Цена: старый GUI сохраняет прежнее поведение; исторические credentials требуют
    отдельного внимания перед публикацией. Новый CLI их автоматически не читает.

## Отложенные minor

Импортированный оригинальный SQL fixture сохраняет CRLF: diff --check по полному
историческому диапазону отмечает CRLF как whitespace. Текущие изменённые
Rust/config/docs проходят diff --check. На SQL-поведение это не влияет.

Ветка и EXE остаются локально. Рабочая почта/БД не очищались, push/merge/deploy
и запуск удалённого CI не выполнялись.
