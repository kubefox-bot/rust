# Приёмка MVP

Проверки выполняются на синтетических данных. Рабочие почтовые ВМ и их
каталоги не использовались. CI/CD, публикация образов и развёртывание в
рабочей сети остаются отдельным этапом.

## Повторение проверок

```sh
mise run test:mvp
# Дополнительно: существующая локальная MySQL fixture и подготовленный release.
HMAIL_MVP_DATABASE=1 HMAIL_TEST_DOCKER_CONTEXT=colima \
  HMAIL_RELEASE_ENGINE=docker HMAIL_RELEASE_DOCKER_CONTEXT=colima \
  HMAIL_MVP_RELEASE_MANIFEST=target/releases/BUILD/release-manifest.json \
  mise run test:mvp
```

Машинный отчёт и логи каждого шага находятся в `target/acceptance`.
`PASS`, `FAIL` и `NOT RUN` сохраняются отдельно. Успешный exit code означает
отсутствие проваленных доступных проверок; непроверенные среды не становятся
успешными автоматически.

Общий harness и замеры используют POSIX-группы процессов и предназначены для
macOS/Linux. При таймауте или отмене завершается только принадлежащая проверке
группа, включая дочерние процессы. На Windows этот способ остановки явно
не поддержан; native Windows-проверки выполняются отдельно по инструкции
агента, а не подменяются этим harness.

Перед тестами SQL harness проверяет локальный Docker context, label
`hmail-cleanup-tests` и привязку MySQL к `127.0.0.1:13306`. Адрес БД для
этой проверки фиксирован и не наследуется из рабочего окружения.
Нативные разрушительные проверки требуют отдельного синтетического корня,
его fixture marker и имени тестовой службы. Проверки границ отвергают
отсутствующий marker, выход за корень, ссылки наружу и имя рабочей службы.

## Подтверждённые сценарии

| Область | Доказательство |
|---|---|
| Ручная очистка | Сначала подтверждение отсутствия файлов, затем SQL; fast/full и восстановление службы проверяются портами runner и disposable MySQL. |
| Доставка задания | Durable receipt до побочного эффекта, одна операция, один ID при потере ответа, отсутствие автоматического повторного clean. |
| mTLS | Настоящий локальный TLS: роль, UUID, serial, CA, имя, отзыв и несовместимый протокол до отправки профиля. |
| Доступ | Один суперадмин, одна сессия, CSRF, отзыв прежнего входа, credential races, смена пароля/recovery без перешифрования профилей. |
| Браузер | 29 Chromium-сценариев полного прогона; затем 16 связанных cleanup/history-проверок после исправления дробной даты через Rust HTTPS: две вкладки/сервера, отмена, потеря ответа, fullscreen, история, настройки, recovery и редактирование профиля. |
| История и футер | Обновление по событиям, одна SSE-подписка, освобождение на смене цели/выходе, 50 записей, явная ошибка, сводка каждого агента. |
| Остановка | Реальный CLI принимает SIGTERM/SIGINT, закрывает admission и выгружает ключ до drain; незавершённый KDF не открывает новую сессию. |
| Backup/health | Согласованный snapshot с vault/schema/build; health до входа не открывает SQLite повторно и проверяет CA/имя. |

Общий прогон завершил 10 доступных проверок без FAIL: Rust workspace — 287 passed, 32 ignored; отдельные проверки MySQL выполнили ещё 31 adapter и 1 agent сценарий. Типизация web — без ошибок/предупреждений, 19 unit tests. OCI lifecycle отдельно прошёл 10 проверок на Docker/Colima; Windows Server 2016 и native Podman/Quadlet остаются NOT RUN. Финальная пересборка и ресурсный отчёт дополняются после выполнения соответствующих команд.

## Остаётся выполнить в целевой среде

- Две изолированные Windows Server 2016 ВМ: настоящий SCM, DACL, файловые
  атрибуты/создание, MySQL и заранее установленный Win32-OpenSSH/SFTP.
- Rootless Podman и Quadlet на Linux с user systemd, cgroup v2, subuid/subgid
  и linger: генерация unit, выход пользователя, перезагрузка и сохранность тома.
- Межверсионное обновление и возврат выбранного digest с соответствующей
  резервной копией при продолжающемся задании отдельного агента.
- Наблюдение медленного SSE-потребителя в течение 30 минут. Ограничения
  journal/очереди проверены тестами, но короткий прогон не доказывает
  стабильность памяти за 30 минут.
