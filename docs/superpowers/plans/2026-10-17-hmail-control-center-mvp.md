# hMail Cleaner MVP — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Выпустить лёгкий центр в OCI-образе под Podman + Quadlet с единым интерфейсом ручной очистки двух hMailServer через нативных Windows-агентов.

**Architecture:** Один монорепозиторий: существующий Cargo workspace, Rust-центр и агенты, Astro static + Svelte в apps/web. В production центр раздаёт готовую статику, API и SSE одним Rust-процессом; очистка выполняется агентом рядом с почтой. Работы разделены на три проверяемые части с общими контрактами ниже.

**Tech Stack:** Rust 1.99.1, Axum + Tokio, SQLite + SQLx, существующие core/adapters, russh + russh-sftp, rustls + ring + rcgen, Argon2id + XChaCha20-Poly1305, Bun для сборки Astro + Svelte, rootless Podman + Quadlet/systemd.

**Spec:** [Спецификация](../specs/2026-10-17-hmail-control-center-design.md). Этот файл содержит общие решения; исполнители читают его вместе со спецификацией и соответствующей частью плана.

## Global Constraints

- Rust 1.99.1 для toolchain и объявленного MSRV; точный номер закрепляется в файлах сборки.
- Astro static + Svelte-острова; Rust-центр раздаёт статику и API с одного origin.
- Linux-ВМ с OCI-образом центра под rootless Podman + Quadlet/systemd на существующем Hyper-V-хосте; cgroup v2 и linger проверяются при подготовке ВМ. Windows Server 2016, x86_64-pc-windows-msvc, статический MSVC runtime для агентов.
- Центр обновляется целым образом по проверенному digest; остановка, backup, замена и проверка выполняются на Linux-хосте. Podman socket в центр не передаётся; автоматическое следование тегу и штатный auto-update timer в исходной поставке выключены.
- CI/CD — отдельный этап после MVP: workflow для автоматизации сборки, публикации и доставки сейчас не создаётся. В C4 остаются локальные проверки/сборка OCI-образа, ручной запуск Quadlet и ручное обновление с backup.
- Нативная SQLite + SQLx у центра; существующий MySQL-адаптер сохраняется без попутного обновления всей линейки зависимостей.
- Только ручная очистка. Расписание, дополнительные пользователи, полная ротация DEK и массовая очистка не входят в первую версию.
- Одна активная сессия. Таймауты: 15 минут, 30 минут, 1 час, 1 день; начальное значение — 15 минут.
- Полный технический профиль шифруется; Argon2id + XChaCha20-Poly1305, случайный DEK и отдельный recovery key.
- Принятое агентом задание переживает выход из панели и рестарт центра; после рестарта агента удаление автоматически не продолжается.
- Файл удаляется и его отсутствие подтверждается до SQL-delete; восстановление службы завершается до освобождения SQL-блокировки.
- Развёртывание на рабочих ВМ, публикация образов/релизов и очистка рабочей почты не разрешены этим планом.

## Review Focus

- Запоздалый POST после потерянного ответа и более раннего GET 404: не освободить слот и не выполнить повторное удаление — A2, B5.
- Центр на Linux, Windows-пути и неоднозначный местный час: сохранить цель и обе границы cutoff, отклонить DST-неоднозначность — A2, A4, B4, C2.
- Старый logout/таймер/вход с устаревшей версией учётной записи: не отозвать новую сессию и не воскресить старый DEK — B3, B7.
- Дисковая ошибка при принятии/финализации или потере питания: не выполнять неподтверждённое задание, не объявлять фиктивный успех — A2, A4, B2, C5.
- Медленный SSE, повторное открытие разделов, большие счётчики: ограничить память и DOM, не терять точность и финальный результат — B5, C1, C2, C5.

Начинаем с A1: фиксируем базовые проверки, выделяем существующий разовый запуск
из CLI и убираем расписание. Алгоритм очистки не переписываем.
Первая вертикальная проверка — один fixture-агент: preview → clean → cancel,
затем потеря ответа и рестарт центра. Полноценный UI подключается к уже
проверенному API. Макет остаётся визуальным образцом, его демонстрационная
логика не переносится в рабочую систему.

Каждая задача заканчивается проверкой и отдельным локальным коммитом.
Команды commit в частях плана — шаги будущего выполнения; при подготовке
этого плана коммиты и изменения исходников не выполняются.

## 2. Монорепозиторий и владельцы

~~~text
/
├── Cargo.toml / Cargo.lock
├── package.json / bun.lock          # Bun workspace; только frontend/tooling
├── mise.toml                       # общий вход в проверки и сборку
├── crates/
│   ├── core/                       # существующие правила очистки
│   ├── adapters/                   # существующие MySQL, FS, Windows/SCM
│   ├── cli/                        # существующий бинарник и пользовательские команды
│   ├── runner/                     # общий разовый сценарий CLI/агента
│   ├── protocol/                   # DTO, версии, идентификаторы и схемы API
│   ├── center/                     # центр: auth, vault, profiles, jobs, enrollment
│   └── agent/                      # агент: принятие, выполнение, локальная отчётность
├── apps/
│   └── web/                        # Astro static + Svelte
├── deploy/                         # Containerfile, Quadlet и примеры конфигурации
├── tools/                          # существующая сборка EXE и инструменты поставки
└── docs/                           # спецификация, планы, эксплуатация
~~~

Не переносить существующие crates и не вводить Nx/Turborepo. Cargo управляет
Rust-зависимостями, Bun — frontend, mise связывает команды. Для текущего объёма
дополнительный граф сборки не требуется. Один репозиторий не означает один
бинарник или общий набор зависимостей для всех поставок.

Направления зависимостей:

- core не знает HTTP, SQLite, Astro и Windows.
- runner использует core/adapters, не импортирует CLI, center или agent.
- protocol не импортирует приложения, драйверы БД, Windows API и UI.
- agent использует runner/protocol; SSH-клиент в агент не попадает.
- center использует protocol, но не runner и не почтовые MySQL/Windows-адаптеры.
- web использует сгенерированные браузерные контракты, не внутренние Rust-модули.

Существующий CLI остаётся точкой входа. Features: local-cli по умолчанию;
center и agent подключают соответствующие приложения. Linux-центр собирается
с --no-default-features --features center. Windows-пакет агента — с
--no-default-features --features local-cli,agent. Команды разовой очистки
сохраняются; hmail-cleaner center init/run/recover и agent enroll/run/service
добавляются явно. Прежний service run завершается диагностикой об удалённом
расписании и ничего не очищает.

SQLx workspace не навязывает mysql/sqlite всем приложениям: features драйверов
переносятся к потребителям без смены текущей версии 0.7.4. Отдельные cargo tree
и сборки проверяют отсутствие mysql/russh в неподходящих артефактах.

Центр и web выпускаются одним образом. Windows-агент — отдельным пакетом
с версией, SHA-256 и диапазоном протокола; версия wire-протокола независима
от версии сборки. В MVP протокол ровно v1. Несовместимая версия блокирует
рабочую команду до передачи профиля.

## 3. Общие контракты между частями

| Контракт | Владелец и содержание |
| --- | --- |
| RunRequest / RunResult / RunObserver | runner; типизированный запрос, прежний Report/exit codes, вывод отделён от выполнения |
| TechnicalProfile | center; MailProfile (MySQL, Data/INI, служба) и AgentCredentials; всё шифруется, клиентский TLS private key центром агенту не передаётся |
| JobCommand | protocol; protocol_version, job_id, agent_id, profile_id, profile_version, operation, scan, resolved_cutoff, service_policy, limits, MailProfile |
| ResolvedCutoff | protocol; local: NaiveDateTime для MySQL, file_cutoff_utc: DateTime<Utc>, utc_offset_seconds: i32 и resolved_at_utc; вычисляет целевой агент |
| RunLimits | protocol; batch_size 1..10000, workers 1..8; defaults 1000 и 2 сохраняются |
| JobSnapshot | protocol; идентичность задания, stream_epoch, revision, phase, stage, SummaryDto, наблюдаемое состояние службы, безопасная ошибка, время наблюдения |
| Agent phase | Accepted, Running, Cancelling, Restoring, Completed, Partial, Failed, Cancelled, Interrupted; отмена не является мгновенным terminal state |
| Center dispatch | PendingDispatch, DispatchUnknown, AgentSnapshot; неизвестность доставки не приравнивается к отказу агента |
| EventEnvelope | protocol; server_id, job_id при наличии, stream_epoch, revision и тип события; снимок/история авторитетнее доставки SSE |
| Browser schemas | protocol экспортирует только браузерные DTO в JSON Schema; web генерирует типы и проверяет ответы по тем же схемам |

UUID передаются каноническими строками. u64 в браузерных DTO — десятичные строки
с проверкой диапазона, а не неточные JS Number; адаптер SummaryDto отделён
от существующего Summary. Секретные структуры не получают вывод Debug
с содержимым. Публичные ошибки — код, безопасное сообщение и correlation_id;
сырые ошибки core/SQLx/SSH, URI, пути и ключи в сетевой журнал не сериализуются.

stream_epoch — UUID текущего запуска публикующего процесса. Revision растёт
в пределах epoch; после смены epoch потребитель запрашивает свежий снимок.
Промежуточные counters не требуют fsync на каждое событие: checkpoint не чаще
одного раза в 5 секунд, при смене фазы и terminal — обязательная запись.
После аварии counters показываются с временем последнего checkpoint,
а не как окончательный проверенный итог.

### Принятие и согласование

Агент использует локальную SQLite только для квитанций/состояния заданий,
не для копии центральных профилей. Открытые MailProfile и пароли остаются
в памяти выполнения. Уникальность job_id и единственная активная операция
обеспечиваются транзакцией до ответа Accepted и до запуска runner.
Для сравнения повтора сохраняется HMAC-SHA256 канонической команды; ключ
квитанций генерируется агентом и защищается локальными правами ОС.
Каноническая команда кодируется по документированной схеме protocol, без
зависимости от порядка полей JSON.

После рестарта прежние незавершённые задания становятся Interrupted;
фактическое состояние службы опрашивается, работа не возобновляется.
Квитанции завершённых job_id не удаляются ротацией подробных журналов.
GET неизвестного задания возвращает 404, ошибка чтения — отдельную ошибку.

Потерянный ответ POST сохраняет DispatchUnknown и общий слот. Один GET 404
не доказывает, что запоздавший POST не придёт. Явная отмена неизвестного job_id
создаёт у агента долговечную Cancelled-квитанцию, блокирующую поздний запуск.
После рестарта центр только запрашивает состояние прежнего job_id, а не
повторно отправляет команду clean. Ошибки восстановления службы показываются
отдельно; слот не освобождается только по факту исчезновения соединения.

## 4. Начальные инженерные значения MVP

Это решения исполнителя для реализации, не результаты измерений.
Все пределы именуются у владельца с единицами измерения и проверяются
тестами; изменение подтверждённых пользовательских сценариев недопустимо.

| Область | Исходное значение / правило |
| --- | --- |
| Параллельность | Одна операция preview/clean через центр; одна на агенте; одна SSH-установка; health/read доступны отдельно |
| Argon2id | v1.3, m=32768 KiB, t=3, p=1; salt 16 байт, output 32; два последовательных KDF при успешном входе, одна арена |
| Ключи | DEK 32 байта; recovery 32 байта; nonce XChaCha 24 байта; tag 16 байт; CSPRNG ОС |
| Recovery | hmc-recovery-v1: + 43 Base64URL символа без padding; подтверждение до commit; кандидат живёт 10 минут, один на сессию |
| Тела запросов | Login 8 KiB; технический профиль 64 KiB; обычный JSON API 128 KiB; пакет EXE передаётся потоком |
| Вход | Пароль 12..1024 Unicode scalar values, дополнительно максимум 4096 UTF-8 байт; без автоматической нормализации; логин 1..64 символа, до 256 байт, trim только логина |
| Ограничитель входа | Общий token bucket: ёмкость 6, пополнение 1 за 10 секунд; один KDF, без очереди, busy/rate limit возвращает 429 |
| Прогресс | Коалесцирование до 4 обновлений/секунду; шина 256 событий, кадр до 4 KiB; terminal result сохраняется до публикации |
| Соединения | До 64 у центра, 16 у агента; до 4 одновременных TLS-handshake на процесс; до 16 browser SSE; один idle HTTP connection на agent endpoint |
| UI | Одно SSE на вкладку; окно журнала 1000 записей; история по 50 строк, максимум 100 на запрос |
| Дисковый журнал | 10 MiB × 5 файлов на процесс; сообщения до 2 KiB; квитанции и результаты хранятся отдельно |
| Сеть | Connect 5 секунд; обычный control request 15 секунд; SSE heartbeat 15 секунд, timeout чтения 45 секунд; очистка не ограничивается этими сетевыми таймаутами |
| SQLite | WAL, synchronous=FULL, foreign_keys=ON, busy_timeout=5 секунд; маленький пул до 2 соединений у центра и 1 у агента |

Параметры Argon2 не снижаются автоматически. SSE/polling не продлевают сессию;
уведомление реальной активности объединяется не чаще одного раза за 30 секунд.
Для resource checks измерять RSS процесса и память контейнера отдельно,
с дополнительной разбивкой Linux-ВМ/процессов Podman; числовой бюджет RSS не придумывать.

### Криптографический формат

Использовать иерархию раздела 5.8 спецификации. Точный encode_aad определяется
в B1: big-endian, фиксированные UUID/числовые поля, версия формата 1, код типа
записи и длины перед переменными полями. Заголовок содержит vault_id,
record_id, record_version, key_id, key_generation, алгоритм и параметры/salt
вывода ключа для обёрток. Типы: profile=1, ca_key=2, center_client_key=3,
password_wrap=4, recovery_wrap=5. HKDF info начинается с hmail-cleaner/v1/
и разделяет password-wrap, recovery-wrap и record/<kind>/<record_id>.
Смена учётной версии не меняет AAD профилей и не требует их перешифрования.

### TLS и bootstrap

Частный CA создаётся при init: CA key и клиентская identity центра шифруются
в SQLite. HTTPS server key центра доступен до входа и хранится в каталоге
bootstrap с правами ОС; публичный CA экспортируется для доверия браузера.
Origin задаётся явно, сертификат включает реальные DNS/IP из конфигурации.
Agent key и CSR создаются на Windows-ВМ; private key не покидает агент.

Исходные сроки: CA 10 лет, HTTPS центра 1 год, mTLS identities 90 дней;
предупреждение за 14 дней. Продление выполняется после входа через управление
агентом; просроченное доверие восстанавливается через проверенный SSH.
Не использовать accept-invalid-certs или автоматическое доверие host key.
SSH probe не принимает пароль: сначала показать SHA-256 fingerprint, затем
явное подтверждение доверия и аутентификация. Изменившийся ключ блокирует
операцию. Пароль/закрытый SSH-ключ живут только в пределах установки.

URI SAN: urn:hmail-cleaner:center:<uuid> и urn:hmail-cleaner:agent:<uuid>.
SAN/EKU/identity разрешает центр, а не CSR. Проверять цепочку, имя endpoint,
роль и ожидаемый UUID во время TLS-handshake, до передачи MailProfile.
Отзыв хранится как denylist серийных номеров; применение обновляет verifier
и закрывает старые соединения. Ключи обновляются атомарно; не запускать
самостоятельное обновление агента во время очистки.

## 5. Проверки и границы готовности

- A1–A5: portable unit/integration + disposable MySQL + Windows SCM fixture.
- B1–B7: SQLite/tempdir, fake clock, TLS/SSH fixtures, два agent test doubles;
  сбои до/после commit, timeout, запрет выдачи секретов.
- C1–C5: browser tests из production-статики Rust, контейнер с persistent volume,
  два изолированных Windows Server 2016 агента на синтетической почте.
- Сборка на windows-2022 не является запуском на Server 2016; cross-build,
  контейнерный smoke и реальная Windows-приёмка отмечаются раздельно.
- Перед публикацией: исходники/тесты → Linux Podman + Quadlet → целевая Windows →
  ресурсный отчёт. Недоступная среда обозначается NOT RUN, не PASS.

Конкретные команды и assertions находятся в частях плана. Никакие package
install, сборки продукта или эти тесты не выполнены при написании документов.
