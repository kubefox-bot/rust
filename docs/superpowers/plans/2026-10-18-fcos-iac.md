# Portable FCOS IaC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Добавить переносимую первоначальную настройку FCOS для существующего Rust-центра без управления ВМ.

**Architecture:** Butane YAML и файлы FCOS находятся в `iac/fcos`; официальный Butane преобразует их в Ignition. Оператор вручную создаёт ВМ, настраивает сеть и устанавливает FCOS с обычного live ISO. После подготовки ОС используется существующая локальная OCI-поставка с интерактивным init.

**Tech Stack:** Fedora CoreOS Stable, Butane schema 1.6.0, Ignition, Podman/Quadlet, systemd, Zincati. Новые production-генераторы, зависимости приложения и CI/CD не добавляются.

**Spec:** [Согласованная спецификация](../specs/2026-10-18-fcos-iac-design.md).

## Global Constraints

- Пользователь вручную создаёт ВМ, выбирает ресурсы, подключает официальный FCOS Stable live ISO, подготавливает диск и сеть.
- Конфигурация не создаёт ВМ, не содержит KVP, cloud metadata, имён виртуальных коммутаторов, гипервизорных команд или жёстко заданного `/dev/sda`.
- CI/CD, публикация, registry credentials, автоматические обновления приложения, Ansible и развёртывание на рабочих серверах не входят в эту задачу.
- Отдельный обычный пользователь `hmail-center` с домашним каталогом в `/var/home`.
- Zincati с periodic strategy: воскресенье, 03:00–04:00 UTC.
- Результат находится под `target/iac/fcos/` и не коммитится.
- Новый генератор, шаблонизатор или пакетный менеджер в первом изменении не добавляется.
- `Pull=never` остаётся действующим контрактом. Шаблоны Quadlet принадлежат `deploy/quadlet`.
- Установка не начинает центр до интерактивного init; пароль и recovery key отсутствуют в IaC.
- Рабочая ветка остаётся `ci/hmail-control-center-mvp`; новый worktree не нужен. Публикации и установки на рабочие машины нет.

## Review Focus

- Отсутствующий/пустой публичный ключ: подготовка завершается ошибкой, готовый JSON не заменяется; проверяет задача 1.
- Чужой CWD и пути с пробелами: `--files-dir` получает явный путь, нужные два файла встраиваются; проверяет задача 1.
- Соседние приватные файлы: в staging переносятся только публичный ключ и Zincati TOML, не весь local/ или HOME; проверяет задача 1.
- Rootless user manager без входа: linger и владельцы каталогов корректны; загрузка и reboot считаются подтверждёнными только реальной VM-проверкой; задачи 1–2.
- ISO с выбором диска и переносом сети: документация не превращает подготовку JSON в разрушительный autoinstall и не обещает автоматический запуск неинициализированного центра; проверяет задача 2.

## File Structure and Ownership

- Create `iac/README.md`: граница IaC и ссылка на FCOS.
- Create `iac/fcos/config.bu`: пользователи, subordinate IDs, linger, каталоги и reference на Zincati TOML.
- Create `iac/fcos/files/zincati.toml`: окно обновления ОС.
- Create `iac/fcos/local.example/README.md`: подготовка реального публичного ключа; фиктивный ключ не поставляется.
- Create `iac/fcos/README.md`: prerequisites, генерация/проверка JSON, установка, postboot acceptance, приложение и восстановление.
- Modify `.gitignore`: ровно `/iac/fcos/local/`; результат уже покрывает `/target/`.
- Modify `README.md`: ссылка на IaC рядом с развёртыванием центра.
- Modify `docs/center-deployment.md`: ссылка на FCOS-подготовку перед существующей процедурой установки приложения.
- Existing `deploy/quadlet/*`, `tools/release/*` и их публичные контракты не меняются.

## Task 1: Конфигурация FCOS и проверка результата

**Files:** Create `iac/fcos/config.bu`, `iac/fcos/files/zincati.toml`, `iac/fcos/local.example/README.md`; Modify `.gitignore`.

**Interfaces:**
- Consumes: публичный ключ `iac/fcos/local/admin.pub` и существующий OCI/Quadlet runtime contract.
- Produces: `config.bu` schema 1.6.0; два reference относительно `--files-dir`: `admin.pub`, `zincati.toml`. Временный staging содержит только эти два файла; Butane читает `config.bu` отдельным аргументом.
- Runtime identity: `hmail-center` UID/GID 2000, home `/var/home/hmail-center`, shell `/bin/bash`, без sudo/wheel и SSH-ключей. Subordinate UID/GID: start 200000, count 65536. Значения предназначены для новой штатной FCOS; после загрузки диапазоны проверяются на пересечения с реальными записями.

- [x] **Step 1: Задать исполняемые критерии проверки до добавления конфига.**

  Использовать временный реальный публичный Ed25519-ключ, созданный disposable `ssh-keygen`, и staging вне исходников. Официальный Butane должен вернуть 0, а Ignition validator — принять JSON. До создания `config.bu` проверка преобразования должна завершиться ошибкой отсутствия исходника. Проверки выполняются командами, сохраняемыми в инструкции задачи 2; отдельный production test framework не добавляется.

- [x] **Step 2: Реализовать `iac/fcos/config.bu`.**

  `core` получает ключ через `ssh_authorized_keys_local: [admin.pub]`. Явная группа GID 2000 и обычный пользователь UID 2000 с `primary_group: hmail-center` и `no_user_group: true`. В `/etc/subuid` и `/etc/subgid` добавляется строка `hmail-center:200000:65536` через `append`, без замены существующего содержимого. Linger: `/var/lib/systemd/linger/hmail-center`, mode 0644. Каталоги `.config`, `.config/containers`, `.config/containers/systemd` под home имеют mode 0700 и владельца пользователя. В `/etc/zincati/config.d/50-hmail-center.toml` встраивается `zincati.toml`, mode 0644.

- [x] **Step 3: Реализовать окно Zincati и изоляцию локальных входов.**

  TOML содержит `strategy = "periodic"`, `time_zone = "UTC"`, `days = ["Sun"]`, `start_time = "03:00"`, `length_minutes = 60`. В `.gitignore` добавить только локальный каталог. `local.example/README.md` объясняет копирование публичного `.pub` и не создаёт готовый ключ вместо оператора.

- [x] **Step 4: Выполнить настоящую положительную проверку.**

  Использовать официальные Butane и `ignition-validate`; доступны native tools или официальные контейнеры на выбранном локальном Docker/Podman. Контейнеру требуется только bind mount staging и исходного YAML, без `--privileged`, `/dev`, HOME или engine socket. На текущем macOS использовать существующий Docker context `colima`, не переключая глобальный context. Записать реальные версии, а при контейнерном запуске и image digests; несовместимость schema завершает проверку ошибкой.

  Команда Butane: `butane --pretty --strict --files-dir <staging> <absolute-config.bu>`. Сначала писать результат во временный файл, проверять его validator, затем переименовывать в `target/iac/fcos/config.ign`. Валидатор вызывается согласно фактическому `--help` выбранной версии. Для любого ненулевого exit code выпуск JSON прекращается.

  Разобрать JSON имеющимся Bun и подтвердить: ключ совпадает побайтно, UID/GID/home/group корректны, оба subid файла используют append, linger существует, три каталога имеют owner 2000 или эквивалентное имя и mode 0700, декодированный Zincati TOML совпадает с исходным. Не считать одну успешную schema validation проверкой этих runtime-смыслов.

- [x] **Step 5: Проверить пять отказов и переносимость подготовки.**

  Повторить генерацию из другого CWD с staging-путём с пробелами. Отдельно проверить отсутствующий ключ, пустой ключ (явный preflight `test -s`), испорченный YAML и несовместимую schema version на временных копиях. В каждом случае итоговый JSON отсутствует либо остаётся прежним проверенным файлом. Поместить sentinel рядом с ключом и подтвердить его отсутствие в JSON. Проверить, что config не содержит network/hostname/firewall изменений, VM API, disk partition directives, production secrets, unit запуска приложения или копии Quadlet. Проверить `git check-ignore` для `local/admin.pub` и `target/iac/fcos/config.ign`.

- [x] **Step 6: Commit.**

  `git diff --check`; коммит только файлов задачи: `feat(iac): add portable FCOS bootstrap configuration`.

## Task 2: Воспроизводимая инструкция и handoff приложению

**Files:** Create `iac/README.md`, `iac/fcos/README.md`; Modify root `README.md`, `docs/center-deployment.md`.

**Interfaces:**
- Consumes: файлы и checked generation workflow задачи 1.
- Produces: операторская инструкция от обычного FCOS live ISO до существующей инструкции установки центра; реальные результаты проверок с отдельными NOT RUN.

- [ ] **Step 1: Описать подготовку без нового генератора.**

  Привести проверенные команды для Linux с официальными native tools; контейнерный вариант допустим как отдельная проверенная альтернатива. Указать выбор совместимых версий и фактически проверенные версии. Команды вычисляют root через `git rev-parse --show-toplevel`, используют quoted paths, временный staging с очисткой, копируют два именованных файла и блокируют отсутствие/пустой ключ. После successful compile+validation атомарно публикуют JSON и считают SHA-256. Не выдавать mutable image tag за закреплённую версию и не обещать побайтовую воспроизводимость без фиксации входов.

- [ ] **Step 2: Описать передачу destination Ignition и ручную установку.**

  Локальный файл на отдельно подключённом носителе — основной путь. Оператор выполняет `lsblk`, выбирает устройство и только затем вызывает `coreos-installer install --ignition-file <path> --copy-network <chosen-disk>`. Пояснить destructive effect и отключение ISO после установки. Альтернатива — `--ignition-url` с HTTPS; HTTP только с `--ignition-hash sha256-<actual-hash>`, без `--insecure-ignition`. Перенос сети применяется при наличии подготовленных NetworkManager keyfiles; DHCP отдельно поясняется. Не использовать флаги неизвестной версии без сверки с help.

- [ ] **Step 3: Описать postboot acceptance и установку центра.**

  Проверить `getent`, home/owner, оба subordinate ID ranges на пересечения, `loginctl show-user hmail-center -p Linger`, доступность его user manager, rootless/cgroup v2 через `podman info` под служебным пользователем. Дать проверенный способ открыть shell и подключиться к user manager из административного SSH-сеанса; не предполагать, что голый `sudo -u` создаёт XDG runtime/session bus. Затем ссылка на существующие manifest verification, `podman load`, named volume, интерактивный init, установку generated release Quadlet, health и browser CA trust. Не копировать весь действующий runbook.

  Явно объяснить firstboot-only, отдельное обновление приложения, ограничение periodic Zincati относительно активных заданий и отсутствие автоматического backup. Восстановление ссылается на `docs/recovery.md`; данные и identities не клонируются в общий образ.

- [ ] **Step 4: Проверить документацию и доступную среду.**

  Повторить документированную генерацию с disposable public key. Проверить все новые относительные ссылки, `git diff --check`, отсутствие tracked local/outputs/secrets. Если доступный локальный QEMU позволяет disposable boot без изменения пользовательских ВМ, выполнить и записать smoke с подходящей архитектурой; иначе отметить загрузку, SSH, rootless, logout/reboot NOT RUN. Не устанавливать/настраивать Hyper-V, не заявлять универсальную runtime-совместимость по schema validation. Полный Rust/web rebuild не требуется: runtime исходники не меняются.

- [ ] **Step 5: Финальная проверка и commit.**

  Сопоставить каждый критерий спецификации с фактическим результатом. Проверить границы безопасности и отсутствие дублирования runtime contracts. Коммит: `docs(iac): document portable FCOS installation and acceptance`. Финальный отчёт содержит пути, hashes/versions проверенных инструментов, actual PASS/FAIL/NOT RUN и оставшиеся VM-проверки. Push/deploy не выполняются.
