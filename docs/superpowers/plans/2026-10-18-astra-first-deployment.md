# Первое развёртывание Astra

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to execute this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Развернуть Astra на тестовой FCOS ВМ, доказать обновление и восстановление, затем перенести проверенную поставку на рабочую ВМ.

**Architecture:** Rust-центр и статический Astro/Svelte работают в одном контейнере через rootless Podman и Quadlet. GitHub Actions публикует проверенную поставку; отдельный host updater проверяет подпись, заранее скачивает образ, закрывает приём новых операций, ожидает активные задания и переключает контейнер с offline backup. Данные находятся вне образа.

**Tech Stack:** Fedora CoreOS Stable, Podman/Quadlet, Rust, Bun, GitHub Actions/GHCR, Cosign/Sigstore, SQLite, Windows-службы агентов.

**Spec:** [Согласованный проект доставки](../specs/2026-10-18-center-image-delivery-design.md), [runbook CI/CD](../../center-cicd.md).

## Границы и исходное состояние

Локальное слияние CI/CD не публикует релиз: workflow доставки запускается при push в `main`, публикация дополнительно закрыта `ASTRA_DELIVERY_ENABLED`. Текущий запрос разрешает локальное слияние и план; push, включение публикации, доступы, установка ОС и рабочее развёртывание выполняются после отдельного согласования конкретной цели.

Начальный target — Linux amd64 в Hyper-V ВМ. Пользователь хоста `hmail-center` UID/GID 2000; контейнер UID/GID 10001 с существующим keep-id mapping. Сохраняем read-only rootfs, SELinux, named volume `hmail-center-data`, digest pin, `Pull=never`. Engine socket не передаётся приложению. Secrets не попадают в Git, Ignition или образ.

Проверки исходной delivery-ветки описаны в [отчёте](../../center-cicd-acceptance.md). Они не доказывают работоспособность новой объединённой сборки на FCOS. Нужны новые артефакты из зафиксированного commit и отдельные runtime-протоколы приёмки.

## 1. Зафиксировать параметры установки

- [ ] Записать целевой Hyper-V хост, отдельную тестовую ВМ, архитектуру, ресурсы и новый целевой диск. Проверить требования выбранного FCOS ISO к прошивке и загрузке ВМ.
- [ ] Утвердить IP/DNS, постоянный HTTPS origin и порт 8443 до `center init`; подготовить административный SSH public key и доверие CA в браузере.
- [ ] Выбрать внешнее место резервных копий, срок хранения и процедуру получения recovery key оператором.
- [ ] Уточнить видимость GitHub/GHCR и необходимость host credentials только на чтение. Зафиксировать доступ к GitHub API, release assets/CDN, GHCR и источникам FCOS.

**Выход:** карточка установки без секретов, точный target и разрешение на его изменение. Диски существующих машин не выбираются автоматически.

## 2. Получить проверенную поставку

- [ ] Отправить согласованную ветку/PR и выполнить GitHub CI: portable checks, MySQL и Windows jobs. До этого локальные тесты не обозначать как успешный GitHub CI.
- [ ] Из чистого зафиксированного SHA собрать согласованные center OCI, Windows agent и Linux updater package. Проверить build identity, manifest, digest и состав поставки.
- [ ] Сохранить CI run/artifact ID, SHA и результаты проверок. Для первоначальной тестовой установки использовать проверенную локальную/offline поставку; публикацию рабочего канала оставить выключенной.

**Выход:** конкретный неизменяемый комплект и воспроизводимая запись его происхождения.

## 3. Поднять тестовую FCOS ВМ и центр

- [ ] По [portable IaC](../../../iac/fcos/README.md) собрать и проверить Ignition с выбранным public key; сохранить версию ISO, IaC SHA и checksum JSON. Установить только на подтверждённый новый диск.
- [ ] После загрузки проверить сеть, SSH host key, UID/GID, все subuid/subgid ranges, private permissions, linger, user manager и rootless Podman/cgroup v2.
- [ ] По [runbook центра](../../center-deployment.md) загрузить точный образ, создать volume и интерактивно выполнить `center init` с утверждённым origin. Пароль и recovery key вводит/сохраняет оператор.
- [ ] Установить Quadlet, сгенерированный из этой поставки; проверить HTTPS health до входа, вход, шапку, настройки и сохранение данных после restart и выхода из SSH.
- [ ] Сделать согласованный backup и восстановить его на отдельной тестовой копии с matching image и сохранёнными mappings. Проверить SQLite, CA/TLS, настройки и повторный вход.

**Выход:** работающий центр и доказанное восстановление из копии вне ВМ. Сам факт запуска контейнера этого не заменяет.

## 4. Подключить тестовые агенты

- [ ] На тестовой Windows Server 2016 установить native agent как службу из той же поставки. Проверить SCM, сеть, SSH provisioning и mTLS, перезапуск службы и обновление сертификата.
- [ ] Настроить отдельные тестовые MySQL и почтовый каталог; выполнить предпросмотр, проверить SSE, таблицу файлов, поиск, сортировку, фильтры и пагинацию.
- [ ] После отдельного разрешения на удаление тестовых файлов проверить подтверждение очистки, прогресс, журнал, отмену и восстановление исходного состояния почтовой службы.

**Выход:** native Windows и полный тестовый сценарий подтверждены отдельно от моков. Реальную почту на этом этапе не используем.

## 5. Проверить доставку и восстановление на FCOS

- [ ] Установить проверенный updater package, Cosign и закреплённый trust root по runbook. Credentials/config оставить на хосте с private permissions; зафиксировать установленную версию updater.
- [ ] Проверить maintenance socket и право доступа служебного пользователя. Сохранить default policy: discovery 60 секунд, graceful timeout 15 минут; подтвердить изменение из настроек и сохранение после restart.
- [ ] На двух проверенных тестовых сборках доказать pre-download, закрытие новых операций, ожидание текущего задания, offline backup, переключение и health с ожидаемым build. При занятом/неизвестном задании timeout должен отложить update без принудительной отмены.
- [ ] Проверить отказ при неверной подписи, несовместимой schema/protocol, нехватке места, недоступной сети и плохом health кандидата. Прежний рабочий образ/данные сохраняются; общий prune не выполняется.
- [ ] Проверить recovery после остановки updater на границах transaction. До `Exposing` допустим возврат matching backup; после `Exposing` автоматическое восстановление старых данных запрещено. Потеря ответа не считается разрешением повторить restore.

Для проверки подписанной сетевой доставки отдельно согласовать публикацию тестовых артефактов. Если используется основной канал, до проверки подписей не включать production timer и не считать offline проверку end-to-end доставкой GitHub → FCOS.

**Выход:** протокол обновления, отказов и восстановления с build/digest, журналами и ожидаемым состоянием данных. Updater/trust root не обновляются этим механизмом автоматически.

## 6. Проверить обновление ОС

- [ ] Связать уникальный node UUID updater с Zincati, запустить FleetLock coordinator. Проверить loopback identity/group и сохранение grant при перезапуске.
- [ ] Проверить отказ reboot при занятом updater, активных заданиях и недоступном центре; проверить штатную перезагрузку и steady-state после неё. Окно ОС — воскресенье 03:00–04:00 UTC.
- [ ] После reboot проверить SELinux, rootless socket, запуск user units без SSH, сохранность профилей/CA/SQLite и повторный вход суперадмина для разблокировки vault.

**Выход:** настоящий FCOS reboot подтверждён. Одна ВМ означает перерыв доступности панели во время перезагрузки.

## 7. Первый рабочий rollout

- [ ] Приложить результаты этапов 1–6 и получить разрешение на конкретную рабочую ВМ, публикацию и доступы. В согласованное окно сделать внешнюю резервную копию.
- [ ] Установить ту же проверенную поставку по digest; подключать рабочие серверы по одному, начиная с предпросмотра и проверки путей/границы времени.
- [ ] После допуска публикации включить `ASTRA_DELIVERY_ENABLED`, проверить реальный main workflow, подпись descriptor и продвижение канала; затем включить timer на согласованной ВМ. Проверить первый полный цикл доставки и наблюдать журналы.
- [ ] Зафиксировать ответственного, доступ к backup/recovery, диагностику и процедуру паузы `astra-updater.timer`. Остановка timer не прерывает текущую transaction.

**Выход:** журнал рабочего развёртывания с отдельными PASS/FAIL/NOT RUN для GitHub, FCOS, Windows, браузера и восстановления. После открытия новой версии пользователям восстановление старой БД требует отдельного решения по новым данным; смена одного образа не является достаточным rollback.
