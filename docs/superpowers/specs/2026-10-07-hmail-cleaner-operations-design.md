# hMailServer cleaner: полная очистка и способы запуска

Дата: 2026-10-07. Статус: предложенный дизайн для согласования; расширения
ещё не реализованы. Дополняет [базовый дизайн](2026-10-07-hmail-retention-design.md),
а не отменяет его правила возраста, путей и порядка удаления.

## Цель и согласованные решения

Завершить очистку старых писем, файловых остатков и связанных записей БД.
Целевая установка — Windows Server 2016 / 1607 x64, hMailServer и существующая
локальная MySQL 5.7.21. Docker на рабочем сервере не требуется.

Пользователь подтвердил:

- Для связанных с БД писем возраст определяется `messagecreatetime`; для
  файлов без записи — датой изменения файла.
- После удаления файла нужно подтвердить его отсутствие до SQL-шага;
  временные блокировки допускают ограниченные повторы.
- Нужны счётчики результата, мини-меню, настройки через env и тихий запуск.
- Нужна настоящая служба Windows; она сама останавливает hMailServer перед
  очисткой и запускает после неё.

Предложения, которые фиксирует этот документ: быстрый и полный режимы;
дочистка исторических metadata/recipients в полном режиме; отсутствие
постоянного файлового каталога; ежедневное расписание службы из явной настройки.
Реальные настройки расписания и подключения задаёт оператор на сервере.
Запуск на рабочей установке и публикация ветки не входят в реализацию.

## Причина отдельной дочистки БД

Если исторически удаляли только `hm_messages`, могли остаться:

- `hm_message_metadata`, где `metadata_messageid` уже отсутствует в `hm_messages`;
- `hm_messagerecipients`, где `recipientmessageid` уже отсутствует в `hm_messages`.

Текущее удаление выбранных писем уже очищает соответствующие строки этих таблиц
в одной транзакции. Оно не выбирает исторические записи без родителя.
В предоставленном DDL есть первичные ключи `metadata_id` и `recipientid`,
индексы на ссылки на письмо и нет объявленных каскадных внешних ключей.
Наличие и число исторических остатков на рабочем сервере пока неизвестны.

Очистка всей таблицы и удаление её строк по собственной дате не нужны.
Основание дочистки — отсутствие родительского `hm_messages.messageid` при
остановленном hMailServer. Аккаунты и логические IMAP-папки только читаются.

## Быстрый и полный режимы

Параметр `--scan fast|full`, по умолчанию `fast`, независим от команды
`preview|clean`. Быстрый режим сохраняет выборку MySQL, точные файловые пути
и порционное удаление базового алгоритма. Полного обхода Data в нём нет;
существующая проверка повторяющихся имён по БД сохраняется.

Полный `clean` при удерживаемом lock БД и STOPPED hMailServer выполняет:

1. Быструю очистку старых писем и их связанных строк.
2. Дочистку исторических metadata и recipients без родительского письма.
3. Полную загрузку набора GUID всех файловых ссылок, оставшихся в БД.
4. Обход допустимого хранилища и удаление старых файлов без ссылки.
5. Удаление пустых затронутых физических каталогов.

Любая фатальная ошибка SQL прекращает новые шаги. Неизвестный результат
COMMIT не считается успехом и останавливает проход. Частичные файловые ошибки
сохраняют соответствующие строки и отражаются в счётчиках.

`preview --scan full` только читает БД и атрибуты файлов и показывает кандидатов
для каждой категории. Для согласованной полной сверки он требует уже
остановленного hMailServer. Preview никогда сам не останавливает службу.
Быстрый preview остаётся доступен при работающем сервере.

Preview показывает текущих кандидатов, а не сохранённый план и не обещание
результата clean. В частности, он не предсказывает новые файловые остатки,
которые могут стать несвязанными после быстрой SQL-фазы. Для одинаковой
границы двух запусков применяется явный BEFORE; ошибки файлов и изменения
состояния учитываются заново при clean.

## Исторические остатки metadata и recipients

Используется один механизм с двумя фиксированными описаниями таблиц:

| Таблица | Первичный ключ | Ссылка на письмо |
| --- | --- | --- |
| `hm_message_metadata` | `metadata_id` | `metadata_messageid` |
| `hm_messagerecipients` | `recipientid` | `recipientmessageid` |

Preflight проверяет новые используемые первичные ключи и прежние требования
InnoDB/SELECT/DELETE. Новых прав на другие таблицы и ALTER не требуется.

Для каждой таблицы фиксируется верхний ID. Кандидаты выбираются порциями по
первичному ключу с `NOT EXISTS` соответствующего `hm_messages.messageid`.
Нет OFFSET, запроса на каждый файл или одного неограниченного DELETE.

В отдельной транзакции порции повторно проверяется отсутствие родителей,
удаляются только отобранные первичные ключи, подтверждается COMMIT и проверяется
отсутствие этих строк. Разрешён только фиксированный список таблиц/колонок;
значения ID передаются SQL-параметрами. Если условие изменилось, строка
сохраняется, а расхождение отмечается как ошибка.

Счётчики увеличиваются только после подтверждения удаления. Потеря ответа
COMMIT даёт неопределённый результат и остановку; повторный запуск согласует
фактически оставшееся состояние. Отмена заканчивает начатую порцию.

## Файлы без ссылки и память

Постоянные SQLite/Turso, синхронизация в облако и сохранённый план удаления
в этот этап не входят. Файловый обход идёт потоком с ограниченной порцией,
а не складывает все пути и атрибуты в память.

Набор ссылок содержит GUID из всех `hm_messages`, включая новые письма,
очередь и публичные сообщения. Ссылка на GUID защищает такой файл от удаления
как остатка даже при повреждённом владельце или неоднозначном пути.
Ссылки с повторяющимся GUID также защищают все совпадения.
Ошибка чтения БД или невозможность однозначно прочитать файловую ссылку
блокирует фазу удаления файлов без записи.

Для этой версии предел — 1 000 000 уникальных GUID, с ранней проверкой до
добавления следующего элемента. Превышение явно прекращает фазу файловых
остатков, а не использует неполный набор. Предел ограничивает число элементов,
а не обещает конкретный RSS. Реальный расход RAM измеряется на проверке;
временный SQLite-индекс остаётся отдельным последующим решением для больших баз.

Обход остатков ограничен физической структурой
`Data/domain/account/XX/{GUID}.eml`, где XX соответствует первым двум символам
GUID. Файлы в корне Data (очередь), `#Public`, посторонние имена, links/reparse
points и неподдерживаемые пути не удаляются этим обходом. Старые абсолютные
пути писем по-прежнему обрабатываются через обычную SQL-карту внутри Data.

Доступность всего допустимого дерева проверяется предварительным проходом
без удаления. При ошибке обхода фаза остатков не запускается. Затем выполняется
поточный проход удаления с повторной проверкой каждого кандидата. Это два
обхода в полном режиме — осознанная цена за отказ удалять по неполному обзору.
Перенос Data и сторонние писатели исключаются на всё время обслуживания.

Возраст остатка — `LastWriteTime`, а не создание файла и не MIME-заголовок Date.
Граница SQL остаётся локальной датой сервера; для атрибутов она один раз
преобразуется в абсолютное время. Неоднозначная/несуществующая локальная дата
при смене часового пояса блокирует фазу остатков с явной ошибкой.
Перед удалением повторно проверяются тип, путь, размер и дата изменения;
изменившийся файл сохраняется с сообщением в отчёте.

## Подтверждение удаления, повторы и счётчики

После запроса удаления проверяется отсутствие пути без следования ссылкам.
Только явный NotFound после проверки корня/цепочки допускает SQL-удаление.
AccessDenied и другие ошибки чтения атрибутов не превращаются в отсутствие.
Если файл остаётся или проверка результата не удалась, строка БД сохраняется.

На Windows повторяются только временные sharing/lock violations и ожидание
завершения удаления. Всего до трёх попыток; паузы перед второй и третьей —
100 и 300 мс. Эти значения принадлежат файловому адаптеру. Ошибки прав,
повреждённые пути и ошибки диска не получают слепых повторов; ACL не меняются.

Вывод и журнал содержат отдельные счётчики:

- выбранные письма, подтверждённо удалённые файлы, отсутствовавшие файлы;
- подтверждённо удалённые сообщения, metadata и recipients выбранных писем;
- отдельно удалённые исторические metadata и recipients;
- просмотренные файлы, выбранные и удалённые файлы без записи;
- сумма размеров подтверждённо удалённых файлов, удалённые папки и ошибки.

Сумма размеров — логический объём файлов, а не гарантированное увеличение
свободного места NTFS. Файлы со статусом ошибки/неопределённости в неё не входят.
Счётчики не смешивают preview-кандидатов с подтверждёнными удалениями.

## Env, мини-меню и тихий запуск

Приоритет значений: CLI → системная среда → явно указанный env-файл → статические
defaults. Период и пути обязательны, придуманного срока удаления нет.
Пара периода (`OLDER_THAN` либо `BEFORE`) выбирается целиком на одном уровне:
CLI заменяет всю пару из env. Два варианта на выбранном уровне дают ошибку.

Параметры: DATABASE_URL, HMAIL_DATA_DIR, HMAIL_INI, HMAIL_OLDER_THAN либо
HMAIL_BEFORE, HMAIL_SERVICE_NAME, HMAIL_BATCH_SIZE, HMAIL_WORKERS, HMAIL_SCAN,
HMAIL_LOG_FILE. Остаются defaults batch=1000, workers=2, scan=fast,
service_name=hMailServer. Старые `.env` автоматически не загружаются;
пароль и полный URL не попадают в вывод. Вся загрузка/валидация принадлежит
существующему модулю config; оболочки получают типизированные настройки.

`menu --env-file <path>` открывает простое текстовое меню: настройки/период,
быстрый preview, полный preview, быстрый clean, полный clean и выход.
Запуск без команды открывает меню только при интерактивном терминале;
иначе показывает ошибку использования. Выбор периода действует на текущую
сессию и не переписывает приватный env-файл. Перед clean меню показывает
границу и требует явного подтверждения выбранной операции.

Существующие прямые `preview`/`clean` остаются. Новая явная опция
`--manage-service` разрешает разовому clean управлять остановкой hMailServer;
обычный clean сохраняет требование уже STOPPED. В меню это отдельный явно
показанный выбор, а не скрытая остановка при preview.

`--silence` отключает меню, запросы и консольный прогресс и требует явного
`--log-file` или HMAIL_LOG_FILE. Ошибки и итог пишутся в локальный NDJSON-журнал;
сохраняются прежние ненулевые exit-коды. Silence несовместим с menu и --json.
Лог открывается до любых остановок/удалений. Ошибка записи просит отмену,
завершает начатую порцию и возвращает ошибку. Ротация: 10 MiB на файл,
до трёх архивов; значения принадлежат владельцу журнала.

## Windows-служба и владение остановкой почты

Один EXE имеет отдельный `service run --env-file <absolute-path>` для запуска
SCM. Вход, сообщения состояния и обработка Stop/Shutdown реализуются через
уже используемое семейство windows-service. Регистрация через стандартные
средства Windows описывается в инструкции; сам cleaner не устанавливает
службу, не создаёт аккаунты и не меняет доступ при обычном запуске.

Служба называется hMailCleaner и использует обязательные HMAIL_RUN_AT=HH:MM
и абсолютный HMAIL_LOG_FILE. Ежедневный запуск — по локальным часам сервера.
При старте служба ждёт следующего будущего времени, не начинает удаление
немедленно и не догоняет пропущенные дни. В несуществующее локальное время
запуск в этот день пропускается; при повторении часа выполняется один раз.
Если проход занял время следующего запуска, очередь проходов не создаётся.
Служба использует быстрый режим; полный проход запускается отдельно вручную.
Настройки считываются при старте; после изменения файла службу перезапускают.
Граница HMAIL_OLDER_THAN вычисляется заново для каждого прохода.

Порядок управляемого прохода:

1. Проверить настройки/журнал/INI/Data и подключение, схему, lock и SQL-права.
2. Прочитать состояние hMailServer. Running разрешает управляемую остановку;
   уже Stopped сохраняет владение оператором; другие состояния дают ошибку.
3. Для Running отправить Stop и ждать Stopped до 60 секунд. При отказе или
   таймауте ничего не удалять. Если cleaner уже отправил Stop, обязанность
   восстановления остаётся у него; не начинать следующую очистку.
4. Выполнить core с прежними проверками STOPPED перед каждой порцией.
5. При успехе, обычной ошибке или отмене дождаться начатой порции, затем
   восстановить Running, только если этот проход остановил почту.
6. Дождаться восстановления до 60 секунд, записать итог и освободить lock БД.

Ошибки восстановления сохраняются рядом с исходной ошибкой очистки; успешного
итога при неудачном восстановлении нет. Восстановление имеет собственный
предел 60 секунд, включая ожидание завершения StopPending после таймаута Stop.
Если Running не достигнут в этот срок, служба cleaner завершается с ошибкой
SCM и записью в журнале; новые проходы не выполняются. Поздний переход почты
в Stopped требует вмешательства оператора. Параллельный администратор не
должен запускать/перемещать службу. Отказ подключения/прав до Stop не прерывает
работу почты.

SCM Stop/Shutdown отменяет ожидание расписания либо просит окончание текущей
порции. До завершения рабочего потока и восстановления почты сообщается
StopPending с обновляемым checkpoint, затем Stopped. Idle-состояние не держит
соединение MySQL или остановленный hMailServer. Принудительное убийство,
сбой питания или отказ ОС не позволяют обещать восстановление; отдельного
журнала восстановления служебного состояния на этом этапе нет.

## Владельцы компонентов и проверка

Core владеет критериями отбора, фазами/счётчиками полной очистки, результатами
и отменой. MySQL-адаптер владеет SQL дочистки, ссылками, schema/probe и транзакциями.
Файловый адаптер — обходом, проверками, повторами и физическим удалением.
Управление hMailServer и хост SCM — отдельные Windows-операции; составной запуск,
меню, расписание, config и журнал имеют отдельных владельцев в CLI.
Rust-core не импортирует SQLx, конкретные файловые/SCM API и console I/O.
Посторонний legacy Tauri/Vue остаётся вне изменений.

Нужны проверки успешного/неподтверждённого удаления файла, временной блокировки
и постоянной ошибки; сохранения свежих/защищённых файлов; неполного набора ссылок
и недоступной папки; удаления старых SQL-остатков при сохранении строк живых
писем, повторного запуска и потери COMMIT; приоритетов env и отсутствия утечки
секретов; menu/EOF, silence/журнала; расписания и отмены; владения остановкой,
сбоев Stop/Start и восстановления после ошибки cleanup.

Проектные checks и тесты MySQL выполняются на изолированных данных.
SCM/файловые особенности проверяются на native Windows и отдельно на Server
2016/1607. Cross-build на Mac подтверждает сборку, а не runtime-совместимость.
Рабочая почта не используется как тестовый стенд.
