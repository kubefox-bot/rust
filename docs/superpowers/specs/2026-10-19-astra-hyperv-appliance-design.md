# Готовая поставка Astra для Hyper-V

Дата: 19 октября 2026 года. Статус: проект для проверки перед реализацией.

## Цель и согласованные ограничения

Заказчик получает один комплект с готовым VHDX, создаёт ВМ и проходит первоначальную настройку. Устанавливать FCOS с ISO и скачивать приложение из registry при первом запуске не требуется. Уже выбранные Rust + статический Astro/Svelte, rootless Podman, Quadlet и отдельный host updater сохраняются.

Предыдущим сообщением пользователь согласовал эту схему поставки. Этот документ фиксирует детали сборки, идентичности машин и первого запуска. Он не является результатом сборки или приёмки готового VHDX.

В текущей рабочей копии параллельно меняется очистка. Её изменения не включаются в реализацию appliance автоматически. Публикация, доступы GitHub/GHCR и действия на Hyper-V заказчика остаются отдельными эксплуатационными действиями.

## Выбранный вариант

Собираем производный VHDX **офлайн из чистого официального FCOS Hyper-V x86_64 image**. В образ добавляется проверенная поставка приложения как набор файлов; контейнерное хранилище Podman создаётся при первом запуске для реального пользователя ВМ. Предварительно запущенная ВМ с установленной Astra не используется как шаблон.

Это сохраняет штатный первый запуск FCOS и генерацию machine-id/SSH host keys. Изменяется только принадлежащий поставке каталог `/var/lib/astra-appliance`; системное дерево ОС, загрузчик и признаки первого запуска не переписываются. Конфигурация конкретной ВМ передаётся через штатный Hyper-V Ignition/KVP до её первого запуска.

Рассмотренные альтернативы: чистый VHDX с загрузкой приложения из registry требует сети/credentials при установке; экспорт настроенной ВМ требует отдельной процедуры удаления её идентичности. Выбранный вариант соответствует требованию заранее включить приложение и сохраняет независимые обновления ОС и Astra.

## Состав комплекта

Архив `astra-hyperv-<build>.zip` содержит:

- `astra-center.vhdx` — FCOS с локальным payload;
- `Install-Astra.ps1` — создание новой ВМ и передача Ignition;
- `kvpctl.exe` закреплённой версии и проверенного SHA-256;
- базовую Ignition-конфигурацию и шаблон параметров установки;
- `appliance-manifest.json`, `SHA256SUMS` и короткую инструкцию.

Payload внутри VHDX содержит `center.oci.tar`, release manifest, сгенерированные Quadlet, host-updater package, проверенный bootstrap и внутренний manifest с SHA-256 всех файлов. Windows-agent package уже входит в OCI центра; отдельная загрузка для его первого подключения не нужна.

Manifest связывает полный source SHA, общий build, upstream FCOS release и оба хеша upstream ZIP/VHDX, OCI digest/config digest, updater identity, версии схемы/протокола, хеши bootstrap/configuration и итогового VHDX. Вложенный manifest не содержит хеш внешнего VHDX, чтобы не создавать циклическую зависимость.

Корневое доверие первоначальной установки — одобренный SHA-256 внешнего архива, полученный оператором отдельно от архива через GitHub release metadata/API или согласованный доверенный канал. Внутренние checksums проверяют состав и повреждение файлов; сами по себе они не удостоверяют издателя. Этот порядок проверки включается в инструкцию до запуска PowerShell installer.

В комплект не входят пароль администратора, recovery key, registry tokens, SSH private keys, готовая SQLite БД, клиентские CA/TLS identities или созданное Podman storage. Публичный SSH-ключ оператора и адрес панели добавляются в конфигурацию отдельной установки.

## Сборка образа

1. Проверить чистый зафиксированный source SHA и готовую same-SHA поставку центра и updater. Не допускать `ALLOW_DIRTY` для распространяемого appliance.
2. Скачать upstream VHDX из закреплённого lock-файла; проверить SHA-256 compressed и uncompressed файлов. Исходный VHDX остаётся неизменным. Доверие upstream в этой итерации основано на официальном HTTPS metadata и закреплённых хешах; это не обозначается как проверка OpenPGP.
3. В отдельной staging-копии открыть VHDX через libguestfs. Проверить формат, единственный ожидаемый root filesystem и OSTree stateroot. Работать только с файлом staging, без доступа к дискам хоста. При неоднозначной разметке или нехватке места завершаться ошибкой; не выбирать раздел по случайному `/dev/sdX`.
4. Добавить payload в shared `/var` выбранного stateroot. Сохранить разметку, UUID, загрузчик и first-boot состояние upstream. Выполнить sync, закрыть guestfs и повторно открыть образ только для проверки содержимого.
5. Проверить allowlist файлов, отсутствие идентичностей/секретов и совпадение хешей. Из двух независимых копий проверить штатный первый запуск до допуска поставки к рабочему использованию.

Bun/TypeScript владеет orchestration, конфигурацией, manifest и проверкой артефактов. Bun не умеет записывать VHDX/XFS; для этого используется специализированный libguestfs, а не новый Python/Node runtime. Builder выполняется на выделенном Linux job, версии образа и инструментов записываются в receipt. Одинаковые входы обязательны; битовая идентичность всех выходов пока не заявляется из-за metadata файловой системы.

## Установка у заказчика

`Install-Astra.ps1` работает из административного Windows PowerShell 5.1+ с установленным модулем Hyper-V. Bun, Node и Linux-инструменты на хосте заказчика не требуются.

Оператор задаёт имя ВМ, существующий virtual switch, каталог новой ВМ, SSH public key и HTTPS origin. Сеть v1 использует DHCP/DHCP reservation; DNS и постоянный адрес согласуются до инициализации. Статическую конфигурацию сети можно передать заранее подготовленным проверенным Ignition, без автоматического выбора адреса скриптом.

Скрипт сначала проверяет входы, manifest/checksums, доступность Hyper-V/KVP и конфликтующие имена/пути. Затем создаёт отдельную копию диска и новую Generation 2 ВМ, выбирает Secure Boot template `Microsoft UEFI Certificate Authority`, передаёт Ignition через `kvpctl` и запускает ВМ. Существующие ВМ/диски/switch не изменяются и не удаляются. При сбое сохраняются только созданные этим запуском ресурсы с понятным описанием состояния; повторный запуск не выдаёт частично созданную ВМ за готовую.

Bootstrap metadata содержит только public configuration. Хеш внутреннего payload ожидается из проверенного комплекта, а не берётся на доверии с изменяемого диска.

## Первый запуск и инициализация

1. Ignition создаёт служебного пользователя UID/GID 2000, subid ranges, linger и units на основе существующей IaC. Первый запуск не требует GitHub/GHCR и не получает секреты из KVP.
2. Bootstrap восстанавливает SELinux labels принадлежащего ему payload, проверяет все хеши и загружает OCI от `hmail-center`, сохраняя keep-id UID/GID 10001. Создаёт named volume и подготавливает Quadlet и host tooling. Ошибка оставляет подготовку незавершённой; непроверенный payload не запускается.
3. До успешного `center init` служба центра не стартует. Оператор подключается по SSH и запускает поставляемую команду инициализации: она вызывает существующий интерактивный `center init` с выбранным origin. Пароль/recovery вводятся и выдаются в интерактивном терминале, не через аргументы, файлы параметров или журналы bootstrap. Новый web-мастер настройки в этот объём не входит.
4. Только после успешного `center init` сохраняется durable initialized marker, разрешающий запуск центра. Готовность установки фиксируется отдельно после HTTPS health с ожидаемым build. Потеря ответа или неуспешный health после выполненного init не запускают повторную инициализацию. Если init частично выполнен, повтор не перезаписывает vault/CA/SQLite и требует диагностики существующего состояния.
5. Повторная загрузка использует существующий volume, ключи и настройки. Bootstrap имеет отдельные durable этапы и не использует один общий marker для незавершённых операций. Сбой после создания volume не даёт права удалить его при retry.

Один VHDX содержит ОС и постоянные данные ВМ. Это не означает замену VHDX при обновлении приложения: updater меняет только контейнер и сохраняет named volume. Резервные копии нужны вне ВМ.

## Updater и обновления ОС

Существующий `deploy/updater/install.sh` сейчас требует работающий центр и сразу включает timer. Для appliance нужны раздельные **подготовка** и **активация**. Существующий обычный режим установки сохраняется; новый режим подготовки устанавливает проверенные файлы/units и генерирует node UUID, но не требует запущенного центра и не включает discovery timer.

После инициализации и health активируется FleetLock coordinator и связывается его node UUID с Zincati. Пока центр/coordinator не готовы, reboot не разрешается. Discovery timer включается отдельным эксплуатационным шагом после настройки read-only credentials и приёмки доставки. Исходная policy остаётся 60 секунд discovery / 15 минут graceful wait.

Координатор и updater используют прежние operation lock/admission/backup/recovery контракты. После `Exposing` автоматическое восстановление старой БД не допускается. Appliance не вводит второй механизм обновления приложения и не меняет trust identity опубликованных релизов.

## Обязательное исправление совместимости схем

Текущий центр использует схему БД 2, а descriptor и updater ожидают 1; несовместимость воспроизведена отдельной проверкой. До упаковки:

- текущая schema 2 объявляется в release metadata и берётся из общего контракта центра/updater/tooling;
- новый descriptor честно указывает schema 2; неизвестные/неподдерживаемые target schema отклоняются до maintenance;
- проверка backup принимает явно поддерживаемые старую 1 и текущую 2, сохраняет проверку build/vault/hash и не превращается в разрешение любой версии;
- интеграционный тест создаёт настоящий backup центра и передаёт его updater, включая schema mismatch и неподдерживаемую версию. Тесты с независимыми фикстурами schema 1 больше не являются единственным доказательством.

Внутренний формат descriptor и версия схемы SQLite — разные поля; `format_version` не повышается только из-за перехода SQLite 1 → 2.

## CI и публикация

Порядок: portable/MySQL/Windows checks → same-SHA OCI + agent + updater → lifecycle → сборка и офлайн-проверка VHDX → упаковка и CI receipt. Receipt связывает appliance manifest и итоговые bytes с исходным SHA; existing publication gate проверяет эти хеши перед публикацией. Дополнительные assets добавляются явным allowlist; произвольные файлы staging не публикуются.

Апплаенс создаётся из уже проверенных бинарных артефактов, без повторной сборки центра из другого checkout. Linux CI подтверждает упаковку, содержимое и boot-проверку там, где доступна виртуализация; обычный Windows runner проверяет PowerShell-контракты, но не выдаётся за Hyper-V хост.

Source identity учитывает `iac/fcos` наряду с существующими `tools`, `deploy`, Rust и web inputs. Изменение конфигурации первого запуска во время сборки должно аннулировать candidate так же, как изменение исходников центра.

Существующий `ASTRA_DELIVERY_ENABLED` остаётся выключенным до отдельной приёмки и разрешения на публикацию. Наличие этой спецификации или workflow не включает рабочую доставку.

## Владельцы изменений

- `tools/appliance/` — сборка VHDX, проверка входов/выходов и appliance manifest;
- `deploy/appliance/` — bootstrap, интерактивная инициализация, units и PowerShell installer;
- `iac/fcos/` — переиспользуемая базовая конфигурация и appliance overlay;
- `tools/release/`, `crates/protocol/`, `crates/center/`, `crates/updater/` — общий контракт совместимости и существующие границы поставки;
- `.github/workflows/center-ci.yml`, `center-delivery.yml` — сборка, receipts и явные assets;
- `docs/` — операторский runbook и отдельная приёмка.

Новые обязанности разделяются по этим владельцам; сборка VHDX не добавляется в общий файл конфигурации релиза как набор несвязанных helpers.

## Приёмка

До распространения нужны реальные записи PASS/FAIL/NOT RUN для следующих сценариев:

- два независимых экземпляра одного VHDX имеют разные machine-id, SSH fingerprints, node UUID и CA/vault после раздельного init;
- приложение загружается из локального payload при закрытом доступе к registry; подготовка не требует outbound GitHub;
- SELinux enforcing, rootless cgroup v2, peer UID socket, linger и старт после logout/reboot;
- bootstrap/инициализация после прерывания не теряют volume и не повторяют успешную инициализацию;
- повреждённый VHDX/payload, неверная identity или schema, конфликтующий путь/ВМ и нехватка места дают явный отказ;
- native Hyper-V Generation 2 с указанным Secure Boot template: первый запуск, сеть, SSH, init и HTTPS;
- A → B, плохой C, active job, unknown receipt, backup/restore и coordinated FCOS reboot;
- Windows Server 2016: установка агента и предпросмотр на тестовом наборе отдельно от упаковки ВМ.

Наличие теста на mock host не закрывает native Hyper-V/FCOS/Windows пункт. До этой приёмки выход считается кандидатом, а не готовым production appliance.
