# hMail Cleaner: единый HTTP-центр управления

Дата: 2026-10-17.

Статус: рабочая спецификация договорённостей. Согласованные решения отмечены
как выбранные; продуктовые предложения требуют завершения обсуждения.
Оставшиеся технические подробности пользователь поручил исполнителю:
библиотеки, форматы и параметры уточняются при подготовке реализации и проверке
совместимости без отдельного согласования каждой детали. Изменения объёма,
поведения, полномочий и договорённостей о сохранности данных обсуждаются явно.
Реализация этого расширения ещё
не начата. Этот документ не является планом реализации или подтверждением
развёртывания на рабочих серверах.

Окончательный выбор стека подтверждён 2026-10-17 после сравнения с Bun:
Rust + Axum + Tokio для центра, Astro static + Svelte для интерфейса.
Bun используется при разработке и сборке frontend; в рабочем контейнере
приложение запускает один Rust-процесс. Astro SSR и серверная часть на Bun
не входят в MVP. Причина выбора — приоритет контроля ресурсов; фактическое
преимущество по RSS/CPU ещё должно быть измерено.

Порядок реализации и проверок:
[план MVP](../plans/2026-10-17-hmail-control-center-mvp.md).

## 1. Цель и исходная среда

Дать суперадмину один веб-интерфейс для настройки и ручной очистки нескольких
hMailServer. В первой установке есть две Windows-ВМ на одном Hyper-V-хосте.
Между ВМ существует локальная сеть с маршрутизацией через маршрутизатор.
Администратор открывает панель со своего компьютера в этой сети.
Для центра выбрана отдельная Linux-ВМ на существующем Hyper-V-хосте,
рядом с двумя почтовыми Windows-ВМ. OCI-образ центра запускается через
Podman + Quadlet под управлением systemd. Отдельный физический сервер для MVP
не планируется. Windows Server 2016 остаётся целевой средой почтовых агентов;
дистрибутив, ресурсы и сеть Linux-ВМ ещё проверяются.
Готового внутреннего CA и доверенных сертификатов для приложения нет.
Для первоначальной установки агентов выбран SSH; его доступность на ВМ
и совместимость пакета OpenSSH с целевой Windows ещё не проверены.

Основные приоритеты: небольшой расход памяти и CPU, отсутствие обязательной
контейнерной среды на почтовых ВМ, централизованные настройки и возможность
перенести центр управления на другую ОС.

Существующая утилита состоит из Rust-ядра, адаптеров и CLI. Действующий
контракт очистки описан в [инструкции CLI](../../cleanup-cli.md) и реализован
в [ядре](../../../crates/core/src/lib.rs). Ранние дизайн-документы сохраняют
историю решений, но не заменяют актуальный контракт CLI.

## 2. Согласованный объём первой версии

- HTTP-интерфейс с одним адресом входа и выбором почтового сервера.
- Основная поставка центра — версионированный Linux OCI-образ. Для MVP
  выбран запуск в Linux-ВМ на существующем Hyper-V-хосте; отдельный физический
  Linux-хост может появиться позже. Выбран rootless Podman + Quadlet;
  systemd управляет запуском и перезапуском контейнера. Версии дистрибутива,
  Podman/systemd и базового образа закрепляются после проверки совместимости.
  На почтовых ВМ агенты остаются отдельными нативными Rust-службами.
- CI/CD откладывается на отдельный этап после MVP. Первая версия включает
  локальные проверки и сборку OCI-образа, ручную установку через Quadlet
  и ручное обновление с backup. Автоматизация сборки, публикации релизов/образов
  и доставки через CI/CD в текущий план не входит.
- Astro static + Svelte-острова: управление очисткой и прогресс в одном острове,
  история и настройки загружаются по необходимости. Rust-центр раздаёт
  собранную статику и обслуживает API с одного origin.
- Rust-backend на Axum и существующем Tokio владеет авторизацией, данными
  и выполнением операций;
  frontend получает готовую HTML-оболочку и добавляет нужную интерактивность.
- Для новой версии выбран актуальный стабильный Rust: на 2026-10-17 это 1.99.1.
  Эта версия становится целевой версией toolchain и объявленным минимумом Rust.
  В файлах сборки закрепляется точный номер; последующие обновления выполняются
  явно после проверки совместимости.
- Общие рабочие данные и события между островами проходят через Rust API
  и серверную шину событий. Острова имеют отдельные обязанности и локальное
  состояние интерфейса.
- Ручной предпросмотр, запуск очистки, просмотр прогресса, результатов и ошибок,
  запрос корректной отмены.
- Централизованное редактирование подключений MySQL, путей и параметров очистки.
- Сначала устанавливается центр с готовой веб-панелью. Затем суперадмин
  добавляет почтовые серверы через неё: центр устанавливает агент по SSH,
  настраивает доверие mTLS и после этого позволяет задать MySQL и пути.
- Рабочий HTTP-канал между центром и агентами использует mTLS.
- Для SSH выбраны russh + russh-sftp; для HTTPS/mTLS — rustls с ring,
  tokio-rustls, axum-server и reqwest; для ключей, CSR и сертификатов — rcgen.
  Распределение ответственности и базовые версии закреплены в разделе 8.4.
- Очистка запускается только вручную, из панели или CLI. Планировщик
  прежнего режима службы исключается из новой версии вместе с настройками
  автоматического запуска очистки. Автозапуск процессов не запускает удаление.
- Локальная нативная SQLite через SQLx у центра управления; отдельный сервер
  БД панели не нужен.
- Собственная учётная запись суперадмина, независимая от Windows-профилей.
- Первый суперадмин создаётся локальной командой центра с интерактивным
  вводом логина и пароля. Первоначальный веб-мастер регистрации не требуется.
- Одна активная сессия суперадмина в первой версии; несколько вкладок
  одного браузера используют эту сессию. Успешный новый вход заменяет
  прежнюю активную сессию. Сессия хранится в памяти центра; cookie содержит
  случайный идентификатор, а ключ данных имеет отдельного владельца в памяти.
- Для cookie выбран tower-cookies, для сессии — одна типизированная запись
  в состоянии Axum, для CSRF — tower-http CsrfLayer с обязательным заголовком
  браузерного API. Атрибуты cookie и правила проверки закреплены в разделе 5.7.
- Выход по бездействию настраивается: 15 минут, 30 минут, 1 час или 1 день;
  начальное значение — 15 минут. Отдельной кнопки и состояния блокировки нет.
- Суперадмин может изменять настройки и запускать очистку/удаление старой почты.
- Технический профиль шифруется целиком: подключение MySQL, пути Data/INI,
  имя службы и секреты доступа к агенту. Пароль суперадмина участвует
  в разблокировке ключа данных. Имена серверов, статусы и счётчики истории
  остаются обычными данными.
- Для получения ключа из пароля выбран Argon2id; для аутентифицированного
  шифрования настроек и защиты копий ключа данных — XChaCha20-Poly1305.
- После перезапуска центр ждёт входа суперадмина для разблокировки настроек.
- Ключ восстановления, сохраняемый владельцем отдельно от базы приложения.
- Минимизация зависимости центра и общего протокола от Windows.

В первую версию не входят расписание и автоматический запуск очистки,
создание других пользователей, дополнительные роли, полная ротация ключа
данных (DEK) и массовая очистка всех серверов одной командой.
Расписание и управление пользователями могут стать
последующими расширениями. Наличие Windows-службы означает автозапуск процесса,
а не автоматический запуск удаления почты.

## 3. Центр и агенты

### 3.1. Центр управления

Центр — Rust-приложение. Его HTTP-сервер на Axum обслуживает статический frontend, API браузера,
вход суперадмина, разблокировку настроек, профили серверов, отправку команд
агентам и представление состояния запусков. Браузер обращается к одному
адресу центра; реквизиты взаимодействия с агентами остаются на backend.
Отдельный Astro-сервер между браузером и Rust в выбранной схеме отсутствует.

Центр должен иметь возможность работать на Windows, Linux и macOS. Список
проверяемых ОС и архитектур сборок фиксируется при выборе стека и планировании;
переносимость дизайна сама по себе не подтверждает работу готового приложения.

### 3.2. Агент на каждой почтовой ВМ

Агент выполняет операции только на своей машине: проверяет локальные пути
и INI, подключается к MySQL, управляет службой hMailServer, запускает существующее
ядро и публикует состояние. По сети не передаются тела писем или весь каталог
почты. Текущий backend hMailServer требует Windows для управления службой
и соответствующих платформенных проверок.

Общая логика заданий и сетевой контракт не должны зависеть от Windows API.
Существующий [контракт MailControl](../../../crates/core/src/maintenance/mail_service.rs)
и его Windows-адаптер переиспользуются. Windows-пути хранятся в центре как
данные целевого сервера; центр на Linux не интерпретирует их как собственные
локальные пути. Окончательная проверка и открытие путей принадлежат агенту.

### 3.3. Выбранное размещение

Выбран порядок: сначала установка центра с собранными Astro + Svelte,
затем добавление агентов из веб-панели. Агент нужен на каждой ВМ, чью почту
планируется очищать, включая ВМ центра, если на ней также работает hMailServer.
Раздельные центр и агенты поддерживаются общим сетевым контрактом.
В выбранной контейнерной схеме центр и агенты — отдельные процессы.
Linux-ВМ запускает контейнер центра, а агенты работают Windows-службами
на почтовых ВМ и имеют локальный доступ к своим установкам. Совмещённый процесс
для MVP не требуется. Windows остаётся требованием текущего hMailServer-адаптера
агента.

Одна кодовая база выпускает сборки центра и агентов. Границы монорепозитория,
CLI-команды и состав артефактов заданы в общем плане MVP и разделе 8.5.
Существующие команды и режим службы CLI
сохраняют контракты, кроме явно выбранного удаления очистки по расписанию.
Команды запуска служб и миграция прежней службы должны быть определены
до реализации; старая настройка расписания не должна активировать очистку.

Podman работает внутри Linux-ВМ центра; Quadlet описывает контейнер как
systemd-службу. Почтовые Windows-ВМ
сохраняют нативные службы агентов. Цель MVP — упростить доставку приложения и замену его сборки,
без обязательного отдельного хоста или дополнительного оркестратора контейнеров.
Отдельный reverse proxy не является обязательной частью архитектуры.

В образ входят Rust-центр и заранее собранные Astro static + Svelte.
Рабочую оркестрацию, API, установку агентов и взаимодействие по mTLS выполняет
Rust; отдельный постоянно работающий Astro/Node/Bun-сервер не добавляется.
SQLite, идентичность центра и необходимый TLS bootstrap хранятся в постоянном
томе/каталоге данных, а не только в заменяемом слое контейнера. Точный состав
резервной копии и процедура обновления с миграциями закрепляются в плане.

Для выбранной схемы используется rootless Podman от отдельного служебного
пользователя Linux. Quadlet-файлы .container и .volume задают контейнер центра
и постоянный том. Пользовательский systemd manager с linger запускает службу
после загрузки ВМ без интерактивного входа. Quadlet требует cgroup v2;
версии Podman/systemd, user namespaces и права каталога данных проверяются
на выбранном дистрибутиве. Данные SQLite располагаются в постоянном томе
на локальной файловой системе Linux-ВМ. Init, run и backup используют один
том и согласованное отображение UID/GID.

Единица обновления — весь OCI-образ: Rust-центр, собранный интерфейс и пакеты
агентов. Применяется конкретный image digest. Операция обновления выполняется
на Linux-хосте: предварительно скачать и проверить выбранный образ, остановить
службу центра, сделать согласованный backup SQLite/bootstrap/config,
изменить Image в Quadlet и запустить службу с миграциями. Health и проверка
версии доступны до входа суперадмина. Для отката используются прежний digest
и соответствующая резервная копия данных; смена образа сама по себе не
отменяет миграции БД. API/socket управления Podman в контейнер центра не
передаётся; отдельный контейнер с собственным updater не требуется.
В исходной поставке AutoUpdate и podman-auto-update.timer не включаются:
автоматическая установка должна учитывать резервное копирование и миграции,
а следование изменяемому тегу не заменяет выбор проверенного digest.

Из сети разрешён исходящий интернет, входящих подключений из интернета нет.
Получение образов и метаданных обновлений использует исходящий HTTPS;
управление агентами и доступ к панели сохраняются в локальной сети.

Проверка контейнерной доставки включает HTTP/TLS, работу SQLite на постоянном
томе, сохранность после пересоздания контейнера и доступ по LAN к двум агентам.
Расход ресурсов центра, процессов Podman и самой Linux-ВМ измеряется раздельно.
Проверка проводится на изолированных данных и не запускает очистку рабочей
почты. Выбранное размещение не подтверждает фактическую готовность ВМ или
развёртывание контейнера.

Последующий перенос на отдельный совместимый Linux-хост с Podman сохраняет
образ центра, данные и протокол. Адреса, сертификаты, сетевой доступ и процедура
переноса проверяются отдельно; изменение размещения не переустанавливает
почтовые агенты само по себе.

Замена контейнера центра не перезапускает принятые задания на агентах.
После рестарта центра нужен вход суперадмина для открытия настроек, затем
центр согласует состояние с агентами по прежним идентификаторам заданий.
Пожелание централизованно обновлять агентов учитывается при планировании;
автоматическое обновление агентов без действия администратора пока не выбрано.

### 3.4. Установка агента из веб-панели

Выбран установочный канал SSH. В панели суперадмин задаёт целевой адрес
и реквизиты доступа к ОС, достаточные для установки службы. Прикладной
суперадмин сам по себе не получает административные права на Windows.
SSH-сервер должен быть доступен заранее; если его нет, требуется первоначальная
подготовка ВМ через существующий административный доступ или локальный запуск.
Конкретный способ такой подготовки ещё определяется.

Целевая среда текущего CLI — Windows Server 2016/1607. Встроенный компонент
OpenSSH из инструкции для Windows Server 2019 и новее не предполагается
доступным на этой ВМ. Для отдельного пакета Win32-OpenSSH требуется проверить
поддержку конкретной версии Windows и работу установки на целевой машине.

Сценарий мастера:

1. Проверить SSH-доступ, подлинность целевого хоста, ОС, архитектуру и права.
2. Передать агент выбранной совместимой версии и проверить пакет перед запуском.
3. Автоматически настроить доверие mTLS: агент создаёт закрытый ключ на своей
   ВМ, а обмен запросом на сертификат, сертификатами и публичными материалами
   доверия выполняется через проверенный SSH-канал.
4. Установить и запустить службу агента в режиме ожидания команд. К этому
   моменту рабочий API настроен на mTLS; ручной перенос сертификатов
   для каждого добавляемого агента не является штатным шагом пользователя.
5. Проверить связь центра с нужным агентом по mTLS и совместимость протокола.
6. Открыть настройку MySQL, Data/INI и имени службы. Профиль становится готовым
   к ручной работе после проверки конфигурации агентом.

Установка и проверка готовности не выполняют удаление почты, полный обход
Data или остановку hMailServer. Агент может быть установлен до заполнения
почтового профиля и показывать состояние «Требуется настройка».

SSH используется для установки; обычные команды и прогресс идут по mTLS.
Установочные реквизиты ОС предлагается держать только на время операции,
без сохранения по умолчанию в профиле или журналах. Метод входа по SSH,
первоначальное доверие к host key, очистка временных секретов и поведение
при прерывании установки ещё требуют технического контракта.

Для Windows используется существующий платформенный механизм размещения
процесса в SCM там, где его контракт подходит. Новый режим агента ожидает
ручные команды. Планировщик существующего CLI и его параметр HMAIL_RUN_AT
подлежат удалению из новой версии, а не переиспользованию для агента.

### 3.5. Доверие центра и агентов

Для рабочего HTTPS API выбран mTLS: центр проверяет сертификат и личность
конкретного агента, агент проверяет сертификат и допуск конкретного центра.
Сертификаты привязываются к стабильным идентификаторам узлов. Одного наличия
сертификата от доверенного CA недостаточно для допуска произвольного узла
к командам. Рабочие команды недоступны без успешной взаимной аутентификации.

Для исходной среды предлагается частный CA приложения с выпуском сертификатов
из центра после входа суперадмина. Это операция приложения, не обязательный
отдельный постоянно работающий сервис. Предлагается хранить закрытый ключ
подписи CA и ключ клиентского сертификата центра в зашифрованных блоках SQLite.
Серверные ключи HTTPS центра и агентов должны быть доступны их процессам
при старте и защищены правами доступа ОС; их хранение относится к TLS bootstrap.

Браузер использует HTTPS центра и прикладной вход суперадмина. Настройка
доверия браузера к CA выполняется при первоначальной установке центра.
mTLS агентов не заменяет авторизацию действий суперадмина в API панели.

Исходные правила выпуска сертификатов, идентификаторы, сроки действия,
обновление и отзыв закреплены общим планом MVP; перенос доверия при смене
центра проверяется вместе с восстановлением данных.
Набор SSH/TLS-библиотек выбран и описан в разделе 8.4 вместе с границами
проверки Windows; выбор библиотек не подтверждает запуск на почтовых ВМ.

## 4. Централизованная SQLite + SQLx

SQLite находится в каталоге данных центра, на его локальном диске.
Почтовые ВМ не открывают этот файл по сети. На агентах не нужна вторая копия
центральной базы профилей; локальное состояние выполняемого задания и журнал
агента имеют собственный жизненный цикл.

Для квитанций и состояния заданий агент использует свою локальную SQLite.
Она содержит job_id, отпечатки команд и безопасную отчётность, без открытых
профилей MySQL и паролей. Это отдельное хранилище исполнения, не реплика
центральной базы настроек. Транзакционное принятие и отмена неизвестного
job_id описаны в общем плане MVP.

Выбраны обычный нативный движок SQLite и библиотека доступа SQLx.
SQLite-драйвер добавляется к уже используемой в проекте библиотеке;
существующий MySQL-адаптер агентов сохраняется. Turso, libSQL и WASM-движок
не являются частью выбранного стека первой версии. Включение драйвера,
совместимость версий и целевых сборок ещё требуют реализации и проверки;
выбор SQLx не разрешает попутное обновление всей текущей линейки зависимостей.

| Группа | Содержимое |
| --- | --- |
| Серверы | Стабильный идентификатор, отображаемое имя, адрес агента и сведения о доверии к нему |
| Настройки hMailServer | MySQL host/port/database/user/password, Data, INI, имя службы |
| Параметры очистки | Граница возраста или период, fast/full, размер пакета и число работников |
| Учётная запись | Суперадмин, проверочные данные входа и сведения об изменении пароля |
| Защита настроек | Соли и параметры получения ключей, защищённые копии ключа данных, версия формата |
| Запуски | Сервер, версия профиля, параметры запуска, время, состояние, итоговые счётчики и ошибки |

Тела писем, копии почтового дерева и полный постоянный каталог файлов
в SQLite центра не сохраняются. История запусков не является журналом,
позволяющим отменить уже выполненное удаление.

Изменение профиля применяется к следующим операциям. Выполняемое задание
использует принятый им неизменяемый снимок настроек; его чувствительная часть
не попадает в открытые записи истории, логи или ответы браузеру.

Например, MySQL `127.0.0.1` в профиле второго сервера означает loopback
второй ВМ. Центр не получает из этого указания доступ к MySQL своей машины.
Конфигурация передаётся выбранному агенту, а подключение открывает агент.

В установочном конфиге агента остаются его идентификатор, адрес прослушивания
и материал доверия к центру. Учётная запись ОС процесса всё равно должна иметь
локальные права на нужные файлы, БД и управление почтовой службой; права
суперадмина приложения эти разрешения не заменяют.

## 5. Вход, шифрование и восстановление

### 5.1. Собственная учётная запись

Суперадмин входит по логину и паролю приложения. В SQLite не хранится сам
пароль. Проверочные данные входа отделены от ключа шифрования: значение,
сохраняемое для проверки пароля, не должно позволять расшифровать настройки.
API проверяет полномочия на backend для настройки профилей, запуска и отмены.

В первой версии выбрана одна активная сессия суперадмина. Несколько вкладок
одного браузера используют общую сессию; отдельный браузер, профиль браузера
или устройство не получают независимую параллельную сессию. Успешный новый
вход отзывает прежнюю сессию и создаёт новую. Для доступа к панели
есть два состояния: пользователь вошёл или не вошёл. Отдельного состояния
«вошёл, но хранилище заблокировано» и действия «Заблокировать» нет.

Выбрана серверная сессия в памяти центра. Защищённая cookie содержит только
её случайный идентификатор; запись сессии не содержит ключ шифрования.
Ключ имеет отдельного владельца в памяти процесса с согласованным жизненным
циклом доступа. Сессия не восстанавливается из SQLite после рестарта.
Выбраны tower-cookies, одна типизированная запись сессии в состоянии Axum
и tower-http CsrfLayer; параметры cookie и защита запросов описаны в разделе 5.7.

Первоначальное создание суперадмина локальной командой центра выбрано
в обсуждении; порядок описан в разделе 5.6. Открытая регистрация в LAN
не требуется. Ограничение параллельных Argon2-расчётов и необходимость
лимитировать попытки входа выбраны; числовые параметры частоты попыток
и ограничений запросов ещё уточняются.

### 5.2. Пароль и ключи

Пароль служит секретным входом функции получения ключа. Соль — отдельное
случайное несекретное значение, сохраняемое с параметрами этой функции.
Пароль не используется в качестве соли.

1. При инициализации генерируется случайный ключ данных.
2. Он используется готовой реализацией аутентифицированного шифрования
   для чувствительных настроек MySQL, доступа к агентам и других секретов.
3. Из пароля и отдельной соли получается ключ защиты, которым шифруется
   ключ данных. Проверочные данные входа не подменяют этот ключ.
4. SQLite хранит зашифрованные значения и защищённые копии ключа данных,
   но не содержит ключ расшифровки в открытом виде.
5. При смене пароля ключ данных защищается заново новым производным ключом;
   повторное шифрование всех настроек только из-за смены пароля не требуется.

Выбраны Argon2id для получения ключа из пароля и XChaCha20-Poly1305
для аутентифицированного шифрования. XChaCha20-Poly1305 используется
для конфигурационных блоков и защищённых копий ключа данных, открываемых
паролем или ключом восстановления. Ключи этих назначений разделяются.
Используются готовые реализации криптографических примитивов; исходные
библиотеки, версии и Cargo features описаны в разделе 5.8 и проверяются
при реализации без отдельного согласования каждой технической детали.

XChaCha20-Poly1305 использует 256-битный ключ и 192-битный nonce (24 байта).
При каждом шифровании генерируется новый случайный nonce из генератора ОС;
повтор nonce с тем же ключом недопустим. Длинный nonce уменьшает вероятность
случайного совпадения, но не даёт устойчивости к его намеренному повтору.
Параметры Argon2id, разделение назначения ключей и солей, формат AAD,
версионирование блоков и порядок смены ключей должны быть явно закреплены
в проверяемом техническом дизайне до реализации. Замеров памяти и скорости
на целевых ВМ этот выбор не подтверждает.

Механизм не зависит от Windows DPAPI или профиля Windows-пользователя.
Шифруется чувствительное содержимое записей; обычная SQLite сама по себе
не обеспечивает шифрование всего файла.

Выбор SQLite + SQLx не меняет этот контракт: Rust шифрует чувствительные
конфигурационные блоки до передачи SQLx для записи. В SQLite, её WAL и резервные
копии эти значения должны попадать уже зашифрованными.

Выбрано шифрование всего технического профиля. В зашифрованный блок входят:

- Подключение MySQL целиком: host, port, database, user и password.
- Пути Data и INI, имя службы hMailServer.
- Секреты доступа центра к агенту: закрытые ключи клиентской аутентификации
  выбранного mTLS. Общие секреты центра могут храниться отдельными
  зашифрованными блоками без дублирования в каждом профиле.

Идентификатор и отображаемое имя сервера, версия профиля, состояния запусков,
даты и итоговые счётчики истории хранятся открыто. Их защита обеспечивается
правами доступа к приложению и файлам БД. Формат зашифрованного блока
и размещение полей в схеме БД ещё требуют технического дизайна.

После входа API настроек может возвращать суперадмину технические поля,
нужные для редактирования, например MySQL host и пути. Пароли, токены
и закрытые ключи в API чтения не возвращаются. История, события и журналы
не должны дублировать значения зашифрованных конфигурационных полей;
ошибки очищаются от таких значений перед сохранением и публикацией.

Установочный материал HTTPS самого центра должен быть доступен до входа
суперадмина. Его хранение определяется отдельно в дизайне TLS; ключ данных
профилей не является обязательным условием открытия HTTPS-экрана входа.

SQLCipher не требуется для шифрования конфигов на уровне приложения.
Он шифрует страницы базы на диске и может рассматриваться отдельно, если
появится требование скрывать содержимое базы целиком. SQLCipher сам по себе
не задаёт правила входа, разблокировки, смены пароля и recovery key;
этот жизненный цикл всё равно принадлежит приложению.

Центр после разблокировки получает открытые реквизиты для работы с агентами.
Защита сохранённой базы не заявляется как полный аналог zero-knowledge
архитектуры Bitwarden или как защита от компрометации работающего процесса.
Сходство с Bitwarden относится к принципу случайного ключа данных и его
защиты производным ключом пароля; алгоритмы и архитектура не копируются целиком.

### 5.3. Состояние после перезапуска

Центр стартует без активной сессии и открытого ключа данных. До успешного
входа суперадмина сохранённые секреты недоступны, новые задания с ними
не запускаются. Вход одновременно открывает доступ к панели и расшифровывает
ключ данных. Этот ключ доступен в памяти процесса, пока действует сессия;
пароль для постоянной работы сохранять не требуется. Возможность автономной
работы сразу после рестарта не входит в выбранную схему и должна отдельно
пересматриваться при добавлении расписания.

Перезапуск центра не означает перезапуск заданий на агентах. После входа
состояние незавершённых операций согласуется с агентами.

### 5.4. Ключ восстановления

При первоначальной настройке создаётся независимый случайный ключ
восстановления, которым защищается дополнительная копия того же ключа данных.
Пользователь получает ключ и сохраняет его отдельно от SQLite и её резервных
копий. Сам ключ восстановления не записывается в SQLite или штатные журналы.

Он должен позволять установить новый пароль без потери зашифрованных
настроек. Предлагаемый сценарий восстановления — локальная команда центра;
после успешного восстановления сессии отзываются и выдаётся новый ключ
восстановления, заменяющий прежний. Для переноса центра нужны резервная копия
БД и один из способов разблокировки: пароль или соответствующий ключ
восстановления. Если утрачены и пароль, и ключ восстановления, зашифрованные
секреты восстановить нельзя.

### 5.5. Сессия и выход по бездействию

В настройках центра выбирается один таймаут бездействия:

| Значение в интерфейсе | Длительность |
| --- | --- |
| 15 минут | 15 минут; начальное значение |
| 30 минут | 30 минут |
| 1 час | 60 минут |
| 1 день | 24 часа |

Настройка сохраняется между перезапусками. Её изменение применяется
к текущей сессии после сохранения; срок отсчитывается от последней
пользовательской активности. Сохранение настройки также является активностью.
Фоновые запросы, события SSE и обновления прогресса сами по себе
не продлевают срок. Определение пользовательской активности и её передача
серверу должны быть закреплены в техническом контракте.

При истечении таймаута выполняется полный выход. Тот же переход происходит
по явному действию «Выйти»: центр отзывает сессию, запрещает новые защищённые
операции, закрывает относящиеся к ней SSE-подключения и очищает принадлежащие
приложению буферы ключа данных после завершения коротких обращений к ключу.
Все вкладки общей сессии переходят к экрану входа. Повторный доступ требует
логина и пароля; отдельного шага разблокировки после входа нет.

Проверка срока и очистка ключа выполняются сервером, в том числе когда
браузер закрыт и новые запросы не поступают. Клиентский таймер не заменяет
проверку на backend. Закрытие вкладки само по себе не считается надёжным
сигналом немедленного выхода.

При новом входе замена сессии выполняется только после успешной проверки
пароля и готовности ключа данных. Неудачная попытка входа не отзывает
действующую сессию. Переход согласован: две активные сессии одновременно
не допускаются. SSE-подключения прежней сессии закрываются, её вкладки
теряют доступ к защищённому API и при получении уведомления или следующей
проверке доступа показывают экран входа.

Ключ данных доступен новой сессии. Запоздалый выход, истечение срока или
завершение запроса уже отозванной сессии не могут отозвать новую сессию
или очистить принадлежащий ей ключ. Детали синхронизации проверяются
при реализации обработки параллельных запросов.

Выход не является отменой уже отправленной команды. Принятая агентом очистка
продолжается независимо от сессии, используя необходимые ей настройки
до безопасного завершения. Если результат отправки неизвестен, после
следующего входа центр выясняет состояние по прежнему идентификатору задания,
а не запускает новую очистку.

Отдельный абсолютный срок сессии не утверждён и не ограничивает выбранный
таймаут бездействия автоматически. В частности, дополнительное ограничение
в 8 часов не является частью текущей договорённости.

### 5.6. Первоначальное создание суперадмина

Выбран локальный интерактивный запуск на машине центра. Команда использует
тот же явно выбранный каталог данных и SQLite, что рабочий процесс центра.
Для этого выбрана команда `hmail-cleaner center init`.
В текущем CLI такой команды ещё нет.

Порядок первоначальной настройки:

1. Установщик размещает центр; до рабочего запуска выполняется init.
   Команда проверяет доступ к каталогу и базе. Ошибка чтения или повреждение
   существующей БД не считаются отсутствием учётной записи.
2. Администратор вводит логин, пароль и подтверждение пароля. Пароль читается
   скрыто из терминала, не передаётся аргументом командной строки и не попадает
   в журнал. Учётная запись приложения не привязывается к профилю ОС.
3. Создаются проверочные данные пароля, случайный ключ данных и независимый
   ключ восстановления. Ключ данных защищается отдельно паролем и recovery key
   по контракту разделов 5.2 и 5.4. В SQLite сохраняются только предусмотренные
   этим контрактом проверочные данные, параметры и зашифрованные блоки.
4. Ключ восстановления показывается владельцу для отдельного сохранения.
   Его сохранение подтверждается повторным вводом до commit. До подтверждения
   учётная запись и обёртки не считаются созданными.
5. Создание учётной записи и связанных блоков защиты фиксируется одной
   транзакцией. Ограничение единственного суперадмина и сериализация init
   исключают создание двух учётных записей параллельными командами.
   После успешной настройки панель предлагает обычный вход. Init не создаёт
   постоянную сессию и не оставляет ключ данных открытым для рабочего процесса.

Повторный init при существующем суперадмине завершается без изменения его
учётной записи или ключей. Смена пароля и восстановление являются отдельными
операциями. Потеря финального ответа после успешного commit не разрешает
повторно инициализировать БД: заменить recovery key можно после входа
с известным паролем. Правила подтверждения, транзакций и восстановления
уточнены в разделе 5.8 и задачах B2/B7 плана.

### 5.7. Выбранные библиотеки и правила авторизации

Библиотеки, схема одной сессии, параметры cookie и правила CSRF согласованы
в обсуждении. Базовые версии проверены по документации и опубликованным
метаданным crates.io на 2026-10-17; новые зависимости ещё не установлены.
Исходные параметры Argon2id, частота попыток входа и числовые лимиты запросов
закреплены в общем плане как инженерные значения для реализации и проверки.

Для одной активной сессии выбраны готовое управление cookie и узкий
типизированный владелец сессии в состоянии Axum. Он хранит не более одной
записи; посещение экрана входа и запросы статики не создают анонимные сессии.

API сессий и подключаемым SessionStore. Он полезен при более широких
требованиях к сессиям. Стандартный MemoryStore в его документации обозначен
как средство для тестирования, не рекомендованное для реальных приложений;
его выбор сам по себе не реализует лимит одной сессии, очистку ключей
и защиту от запоздалых запросов. Для нашего сценария выбрана одна
типизированная запись. Сравнение RSS этих вариантов не проводилось;
число зависимостей или отсутствие HashMap не доказывают экономию памяти.

Идентификатор сессии — 32 случайных байта от CSPRNG ОС
в безопасном текстовом кодировании. Cookie содержит только этот токен;
в записи сессии остаются его SHA-256-отпечаток, идентификатор учётной записи,
поколение и время последней активности. Пароль и ключ данных в запись
сессии не помещаются. Генерация или декодирование токена не получает
небезопасного fallback при ошибке; токены не попадают в URL и журналы.
Длина cookie и кодированного токена проверяется до выделения буфера
декодирования; допустимый токен декодируется в массив фиксированного размера.

Выбранные атрибуты: имя __Host-hmail-session, Secure, HttpOnly,
SameSite=Strict, Path=/, без Domain. Cookie остаётся сессионной cookie
браузера; авторитетный срок задаётся сервером по выбранному таймауту
бездействия. Восстановленная браузером cookie после рестарта центра
доступа не даёт. Отдельное шифрование случайного токена не заменяет
серверную проверку его принадлежности действующей сессии.

Ключ данных имеет отдельного владельца, связанного с поколением сессии.
После проверки пароля и готовности ключа новый вход атомарно меняет
поколение и токен. Старые запросы и таймеры не обновляют новую сессию
и не очищают её ключ. Перед началом защищённого эффекта проверяется
актуальность допуска; уже принятое агентом задание продолжает работу
по ранее согласованному контракту. Сетевые ожидания и Argon2 не выполняются
под блокировкой владельца сессии.

Сервер измеряет бездействие монотонными часами. Для ввода и навигации,
которые сами не отправляют изменяющий запрос, используется отдельное
уведомление об активности, объединяемое клиентом не чаще одного раза
за 30 секунд и отправляемое только после действий пользователя.
Время клиента не определяет срок. Фоновый опрос и SSE не обновляют активность;
таймер отзыва работает и без новых HTTP-запросов. Интервал 30 секунд
задаёт объединение уведомлений об активности и не меняет выбранные
варианты таймаута сессии.

Выбранная CSRF-защита для браузерного JSON API:

- CsrfLayer включён также для входа, выхода и уведомлений об активности.
  Все изменяющие запросы проходят проверку до выполнения действия.
- Такие запросы обязаны содержать заголовок X-HMail-Request: 1.
  Для запросов с JSON-телом требуется application/json; обычные HTML-формы
  и text/plain не используются как альтернативный способ вызова этих API.
- Браузер и API работают с одного origin. Разрешения CORS сторонним origin
  не выдаются. Допустимый HTTPS origin и Host задаются конфигурацией центра;
  произвольный Host не становится источником доверия. Заголовки прокси
  не принимаются как доверенные без отдельной настройки проксирования.
- Сам CsrfLayer допускает запросы без Sec-Fetch-Site и Origin. Поэтому
  обязательный нестандартный заголовок остаётся отдельным условием допуска,
  а отсутствие браузерных заголовков не отключает защиту API.
- GET/HEAD/OPTIONS не запускают очистку, изменение настроек, вход или выход.
  SSE используется для чтения. Проверка cookie и полномочий остаётся
  обязательной для защищённых операций независимо от результата CSRF.
- API агентов с mTLS имеет отдельную границу доверия и не заимствует
  браузерные cookie или требования к заголовкам Svelte.

Для ограничения ресурсов выбран один одновременно выполняющийся
Argon2-расчёт в центре, без неограниченной очереди входов. Работа выполняется
через ограниченный spawn_blocking; разрешение удерживается до фактического
завершения расчёта, в том числе после отключения клиента. До него проверяются
размер тела и полей, CSRF и лимит попыток. Лимитирование попыток имеет
ограниченное состояние и не создаёт постоянной блокировки учётной записи.
Начальные параметры Argon2id описаны в разделе 5.8; частота попыток
и лимиты запросов закреплены инженерным профилем общего плана.

Выбор предполагает постоянный ограниченный объём состояния сессии и отсутствие
хранилища CSRF-токенов. Он не устанавливает измеренный RSS или скорость:
нужны замеры release-сборки в покое, при входе и при отклонении лишних запросов,
а также проверка скрытого ввода и HTTPS в целевой Windows-среде.

### 5.8. Исходный формат шифрования, параметры и восстановление

Статус: исходный технический профиль MVP. Argon2id, XChaCha20-Poly1305,
отдельный ключ данных и recovery key выбраны пользователем. Библиотеки,
параметры и сценарии ниже приняты исполнителем за основу по поручению
уточнить технические подробности; точные контракты и проверки закреплены
в общем плане и задачах B1/B2/B7. Зависимости не добавлены, код и замеры
на целевых ВМ отсутствуют. Отдельно согласовано отложить полную ротацию DEK:
в первую версию она не входит.

#### Библиотеки и расход ресурсов

| Ответственность | Предлагаемый компонент | Использование |
| --- | --- | --- |
| Парольный хеш и получение ключа | RustCrypto argon2 0.6.0 | Argon2id v1.3; независимые соли для проверочных данных и ключа защиты |
| Кодирование проверочных данных | password-hash 0.6.1 через feature/re-export argon2 | PHC-формат с алгоритмом, версией, параметрами, солью и результатом |
| Аутентифицированное шифрование | RustCrypto chacha20poly1305 0.11.0 | XChaCha20Poly1305 для профилей и защищённых копий ключа данных |

Для argon2 предлагаются default-features=false и features alloc,
password-hash, zeroize; parallel/Rayon не включается. Для chacha20poly1305 —
default-features=false и features alloc, zeroize. Соли, ключи и nonce
получаются из CSPRNG ОС через выбранный общий механизм; reduced-round
не используется. Полный граф features, PHC API и целевые сборки ещё проверяются.

Рабочий буфер Argon2 имеет явного владельца: hash_password_into_with_memory
позволяет использовать одну область памяти для последовательных вычислений.
Feature zeroize даёт нужные операции очистки, но не заменяет очистку всей
арены её владельцем на успешном выходе и при ошибке. Буфер обнуляется
и освобождается после операции; постоянно держать его в сессии не требуется.
Возврат страниц ОС и итоговый RSS зависят от аллокатора и проверяются замерами.
Обнуление собственных буферов не обещает удаления всех копий из регистров,
сторонних библиотек, swap, дампов или ранее созданных резервных копий.

#### Профиль Argon2id и схема ключей

Для первой версии предлагается явный профиль:

- Алгоритм Argon2id, версия 0x13 (v1.3).
- m_cost=32768 KiB: 32 МиБ рабочей памяти на вычисление.
- t_cost=3: три прохода; p_cost=1: одна полоса параллелизма.
- Соль — 16 случайных байт; результат — 32 байта.
- Для проверочных данных пароля и ключа защиты используются разные соли
  и два последовательных вычисления Argon2id. Сохранённый проверочный
  результат не является входом получения ключа расшифровки.

Это предлагаемый инженерный профиль приложения. Минимум OWASP —
19 МиБ/t=2/p=1; второй рекомендуемый профиль RFC 9106 — 64 МиБ/t=3/p=4.
Предложение 32 МиБ/t=3/p=1 не объявляется дословным профилем RFC.
При успешном входе оба вычисления используют одну арену последовательно:
32 МиБ — размер этой арены, не полный RSS процесса и не гарантия времени входа.
На неверном пароле второе вычисление не требуется. Автоматического снижения
параметров при нехватке памяти или большой нагрузке нет.

Алгоритм, версия, параметры и соли хранятся с соответствующей записью.
До вычисления проверяются поддерживаемый профиль, длины и версии; значения
из PHC, повреждённой БД или импортируемой копии не разрешают произвольные
выделения памяти и число проходов. Переход к другому профилю выполняется
явной миграцией с известным паролем, а не на каждом обычном запросе.

Предлагаемая иерархия:

- DEK — независимый случайный ключ данных, 32 байта.
- Парольная ветка: Argon2id с собственной солью даёт временный материал;
  HKDF-SHA256 с меткой password-wrap и идентификатором хранилища даёт ключ
  защиты DEK. Отдельная соль Argon2id используется для проверочных данных входа.
- Recovery key — независимые 32 случайных байта. HKDF-SHA256 с отдельной
  случайной солью, идентификатором хранилища и меткой recovery-wrap даёт
  второй ключ защиты DEK. Argon2id для случайного recovery key не используется.
- Рабочие ключи шифрования выводятся из DEK через HKDF-SHA256 с отдельными
  метками типа блока и стабильным идентификатором записи. Ключ защиты DEK
  не используется напрямую для шифрования профиля.

Метки HKDF включают имя приложения и версию формата; виды ключей разделены
типами и владельцами. Проверочные данные, DEK, ключи защиты и recovery key
не принимаются API как взаимозаменяемые способы обычного входа.

#### Формат сохранения и границы проверки

Версия формата — 1. Для зашифрованной записи сохраняются идентификатор
хранилища, тип и идентификатор записи, версия схемы/профиля, идентификатор
и поколение ключа, алгоритм, 24-байтный nonce и ciphertext с 16-байтным tag.
Новый случайный nonce генерируется для каждого шифрования, в том числе
при повторном сохранении или перепаковке ключа. DEK имеет две отдельные
защищённые копии — парольную и recovery; сами секретные ключи защиты не хранятся.

Публичные идентификаторы, версии и назначение блока аутентифицируются как AAD
в однозначно определённом кодировании с фиксированными длинами полей.
Обёртки дополнительно связываются с учётной записью, своим типом и поколением;
параметры получения ключа включаются в аутентифицируемый заголовок.
Точная байтовая схема кодирования закрепляется до реализации; обычная
сериализация произвольного JSON-объекта не является каноническим AAD.
Копирование ciphertext между профилями и типами блоков не должно проходить
проверку. Откат всей БД к старой копии не предотвращается одним AAD.

Открытый профиль сериализуется существующим serde_json в ограниченный буфер
и шифруется до передачи SQLx. По возможности используется in-place API;
одновременно не расшифровываются все профили. До обработки ограничиваются
размеры ciphertext, метаданных и открытого профиля. Конкретный лимит записи
зафиксирован общим планом: 64 KiB для открытого профиля, с отдельным пределом
тела JSON-запроса. Ошибка tag, версии или формата не заменяется пустым профилем.

Recovery key предлагается выдавать с префиксом hmc-recovery-v1: и 43 символами
Base64URL без padding для 32 секретных байт. Секрет создаёт генератор ОС;
пользователь его не придумывает. Существующий recovery key нельзя получить
через API чтения; новый выдаётся только в операции создания/замены,
без кеширования, журналирования или автоматического сохранения браузером.

#### Смена пароля, recovery key и восстановление

| Операция | Что меняется | Затраты относительно числа профилей |
| --- | --- | --- |
| Обычная смена пароля | Проверочные данные, обе парольные соли и парольная обёртка прежнего DEK | Постоянный объём; профили и recovery-обёртка сохраняются |
| Обычная замена recovery key | Случайный recovery key, его соль, поколение и recovery-обёртка прежнего DEK | Постоянный объём; профили и парольная обёртка сохраняются |
| Восстановление с забытым паролем | Новый пароль и его проверочные данные/обёртка, новый recovery key и его обёртка | Постоянный объём; прежний DEK открывается recovery key |

Обычная смена пароля выполняется из панели после повторной проверки текущего
пароля: новый пароль вводится дважды, создаются новые соли и обёртка DEK.
Recovery key при такой смене остаётся действительным. Все Argon2-вычисления
идут последовательно через общий ограничитель; пароли и производные ключи
не удерживаются после завершения операции.

Замена recovery key из панели также требует текущего пароля, но не требует
знания прежнего recovery key. Предлагается две фазы: подготовить и показать
новый ключ, затем подтвердить его сохранение повторным вводом. До подтверждения
старый recovery key остаётся действительным. Допускается не более одной
незавершённой подготовки; она привязана к действующей сессии/версии учётной
записи, имеет ограниченный срок и очищается при выходе или рестарте.
Исходный срок подготовки — 10 минут по инженерному профилю плана. Сам новый recovery key в БД
не сохраняется и не возвращается последующим API чтения. При потере
первоначальной выдачи подготовка отменяется и создаётся новый кандидат;
действующий старый ключ до commit сохраняется.

Для забытого пароля предлагается локальная команда hmail-cleaner center recover
при остановленном центре и исключительном доступе к его каталогу данных.
В терминале скрыто вводятся recovery key и новый пароль. После открытия DEK
создаются новые парольные данные и новый recovery key; новый ключ сохраняется
и подтверждается до замены записей. Затем центр запускается и требует
обычного входа. Старый пароль и старый recovery key текущим приложением
больше не принимаются. Автоматического запуска очистки нет.

Вычисления и проверка подготовленных обёрток выполняются до короткой
сериализованной операции фиксации. Изменения проверочных данных, обёрток
и версии учётной записи фиксируются одной транзакцией с проверкой исходной
версии. Конкурентная смена или вход с устаревшим снимком не могут установить
обратно прежние данные или сессию. После успешного изменения пароля или
recovery key текущая сессия отзывается, ключ очищается и требуется вход.
При откате сохраняются прежние данные входа и обёртки; сессия может быть
завершена. Порядок синхронизации commit с отзывом проверяется отдельно.

Для init из раздела 5.6 принят порядок шагов 4–5:
выдать recovery key и подтвердить его сохранение до commit, затем атомарно
создать учётную запись и обёртки. Это исключает завершение init до этапа
сохранения ключа владельцем. Ошибка commit остаётся ошибкой создания,
а выданный кандидат не объявляется действующим ключом установленного центра.

Обычная перепаковка закрывает старый способ входа/открытия текущей обёртки
в приложении, но не отзывает ранее скопированные БД, WAL, снимки или резервные
копии. Старый пароль/recovery key вместе со старой обёрткой может раскрыть
сохранившийся DEK и блоки, которые до сих пор используют его производные ключи.
Полная ротация DEK отложена за пределы первой версии по решению обсуждения.
Обычная смена пароля или recovery key не объявляется её заменой и не даёт
гарантии отзыва ранее раскрытого DEK. Замена раскрытых паролей MySQL
или TLS-ключей относится к управлению соответствующими реквизитами
и доверием; перешифрование их хранимых копий само по себе их не отзывает.
Старые копии БД сохраняют свою прежнюю защиту.

В задачи реализации включены тесты двух способов открытия одного DEK, неверных
паролей/ключей/tag/AAD, перепутанных записей, версий и ограничений KDF,
отката транзакций и гонок смены пароля, отмены подготовки recovery key,
повторных запросов и сбоя после commit до ответа. Отдельно проверяются
невозможность входа по сохранённому проверочному значению и отсутствие
открытых секретов в SQLite/WAL/backup и штатных логах. CPU/RSS измеряются
на целевой ВМ при полном входе и смене ключей; результаты пока не получены.

## 6. Ручной запуск и состояния операций

Пользователь выбирает сервер, период или дату и режим fast/full, выполняет
предпросмотр и подтверждает очистку. Подтверждение показывает имя целевого
сервера, конкретную границу удаления в его часовом поясе, выбранный режим
и управление состоянием hMailServer. Результат preview является оценкой
текущего состояния, а не сохранённым неизменяемым планом удаления.

### 6.1. Сохраняемые правила ядра

- Существующие файлы отбираются по `CreationTime`; для отсутствующего файла
  применяется дата записи БД. Отбор по дате строго предшествует cutoff.
- fast и full сохраняют текущую семантику, включая рекурсивный обход Data.
- Быстрый preview допускает работающую почту. Полный preview требует уже
  остановленной службы и не останавливает её скрыто.
- clean сохраняет явный выбор: требовать остановленную службу либо управлять
  остановкой и восстановлением её исходного состояния.
- Подтверждённое отсутствие файла предшествует удалению связанных SQL-строк.
- Проверки корня, DataFolder, путей, ссылок, повторных наблюдений и прав
  остаются на агенте. Нет ослабления проверки из-за доверия к центру.
- Сохраняются транзакции, блокировка БД и восстановление службы до
  освобождения блокировки. Ошибки и частичные результаты не считаются успехом.
- Отмена завершает текущий безопасный пакет и выполняет необходимую уборку
  ресурсов; подтверждение запроса отмены не означает завершение операции.

### 6.2. Предлагаемые правила сетевого выполнения

- Агент владеет жизненным циклом принятого задания. Закрытие браузера,
  смена выбранного сервера или потеря связи с центром не отменяют его.
- У задания есть стабильный идентификатор, целевой агент и версия снимка
  профиля. Повтор команды с тем же идентификатором возвращает существующее
  состояние; изменение параметров под тем же идентификатором отклоняется.
- Потерянный ответ запуска даёт состояние «результат запроса неизвестен»;
  центр выясняет состояние по идентификатору, не создавая новую очистку.
- На одном агенте не выполняются перекрывающиеся операции, затрагивающие
  одну почтовую установку; существующая SQL-блокировка сохраняется.
- Для общего Hyper-V-хоста предлагается одна тяжёлая операция за раз через
  центр. Это координация операций панели, а не распределённая гарантия
  против независимого запуска CLI. Автоматическая очередь пока не требуется.
- Потеря связи с работающим агентом не освобождает ограничение запуска
  другой тяжёлой операции до согласования фактического состояния.
- Агент хранит минимум локального состояния, достаточный для узнавания
  принятого задания и восстановления отчётности. Это не копия профилей SQLite.
- После перезапуска агента удаление не продолжается автоматически. Панель
  показывает прерывание и фактическое состояние почтовой службы; гарантировать
  восстановление службы после аварийного завершения без проверки нельзя.

Ошибки связи, ошибки аутентификации, недоступная SQLite и повреждённые
профили не преобразуются в пустой список серверов или успешный результат.
Атомарное принятие задания, формат сохранения локального состояния и порядок
согласования после сбоев должны быть завершены в техническом дизайне.

## 7. HTTP, интерфейс и расход ресурсов

Панель, API и поток прогресса доступны с одного origin. Предлагаемый канал
прогресса — SSE. Браузер получает начальный снимок и обновления состояния;
повторное подключение восстанавливает актуальное представление задания.
Журнал ошибок не должен зависеть от доставки каждого промежуточного события
счётчиков в браузер.

Из-за передачи паролей, сессий и реквизитов предлагается HTTPS для браузера.
Между центром и агентами выбран HTTPS с обязательным mTLS и проверкой доверия
к сертификатам и идентичности узлов. Первоначальная установка идёт по SSH.
HTTP описывает тип интерфейса, а не требование передавать секреты открытым
текстом. Отдельный прокси не обязателен. Схема выпуска сертификатов и начального
доверия ещё уточняется; при проксировании SSE важны буферизация и таймауты.

Статическая сборка Astro + Svelte встраивается в сборку центра и отдаётся
готовыми HTML/CSS/JS из Rust-приложения.
На рабочем сервере не требуется frontend dev-server или отдельный процесс
Node.js, Bun либо Astro. Статическая сборка не означает статичные данные:
настройки, права и состояние операций приходят из API после входа.

Согласованная схема сборки и работы:

```text
Сборка: Astro + Svelte -> HTML/CSS/JS, включая код запуска островов

Работа: браузер <-> HTTPS, API и SSE <-> Rust-центр
                                             |
                                        HTTPS + mTLS
                                             |
                                         Rust-агент

Установка агента: Rust-центр -> SSH -> целевая ВМ
```

Статика, API и SSE обслуживаются одним HTTP-сервером центра. Разделение
на центр и агентов сохраняет локальное выполнение очистки на почтовых ВМ;
оно не добавляет Astro в цепочку сетевых запросов.

Для небольшого расхода ресурсов предлагаются:

- Объединение частых промежуточных обновлений счётчиков и ограниченная частота
  отправки/перерисовки, без ограничения скорости самой очистки.
- Ограниченные очереди и буферы в центре, агенте и браузере; медленный клиент
  не задерживает очистку и не вызывает бесконечного накопления событий.
- Ограниченное окно журнала и постраничное чтение истории, без загрузки
  всех результатов или всего почтового дерева в браузер.
- Хранение подробных журналов на диске с ротацией и без паролей/полных URI.
- Освобождение сетевых подписок и отсутствие фоновых сканирований Data
  только ради открытой панели.
- Получение ключей из пароля при входе и смене пароля,
  без повторения этой дорогой операции на каждом запросе или событии SSE.

Начальные инженерные лимиты закреплены в общем плане и проверяются
при реализации. После измерений они уточняются как именованные настройки
с единицами измерения, без ослабления согласованных правил сохранности.
Числа RSS, CPU и размеров JS-бандла до измерений не обещаются.

Панель показывает реальные этапы, счётчики и время последнего изменения.
Процент допустим только для этапа с известным объёмом работы. Потенциальные
объёмы preview отличаются от подтверждённых удалений; сумма размеров удалённых
файлов не выдаётся за измеренное увеличение свободного места диска.
`remaining_old_files = null` сохраняет значение «итоговая сверка не завершена»,
а не «остатков нет».

### 7.1. Навигация и оформление MVP

Выбраны светлая рабочая область и графитовый sidebar. В sidebar первой
версии находится один модуль — «Очистка почты». В будущем сюда добавляются
другие модули; пустые пункты и заглушки будущих разделов в MVP не показываются.
Оболочка навигации отделена от содержимого модуля, без реализации отдельной
системы плагинов на этом этапе.

Внутри модуля пользователь выбирает почтовый сервер. В шапке рабочей области
находятся выбор сервера и разделы «Очистка», «История»; история относится
к выбранному серверу. Общая кнопка «Настройки» находится в верхней части шапки
рядом с SA — учётной записью суперадмина и выходом. В настройках размещены
управление агентами и технические профили почтовых серверов. Для редактирования
профиля явно указан выбранный сервер. Добавление сервера находится в управлении
агентами: подключение, установка агента и настройка почты. Дополнительного
модуля настроек или агентов в sidebar нет.

В футере находятся версия и идентификатор сборки центра, а также сводка
состояния агентов. Сводка раскрывается в список с названием каждого сервера,
состоянием связи, версией агента и временем последнего контакта. Недоступный
агент явно отличается от доступного; сохранённая версия и последнее состояние
не выдаются за свежие данные. Футер не перекрывает рабочую область.

Предложенная композиция основного экрана:

1. Под шапкой — действие, режим, период хранения и поведение почтовой службы.
   Основные действия — предпросмотр и переход к подтверждению очистки.
2. В центре — текущий этап, progress bar, подтверждённые счётчики и журнал.
   При неизвестном объёме этапа показывается неопределённый прогресс без
   вымышленного процента или времени завершения.
   Кнопка в заголовке журнала раскрывает его на всю область приложения:
   sidebar, шапка и параметры скрываются, а контекст сервера, прогресс операции
   и футер сохраняются. Кнопка «Свернуть» или Escape возвращает обычный вид.
   Раскрытие и сворачивание не перезапускают задание, не очищают журнал
   и не создают отдельную подписку на события. Раскрытый журнал сохраняет
   ограниченное окно событий; полноэкранное представление не означает
   загрузку всей истории в память браузера.
3. Перед удалением — отдельное подтверждение с выбранным сервером, режимом,
   датой отсечения во времени сервера, результатом предпросмотра и действием
   со службой. Цель подтверждения зафиксирована. Изменение сервера или
   параметров делает прежний предпросмотр недействительным.

Полный предпросмотр требует уже остановленной службы и сам её не
останавливает. Очистка различает требование остановленной службы и явное
управление остановкой с восстановлением исходного состояния. Во время
выполнения параметры принятого задания не редактируются. Остановка задания
показывает ожидание завершения текущего пакета и восстановления службы;
успех остановки не сообщается до подтверждённого результата.

История загружается при открытии, относится к выбранному серверу и читается
страницами. Настройки также подгружаются при открытии; технический профиль
не выводится в общий журнал. Данные о потенциальном удалении отличаются
от подтверждённых удалений. Журнал показывает ограниченное окно событий.
При потере связи остаются последние полученные данные с отметкой их времени
и отсутствия актуальных обновлений. Выход из панели не отменяет принятое
агентом задание.

Вход — отдельный экран собственной учётной записи приложения. Настройки
учётной записи центра не смешиваются с настройками выбранного почтового
сервера; точное размещение этих дополнительных действий уточняется при
проектировании экрана учётной записи. Отдельной UI-блокировки и расписаний нет.

Композиция, подписи и поведение переходов показываются интерактивным
дизайн-макетом с явно обозначенными демонстрационными данными. Макет не
подключается к серверам и не подтверждает готовность frontend или backend.
На узких экранах область модулей и формы перестраиваются без потери основных
действий. Внешний вид макета остаётся предложением до обсуждения результата.

### 8.1. Выбранный frontend: Astro static + Svelte-острова

Astro заранее формирует страницы, layout и статичную оболочку. Svelte добавляет
интерактивность в явно определённых клиентских островах.
Острова сохраняются в статической сборке: она содержит их HTML, клиентские
модули и код загрузки/гидратации. После получения файлов от Rust этот код
запускается в браузере; наличие островов не требует отдельного Astro-процесса.

JavaScript/TypeScript, браузерные события, fetch и SSE остаются доступны
frontend. Выбор Rust-backend не переносит интерфейс на Rust и не исключает
Svelte. Серверные операции, авторизация и доступ к данным принадлежат Rust API;
в production не используются Astro Actions, Astro Sessions или server islands.

| Часть интерфейса | Граница и момент загрузки |
| --- | --- |
| Выбор сервера, параметры, предпросмотр, запуск, отмена и прогресс очистки | Один основной Svelte-остров; становится интерактивным при открытии рабочего экрана |
| История запусков | Отдельный Svelte-остров; его JS и данные загружаются при первом открытии раздела |
| Настройки серверов и подключений | Отдельный Svelte-остров; его JS и данные загружаются при первом открытии раздела |
| Заголовки, обычная навигация, пояснения и справка | Статические Astro-компоненты без клиентской гидратации, пока им не требуется интерактивное поведение |

Основной остров содержит небольшие компоненты с общим состоянием и не является
одним монолитным компонентом. Для его начальной разметки предлагается
`client:load`: HTML формируется при сборке, затем Svelte подключает действия.
Заготовка не содержит реальных настроек, секретов или пользовательских данных;
состояние сессии и свежие данные запрашиваются у Rust-backend.

Загрузка истории и настроек по необходимости означает явное открытие раздела,
а не обязательную загрузку всех островов вместе с рабочим экраном. Механизм
реализации выбирается так, чтобы сохранять это поведение. `client:visible`
реагирует на появление элемента в viewport и подходит, если раздел до открытия
действительно скрыт; директива сама по себе не означает загрузку по нажатию.
Допустима явная загрузка модуля при открытии. `client:idle` не заменяет это
требование, поскольку может загрузить ещё не открытый раздел.

Рабочее состояние, общее для нескольких островов, принадлежит Rust-backend.
Островы получают его через API и события, а не через общий авторитетный
Svelte store. Внутри каждого острова допустимы собственные компоненты, stores
или другая реактивность для локального UI и представления серверных данных.
Обычный компонентный context не используется для связи разных островов.

Один транспортный модуль браузера может владеть SSE-подключением в пределах
вкладки и доставлять полученные события заинтересованным островам. Это общий
канал доставки, а не второй источник рабочих данных. История и настройки
не создают собственные дублирующие потоки прогресса для того же задания.

Отложенная загрузка сокращает начальную работу браузера, когда дополнительные
разделы не открываются. После активации всех островов меньший расход RAM/CPU
сам по себе не гарантирован. Закрытие раздела не считается автоматической
выгрузкой его JS; жизненный цикл подписок и буферов контролируется явно.

### 8.2. Server-first и Rust-backend

В выбранной схеме сервер является источником прав, данных и состояния
операций. Rust-backend проверяет сессии и полномочия при каждом защищённом
запросе, валидирует настройки и параметры запуска, работает с SQLite,
разблокирует секреты и взаимодействует с агентами. Изменение клиентского
состояния или обход интерфейса не позволяет обойти эти проверки.

Astro выполняет предварительный рендеринг HTML во время сборки. Rust отдаёт
этот HTML и собранные ресурсы, а Svelte гидратирует только нужные острова.
Актуальные авторизованные данные поступают через Rust API и SSE. Ключи
шифрования, материал доверия к агентам и реальные настройки серверов
не попадают в статическую сборку.

Это сочетание server-first организации логики и предварительного рендеринга
оболочки, а не Astro SSR на каждый HTTP-запрос. Раздача статических файлов
Rust-сервером не выполняет `.astro`-компоненты во время запроса. Для такого
Astro SSR нужен соответствующий adapter/runtime и отдельное решение о размещении.
В текущую схему не входят обязательный JS-server runtime, Astro API endpoints
для рабочих операций, Astro Actions и server islands с `server:defer`.
Рабочий API принадлежит Rust; выбранные острова — клиентские.

### 8.3. Изолированные острова и шина данных через Rust

Изоляция означает отдельные frontend-модули с явными контрактами:
очистка/прогресс, история и настройки. Они не вызывают внутренние операции
друг друга. Разделение на отдельные репозитории, процессы или независимо
развёртываемые приложения для этого не требуется.

| Действие или событие | Владелец |
| --- | --- |
| Запросить историю или текущие настройки | Остров обращается к Rust API; backend проверяет права и возвращает данные |
| Сохранить профиль или запросить запуск/отмену | Остров отправляет явную команду Rust-backend; ответ клиенту сам по себе не подменяет фактическое состояние агента |
| Изменить состояние задания | Агент сообщает фактический результат центру; Rust обновляет серверное состояние и историю и публикует событие |
| Обновить представление после изменения | Загруженный остров получает событие и обновляет свой снимок либо перечитывает нужную часть через API |
| Открыть вкладку, набрать ещё не сохранённый текст, показать подсказку | Локальное состояние соответствующего острова |

Например, после принятого запуска центр публикует событие начала задания.
При завершении агент сообщает результат, центр фиксирует его и публикует
событие завершения. Остров очистки показывает итог, а загруженный остров
истории обновляет записи. Если история ещё не открывалась, для обработки
этого события её JS не загружается: при открытии она читает актуальную историю
с Rust-backend. После сохранения настроек сервер публикует изменение профиля;
оно не меняет снимок уже выполняемого задания.

Обмен имеет две стороны: команды/чтение через HTTP API, уведомления от Rust
через SSE. Внутри процесса Rust предлагается ограниченная шина событий
с типизированными контрактами. Подробная история и финальные результаты
не должны существовать только в памяти шины или зависеть от того, успел ли
браузер получить событие. После переподключения, пропуска или отставания
потребителя клиент заново согласует состояние с backend. Важные сведения
сохраняются владельцем операции; промежуточные счётчики можно объединять.

Каждая команда очистки явно содержит идентификатор сервера и привязку
к подтверждённым параметрам. События заданий несут идентификаторы сервера
и запуска, а изменения профилей — их идентификатор и версию. Выбранный
сервер относится к конкретному экрану/вкладке, а не к глобальной переменной
центра или единой цели для всех сессий суперадмина. Если выбор транслируется
через Rust другим островам, он имеет область действия соответствующей вкладки.
Работа во второй вкладке не может подменить цель подтверждения или запуска
в первой. Идентификаторы области UI не заменяют проверку полномочий.

Rust фильтрует выдачу событий по действующей авторизации и области подписки.
События не содержат паролей, ключей и полных строк подключения. Клиентские
снимки не являются основанием для допуска удаления или изменения профиля.
Готовые настройки и результаты сохраняются сервером, но несохранённый ввод
формы и каждое нажатие клавиши не пересылаются через Rust без необходимости.
Так серверная шина не добавляет сетевые обращения для чисто локальных UI-действий.

### 8.4. Библиотеки SSH и mTLS: выбранный набор

Для SSH и mTLS в обсуждении выбран следующий набор. Базовые версии проверены
по опубликованным метаданным crates.io на 2026-10-17. Выбор библиотек
и версий не означает, что зависимости уже добавлены в Cargo.lock или
совместимость всей сборки с Windows Server 2016 подтверждена.

| Ответственность | Выбранная библиотека и базовая версия | Причина выбора |
| --- | --- | --- |
| SSH-клиент центра | russh 0.64.1 | Асинхронный клиент на существующем Tokio; проверка host key и выполнение установочных команд |
| Передача пакета | russh-sftp 3.0.1 | Потоковая передача по SFTP поверх SSH без загрузки всего EXE в память |
| TLS и проверка сертификатов | rustls 0.23.46 с провайдером ring 0.17.14 | Управляемое приложением доверие и mTLS, переносимый TLS-стек |
| Интеграция TLS с Tokio | tokio-rustls 0.26.6 | Асинхронный TLS; используется в том числе через серверную и клиентскую библиотеки |
| HTTPS для Axum | axum-server 0.8.0 | Подключение собственного rustls ServerConfig с обязательной проверкой клиентских сертификатов |
| HTTP-клиент центра | reqwest 0.13.5 | Запросы и потоковые ответы агентов, клиентский сертификат и ограниченный пул соединений |
| Ключи, CSR и сертификаты | rcgen 0.14.10 | Локальное создание ключа/CSR агентом, выпуск сертификатов в центре |

Для SSH также рассмотрен ssh2 0.9.6: он предоставляет SFTP и работает
поверх libssh2, однако добавляет нативную C-библиотеку и требует отдельной
интеграции её I/O с Tokio. Russh выбран по соответствию
текущему runtime и управлению соединением; меньший RSS относительно ssh2
не измерен и не считается доказанным.

Предлагается отключать default features и явно выбирать ring для Russh,
Rustls, Tokio-Rustls и rcgen, а для обёрток — варианты без автоматического
выбора криптопровайдера: tls-rustls-no-provider у axum-server и
rustls-no-provider у reqwest. У reqwest нужны JSON и потоковые ответы.
Граф Cargo features проверяется целиком: транзитивные зависимости могут
повторно включить AWS-LC или другие отключённые возможности.
Сжатие SSH и поддержка RSA включаются только по подтверждённой необходимости
совместимости с целевым SSH-сервером и выбранными ключами.

Ring уже присутствует в Cargo.lock через SQLx; его переиспользование
сокращает число различных криптографических backend в выбранном наборе,
но само по себе не доказывает выигрыш RSS или скорости относительно AWS-LC.
Ring содержит C/assembler-компоненты и требует соответствующих инструментов
на сборочном хосте. На почтовую ВМ устанавливается готовая сборка.

Существующий SQLx 0.7.4 использует rustls 0.21.12. По политике Rustls ветка
0.21 не получает исправлений безопасности; она не предлагается для нового
HTTP API ради совпадения версий. Новая ветка 0.23 и прежняя зависимость SQLx
могут присутствовать одновременно. Решение о переносе MySQL-адаптера
и обновлении SQLx принимается отдельно; этот подбор не обновляет их автоматически.

Для новой версии согласовано обновление до актуального стабильного Rust.
На 2026-10-17 это Rust 1.99.1, выпущенный 2026-10-15; он выбран и для
toolchain, и как объявленный минимум компилятора (MSRV). В mise.toml
и workspace.package.rust-version при реализации закрепляется точный номер
1.99.1. Дальнейшие обновления выполняются явно, с проверкой зависимостей
и целевых сборок.

Опубликованный russh 0.64.1 требует Rust 1.89, rcgen 0.14.10 — Rust 1.88;
их заявленные минимумы укладываются в выбранную версию. Полный граф
зависимостей ещё проверяется при разрешении и сборке на Rust 1.99.1.
Сейчас mise.toml по-прежнему содержит Rust 1.98.1, а Cargo.toml — минимум
1.85: манифесты проекта в этом обсуждении не изменяются. Поддержка
компилятора и минимальной ОС проверяется раздельно.

Rust документирует Windows Server 2016 как минимальную серверную ОС
для Windows MSVC. У Russh есть сборка на windows-latest; это подтверждает
поддержку Windows в CI, но не выполнение на Server 2016. Целевая сборка —
x86_64-pc-windows-msvc с существующей политикой статического MSVC runtime.
TLS реализуется Rustls, а не возможностями системного Schannel;
CA приложения задаётся явно, с проверкой цепочки, имени и разрешённого узла.
Проверка цепочки сама по себе не подменяет допуск конкретного центра/агента.

При приёме CSR центр использует библиотечную проверку подписи запроса;
разрешённые идентификаторы, SAN, EKU и права CA задаёт политика центра,
а не произвольные поля запроса. Функции разбора и проверки CSR у rcgen
требуют feature x509-parser. Конфигурация серверного rustls должна явно
требовать клиентский сертификат; клиентский HTTP API доверяет CA приложения
и использует свою mTLS identity. Детали допуска и отзыва остаются частью
контракта доверия, а не автоматически решённой задачей библиотеки.

Для расхода ресурсов предлагаются:

- SSH/SFTP относятся к центру; сборке рабочего агента они не нужны.
  Агент сохраняет TLS и локальную подготовку собственного ключа/CSR.
- Пакеты передаются потоком; размеры SSH-пакетов, буферов каналов
  и числа незавершённых SFTP-запросов ограничиваются явно.
- SSH-соединение и установочные буферы освобождаются после операции.
- TLS-конфигурации и HTTP-клиенты переиспользуются в пределах своего
  жизненного цикла доверия; смена сертификатов и отзыв доступа обновляют
  соответствующие соединения и пулы.
- Параллельность установок, TLS-handshake, число соединений и очередей
  ограничиваются. Конкретные значения выбираются после измерений.

На настоящем Server 2016 нужны установка через OpenSSH/SFTP, проверка host key,
запуск службы, успешный mTLS и отказы для неверных сертификатов, а также
измерения CPU/RSS при установке, TLS-handshake и после освобождения соединений.
Размер EXE, отсутствие требуемых сторонних DLL и расход памяти проверяются
на итоговой release-сборке; число зависимостей не заменяет эти измерения.

### 8.5. Монорепозиторий и отдельные поставки

Существующий Cargo workspace становится основой единого монорепозитория.
Текущие crates/core, crates/adapters и crates/cli сохраняют расположение.
Добавляются crates/runner для общего разового запуска, crates/protocol для
контрактов, crates/center и crates/agent для приложений. Frontend размещается
в apps/web, Containerfile/Quadlet — в deploy, инструменты сборки — в tools.
Детальная структура и владельцы файлов заданы в трёх частях плана MVP.

В корне остаются Cargo.toml/Cargo.lock и mise.toml; для frontend добавляются
private Bun workspace с package.json и один bun.lock. Cargo управляет
Rust-графом, Bun — frontend, mise предоставляет общий вход в проверки.
Nx/Turborepo и отдельная система плагинов для будущих модулей в MVP не нужны.
Существующие команды не переименовываются ради новой структуры.

Зависимости разделяются по поставкам. Центру не нужны runner, почтовый MySQL
и Windows/SCM; агенту не нужны SSH/SFTP-клиент установки и frontend.
Общий wire-контракт не импортирует эти приложения или драйверы.
Features проверяются отдельными целевыми сборками; один репозиторий
не означает включение всех зависимостей в каждый бинарник.

Центр и собранный web выпускаются одним OCI-образом, Windows-агент —
отдельным проверяемым пакетом. Версия API-протокола отделяется от версии
сборки. В MVP используется protocol v1; несовместимый агент не получает
рабочую команду и технический профиль. Установка и обновление агента
выполняются по явному действию администратора; unattended update не добавляется.
Операции одного агента не прерываются ради установки новой версии.

## 9. Проверка реализации и критерии приёмки

После реализации должны быть проверены:

1. Вход суперадмина без Windows-профиля; закрытый доступ к действиям без сессии.
2. Два профиля в одной SQLite; изменение параметров через общую панель.
3. Работа центра с Windows-путями целевых агентов независимо от ОС центра.
4. Сохранение секретов в зашифрованном виде; отсутствие их в API чтения,
   штатных журналах и незашифрованных снимках истории. Проверка файлов
   SQLite/WAL и резервной копии не обнаруживает открытые значения,
   отнесённые к зашифрованной части конфигурации: все поля подключения MySQL,
   пути Data/INI, имя службы и секреты доступа к агенту. События, история
   и ошибки не раскрывают эти значения. Авторизованный API настроек позволяет
   редактировать технические поля и не возвращает сохранённые секреты.
5. Отсутствие сессии и открытого ключа после рестарта, расшифрование при входе,
   смена пароля и восстановление без потери секретов.
6. Запуск только на выбранном сервере, явное подтверждение параметров
   и сохранение правил preview/clean/fast/full существующего ядра.
7. Повторная отправка команды, потеря ответа запуска, потеря SSE и восстановление
   соединения без повторного удаления или ложного статуса завершения.
8. Отмена, ошибка очистки и ошибка восстановления службы с корректным итогом.
9. Перезапуск центра при работающем агенте и прерывание самого агента;
   ни один случай не получает фиктивное подтверждение завершения или восстановления.
10. Длительно открытая панель и медленный клиент не вызывают неограниченного
    роста журналов в памяти и не блокируют обработку почтового хранилища.
11. Управление очисткой и прогресс находятся в одном острове; JS и данные
    истории и настроек загружаются по первому открытию соответствующего раздела,
    без дублирования потока прогресса. Повторные открытия не накапливают подписки.
12. Статическая HTML-оболочка доступна из Rust-приложения без запущенного
    Astro/Node/Bun-сервера и не содержит секретов или данных рабочей установки.
    Тот же HTTP-сервер центра обслуживает API и SSE; Svelte-острова остаются
    интерактивными при раздаче production-сборки непосредственно из Rust.
13. Общие рабочие данные и события островов проходят через Rust; открытие
    истории после завершения очистки показывает сохранённый результат даже
    без получения исходного события. Две вкладки с разными целевыми серверами
    не влияют на цель подтверждения/запуска друг друга.
14. Таймаут бездействия выбирается из 15 минут, 30 минут, 1 часа и 1 дня
    и сохраняется между перезапусками. Его истечение отзывает общую сессию
    всех вкладок и очищает ключ центра; фоновые обновления не продлевают срок.
    Выход не отменяет принятое агентом задание. Отдельной UI-блокировки нет.
15. Успешный новый вход заменяет прежнюю сессию без одновременного доступа
    из двух сессий; неудачный вход не прерывает текущую. Прежние cookie и SSE
    больше не дают доступа. Запоздалый выход или таймаут прежней сессии
    не завершает новую и не очищает её ключ. Принятое агентом задание продолжается.
16. После запуска или перезапуска процессов, наступления прежнего времени
    расписания и восстановления связи удаление самостоятельно не начинается.
    Автоматический запуск очистки и настройки планировщика удалены из новой
    версии CLI. Служба агента ожидает явную ручную команду.
17. Добавление сервера из панели устанавливает агент через заранее настроенный
    SSH-доступ, автоматически настраивает mTLS и только затем предлагает
    настройку MySQL и путей. Установка не запускает очистку и не останавливает
    hMailServer; в UI различаются «Агент установлен» и «Профиль готов».
18. Команды отвергаются при отсутствии действительного разрешённого участника
    mTLS. Перепутанный агент не получает профиль другого сервера. Установочные
    реквизиты и закрытые ключи не раскрываются в истории, событиях и журналах.

Для локального init проверяются повторный и конкурентный запуск, отсутствие
частично созданной учётной записи при откате транзакции и различение новой
БД с ошибкой чтения или повреждением существующей базы. Пароль и recovery key
не появляются в аргументах процесса и штатных логах.

Для выбранной защиты раздела 5.7 дополнительно проверяются
отказы браузерного API для чужого origin, отсутствующего обязательного
заголовка и простых HTML-форм, включая вход и выход. Проверяются сценарии
без Fetch Metadata, безопасные методы, ограничения буферов и отсутствие
неограниченной очереди Argon2 при множестве запросов и отключении клиентов.

Расход CPU/RSS центра и агента измеряется отдельно в покое, с открытой панелью
и во время fast/full. На клиенте отдельно измеряются production JS, первый
показ/готовность действий, память после длительной работы и число DOM-узлов.
Нагрузка существующего MySQL и диска рассматривается отдельно от UI.

Нужны реальные проверки Windows-агентов, SCM и файловых атрибутов на целевой
среде; cross-build и переносимые тесты их не заменяют. Для переносимости центра
нужны самостоятельные сборка и запуск на заявленных платформах.
Развёртывание и очистка рабочей почты требуют отдельной авторизации и не входят
в подготовку этой спецификации.

## 10. Инженерная проработка и план реализации

Перечисленные технические решения и проверки выполняет исполнитель.
По отдельности утверждать версии библиотек, размеры буферов или внутренние
форматы пользователь не должен; вопросы возвращаются к нему, если решение
меняет согласованные сценарии, полномочия или сохранность данных.

1. Для выбранных Astro static + Svelte определить routing, подход к стилям,
   механизм загрузки истории/настроек по открытию и конкретные версии.
2. Для выбранных Axum + Tokio и SQLite + SQLx утвердить остальные
   backend-библиотеки, Cargo features, платформенные сборки и точные версии
   остальных инструментов без попутной несогласованной миграции текущего стека.
   Rust 1.99.1 для toolchain и объявленного MSRV уже выбран.
   Остаются проверка совместимости, миграции, настройки подключений,
   режим сохранности и резервное копирование.
3. Для выбранного порядка «Podman + Quadlet с центром в Linux-ВМ на существующем
   Hyper-V-хосте, затем агенты на Windows-ВМ из панели» проверить дистрибутив,
   rootless Podman/systemd, cgroup v2, linger, базовый образ, ресурсы/сеть ВМ
   и постоянный каталог данных. Совмещённый
   процесс центра и агента для MVP не требуется. Закрепить доставку,
   обновление с миграциями и восстановление центра, правило последовательных
   тяжёлых операций и безопасное обновление агентов; фактические адреса
   задаются при установке. Отдельный Linux-хост остаётся будущим вариантом.
4. Набор библиотек установки по SSH и рабочего mTLS выбран в разделе 8.4.
   Проверить полный граф features и сборку на выбранном Rust 1.99.1
   для целевых ОС.
   Определить способ входа и первоначальной проверки host key, подготовку OpenSSH
   на целевой Windows, пакет и проверку артефакта агента. Закрепить выдачу
   сертификатов, HTTPS bootstrap браузера и обновление/отзыв доверия.
   Локальное первоначальное создание суперадмина уже выбрано (раздел 5.6).
   Уточнить повторную установку,
   конфликт с существующей службой, обработку частичного сбоя и выхода
   суперадмина во время установки; секреты требуют явного жизненного цикла.
5. Для выбранной схемы авторизации из разделов 5.6–5.7 завершить
   синхронизацию вкладок и правила гонок отзыва доступа с выполняемыми
   запросами; закрепить числовые лимиты попыток входа и размеров запросов.
   Tower-cookies, одна типизированная запись сессии в Axum, атрибуты cookie
   и tower-http CsrfLayer с обязательным заголовком браузерного API выбраны.
   Хранение сессии в памяти, отдельный владелец ключа, учёт реальной активности
   и не более одного одновременно выполняющегося Argon2-расчёта выбраны.
   Таймаут бездействия с вариантами 15 минут, 30 минут, 1 час и 1 день,
   полный выход с очисткой ключа и отсутствие отдельной UI-блокировки выбраны.
   Успешный новый вход заменяет прежнюю активную сессию.
   Дополнительный абсолютный срок сессии не утверждён.
6. Для выбранных Argon2id + XChaCha20-Poly1305 завершить формат ключей
   и восстановления, атомарную смену пароля, отзыв сессий и замену recovery key.
   Предложение библиотек, параметров, иерархии ключей и сценариев находится
   в разделе 5.8; это исходный вариант инженерной проработки. Уточнить двухфазное
   подтверждение recovery key, точное кодирование AAD и размеры блоков.
   Полная ротация DEK отложена за пределы первой версии.
   Утвердить криптобиблиотеки, версии и параметры Argon2id, формат AAD,
   версионирование и размещение зашифрованных блоков. Шифрование всего технического
   профиля — MySQL, путей, имени службы и секретов доступа к агенту — выбрано;
   имена серверов, статусы и счётчики истории остаются обычными данными.
7. Завершить контракт принятия/сохранения заданий, согласование после сбоев,
   совместимость версий центра и агентов и хранение истории/ротацию.
   Для шины Rust определить контракты событий, области подписок,
   версии/порядок обновлений и согласование снимка после пропусков.
8. Выбрать измеряемые ресурсные лимиты. Отсутствие замеров не является
   подтверждением соответствия требованию небольшого расхода ресурсов.
9. Для выбранного удаления очистки по расписанию определить миграцию
   существующей службы CLI и обработку прежних параметров расписания.
   Установка новой версии не должна оставлять параллельно работающий
   прежний планировщик. Службы новой версии запускают процессы ожидания команд.

Пользователь подтвердил стек и поручил подготовить план реализации MVP.
[Общий план](../plans/2026-10-17-hmail-control-center-mvp.md) задаёт порядок,
границы модулей, исходные инженерные значения и ссылки на три исполнимые части:
агент, центр, интерфейс и поставка. Указанные выше проверки распределены
между задачами этих частей; это не список отдельных вопросов к пользователю.
Технические предложения раздела 5.8 используются как исходный профиль реализации
с уточнениями общего плана. Продуктовые ограничения этой спецификации имеют
приоритет. Подготовка плана не означает начала реализации или развёртывания.
Делегирование технических подробностей не меняет согласованный объём продукта
и не подтверждает совместимость или результаты ещё не выполненных измерений.
