# Очистка hMailServer: ядро, CLI и карта файлов из БД

Дата: 2026-10-07. Статус: проект для проверки пользователем; реализация ещё не начата.

## Назначение и согласованные требования

Программа запускается непосредственно на Windows Server 2016 с hMailServer.
Она удаляет старые письма во всех аккаунтах и их почтовых папках, сохраняя сами
аккаунты и папки. Пользователь задаёт срок хранения в днях, календарных месяцах
или годах либо явную границу даты и времени.

БД определяет, какие письма подлежат удалению, и задаёт карту физических файлов.
Порядок для каждой порции: сначала удаление файлов, затем удаление соответствующих
записей из БД. Если файл уже отсутствует, его старая запись тоже удаляется.
Ошибка доступа, ошибочный путь и отсутствие файла — разные результаты.

Первый рабочий интерфейс — CLI; ядро должно быть пригодно для последующего окна
Tauri. Разработка и переносимые тесты выполняются на macOS. Рабочая проверка
Windows, службы и файловой системы проводится отдельно на тестовом сервере.

Ветка `update` создана локально от `main` репозитория `kubefox-bot/rust`,
исходный коммит `94836e5e770bc30009a4d256080de8ceb1fa09c5`.
Публикация ветки и запуск на настоящей почтовой БД не входят в текущую подготовку.

## Что обнаружено в существующей реализации

- `src-tauri/src/service/files/file_service.rs:53` обходит всё дерево `Data`.
- На строке 59 для каждого найденного файла вызывается `Vec::contains` по всему
  списку имён из БД. При F файлах и K выбранных письмах получается до F × K
  сравнений. На Windows сравнение только имён также не проверяет владельца файла.
- Удаление на строке 68 последовательное; на каждое письмо отправляются событие
  в окно и запись успешного удаления в лог.
- Строка 84 запускает второй полный обход для удаления пустых директорий.
  Эта процедура может удалить и сам корень при его опустошении.
- Ошибки удаления файлов логируются, но `delete_files` всё равно возвращает
  успешный результат, если другие операции не завершились ошибкой.
- `src-tauri/src/service/db/mod.rs:44` удаляет все строки старше границы даты,
  без связи с результатами удаления файлов и без очистки зависимых таблиц.
  Ранее закомментированный вызов нельзя безопасно восстановить одним изменением.
- Выборка читает все выбранные сообщения в память и сортирует их по дате.
  В предоставленной схеме нет индекса по `messagecreatetime`.

Это подтверждённые свойства кода. Точная причина прошлых ошибок удаления из БД
не установлена: журнал ошибок с того сервера не предоставлен.

## Сравнение алгоритмов

| Подход | Стоимость поиска файлов | Ограничение |
| --- | --- | --- |
| Полный обход + поиск имени в Vec | До O(F × K) | Существующий медленный путь |
| Полный обход + HashSet имён | Ожидаемо O(F + K) | Всё ещё читает всё дерево и требует проверки владельца |
| Точный путь из записи БД | O(K) построений путей | Требует поддержки структуры и старых абсолютных путей |

Выбран третий подход. Служебная карта ссылок из всей БД строится отдельно,
порциями, чтобы выявлять общий файл у нескольких записей. Это линейный объём
чтения R строк БД; индекс локальной карты имеет собственную стоимость.
Общее время работы не описывается одним O(K): чтение БД, журнал и удаление на
файловой системе измеряются отдельно.

Проверочный синтетический замер на этом Mac, Rust 1.98.1, оптимизация `-O`:
50 000 имён файлов, 5 000 выбранных имён, каждый десятый файл выбран.
Алгоритм с Vec выполнил 237 502 500 сравнений.

| Операция | Один замер |
| --- | --- |
| Сопоставление через Vec::contains | 397,005 мс |
| Создание HashSet и сопоставление | 1,393 мс |
| Построение 5 000 точных путей | 1,302 мс |

Генерация входных строк исключена из замера. HashSet создавался внутри своего
замера. Проверено совпадение числа выбранных элементов. Это диагностический
замер в памяти без MySQL, NTFS и удаления файлов; обещать такое же ускорение
всей очистки на его основании нельзя.

## Отбор писем и построение карты

Авторитетная дата — `hm_messages.messagecreatetime`, сравнение строго `< cutoff`.
Дата изменения файла и MIME-заголовок `Date` не участвуют в отборе.
Граница фиксируется один раз и записывается в план операции.

`messagecreatetime` имеет тип DATETIME. Его нужно сравнивать как время в локальной
шкале почтового сервера (`chrono::NaiveDateTime`), не объявляя его автоматически
UTC. Для дней вычитается число календарных дней с сохранением времени суток;
для месяцев и лет день ограничивается последним существующим днём результата.
CLI показывает итоговую границу и часовой пояс сервера до применения.

Первая версия обрабатывает сохранённые письма аккаунтов: `messageaccountid > 0`
и состояние Delivered (`messagetype = 2`), включая сохранённые черновики.
Связь аккаунта и IMAP-папки проверяется по БД. Неизвестные состояния и нарушенные
связи становятся диагностикой, а не основанием удалять файл.
Очередь доставки и `#Public` защищены от удаления в этой версии. Файлы, которые
не упомянуты в БД, не удаляются; их поиск не входит в обычный проход очистки.

Путь обычного письма вычисляется по адресу аккаунта и имени файла:

```text
Data / domain-from-account-address / local-part / first-two-GUID-characters / {GUID}.eml
```

Логическая папка Inbox/Sent/Archive не добавляет уровень к этому пути.
Старый абсолютный `messagefilename` используется после проверки принадлежности
разрешённому дереву Data. Для относительного имени поддерживается подтверждённый
формат имени GUID; неизвестный формат не запускает поиск по всему диску.

Адреса аккаунтов, компоненты пути и имена проверяются на границе адаптера.
Проверяются настоящий корень Data, принадлежность пути этому корню, расширение
и запрет symlink/reparse point в цепочке пути. Проверка корня сопоставляет его
с DataFolder установленного hMailServer. Ошибка чтения настройки блокирует
изменения, а не подставляет предполагаемый каталог.

Карта учитывает все ссылки из БД, включая более новые и исключённые письма.
Пути на Windows сравниваются с учётом правил файловой системы. Один физический
файл удаляется один раз, даже если на него ссылаются несколько выбранных строк.
Если есть ссылка из невыбранной строки, операция для этого пути блокируется.
Таким образом, совпадение имени не позволяет удалить файл сохраняемого письма.

## Исполнение: файлы, затем БД

1. Проверить конфигурацию, схему БД и доступность журнала. Через Windows SCM
   подтвердить, что указанная служба hMailServer остановлена. В первой версии
   оператор останавливает и запускает службу; CLI проверяет её состояние.
2. Получить исключительное право на очистку этой БД и журнал операции.
   Защита должна исключать одновременную работу двух экземпляров программы.
3. Зафиксировать карту и план по согласованной границе. Сообщения и справочник
   аккаунтов читаются в согласованном read-only snapshot MySQL. Сообщения читаются
   порциями по первичному ключу `messageid`, без OFFSET, полной загрузки в RAM и
   сортировки всех писем по дате.
4. Перед изменениями проверить актуальность записей и карты. Старый план не
   должен удалять запись, у которой изменились аккаунт, путь, дата или состояние.
   Новые ссылки на выбранный физический файл также блокируют его удаление.
5. Долговечно записать в локальный журнал намерение обработать порцию и её
   идентификаторы. Сбой записи журнала останавливает работу до удаления файлов.
6. Проверить безопасные пути и удалить файлы порции. Допустимые результаты:
   `Removed`, `AlreadyAbsent`, `Failed`. Только первые два допускают удаление
   соответствующих строк почтовой БД. NotFound учитывается после проверки пути;
   PermissionDenied и остальные ошибки никогда не преобразуются в NotFound.
7. Сохранить результаты файлового шага в журнале. При сбое журналирования
   остановить новые удаления и оставить операцию для согласования при resume.
8. В одной MySQL-транзакции удалить зависимые `hm_message_metadata`,
   `hm_messagerecipients` и `hm_messages` только для допустимых `messageid`.
   Параметры передаются через bind; пустой набор не создаёт SQL удаления.
   Число удалённых основных строк проверяется против ожидаемых идентификаторов.
9. Подтвердить commit и сохранить состояние завершённой порции. При SQL-ошибке
   не начинать следующую порцию. Ошибки отдельных файлов дают частичный результат;
   успешные файлы той же порции можно завершить в БД.
10. Проверить, что подтверждённые идентификаторы и их зависимые записи отсутствуют,
    а число результатов соответствует плану. Выдать отдельные счётчики удалённых
    файлов, ранее отсутствовавших файлов, удалённых строк, ошибок и незавершённых
    операций. Частичный результат возвращает ненулевой код CLI.

Состояние службы проверяется перед каждой порцией. Оператор обеспечивает
отсутствие других записывающих клиентов и держит hMailServer остановленным до
завершения или устранения незавершённой операции. Программа не гарантирует
изоляцию от администратора, одновременно меняющего файлы или запускающего сервер.
Аккаунты, домены, IMAP-папки, их UID-счётчики и каталоги не удаляются.
Состояние штатных кешей обновится при запуске остановленного hMailServer.

## Сбои, возобновление и предел надёжности

Файловая система и MySQL не образуют общую транзакцию. Журнал сохраняет
идентификатор запуска, границу, источник БД и Data, существенные поля выбранных
записей, идентичность существующих файлов, результаты и ошибки. Он не содержит
пароль подключения или тела писем и хранится вне Data.

| Момент сбоя | Поведение |
| --- | --- |
| До долговечной записи намерения | Файлы не меняются |
| Файл удалён, запись результата потеряна | Resume сверяет журнал, путь и БД; отсутствие файла допускает завершить SQL-шаг |
| Файл не удалён из-за доступа | Его записи сохраняются, причина попадает в отчёт |
| SQL откатился после удаления файлов | Незавершённая порция завершается через resume при остановленной службе |
| Ответ COMMIT потерян | Результат определяется чтением основных и зависимых строк; ошибка сети не означает rollback |
| Запись или файл заменены | Конфликт; никаких слепых повторных удалений |

Resume использует первоначальный план. Он сверяет идентичность источника,
актуальные поля строк, наличие файлов и все ссылки на путь. Уже завершённые
операции не считаются ошибкой. Неоднозначный или смешанный результат SQL требует
диагностики вместо заявления об успешной очистке. После отмены завершаются уже
начатые файловые операции и согласование их результатов; процесс не вызывает
немедленный `process::exit(0)` посреди порции.

Журнал обеспечивает возможность продолжения, но не восстановление удалённого
содержимого. Даже rollback SQL не возвращает настоящее удалённое письмо.
Для полного отката нужна согласованная резервная копия Data и БД.
Альтернатива — карантин на том же томе: сначала переместить файл из Data,
затем обновить БД, а окончательное удаление выполнить после проверки.
Это отдельное изменение поведения; в этом проекте сохранён запрошенный порядок
прямого удаления. Карантин удерживал бы занимаемое место до окончательной очистки.

## Производительность и наблюдаемость

- Базовая порция — 1 000 записей, значение задаётся валидированной настройкой.
  Результаты и индексы карты хранятся в локальном SQLite-журнале; в RAM находится
  текущая порция и справочник аккаунтов, а не всё дерево файлов.
- Пути порции группируются по аккаунту и GUID-каталогу для лучшей локальности.
  Внутри группы порядок последовательный; независимые группы могут исполняться
  ограниченным числом работников. Начальное значение — 2, доступны 1–8.
  Максимальная параллельность не считается автоматически самой быстрой на HDD.
- Для блокирующих операций используются ограниченные работники; бесконтрольного
  создания задачи на каждый файл и отдельных потоков на каждое письмо нет.
- Подтверждения журнала группируются по порциям. Намерение обязано быть
  долговечным до файлового шага независимо от выбранной оптимизации записи.
- Прогресс публикуется агрегированно не чаще раза в 250 мс и при завершении
  этапа. Ошибки сохраняют конкретные идентификаторы; каждый успех не требует
  отдельного UI-события и информационного сообщения в лог.
- Полное рекурсивное удаление пустых папок исключается из очистки писем.
- Отдельно измеряются выборка БД, построение карты, файловый шаг, SQL commit,
  журнал и итоговая проверка. Настройка работников проверяется на реальном диске.

Автоматический ALTER TABLE или OPTIMIZE TABLE не выполняется. Для новой схемы
индексов сначала нужны EXPLAIN и замеры на репрезентативной БД, затем отдельное
согласование изменения живой схемы.

## Границы компонентов и повторное использование

- `crates/core`: срок хранения, план, правила отбора, типы результатов и сценарии
  применения/возобновления. Порты задают потребности этих сценариев. Ядро не
  зависит от Tauri, CLI, переменных окружения, MySQL или Windows SCM.
- `crates/adapters`: MySQL через существующий SQLx, файловая система, локальный
  SQLite-журнал, проверка службы Windows и источник времени сервера. Независимые
  адаптеры находятся в собственных модулях, без общего набора utils.
- `crates/cli`: разбор команд `plan`, `apply`, `resume`, `status`, валидированная
  конфигурация и сборка зависимостей, вывод прогресса и коды завершения.
- `src-tauri`: существующее окно остаётся отдельной оболочкой для последующего
  подключения ядра. Перенос UI и миграция Tauri 1 → 2 — следующий этап;
  нынешнее окно не объявляется исправленным новой CLI-реализацией.

Переиспользуются Rust, SQLx, Tokio, Chrono, Serde и существующая инфраструктура
логирования, где их контракты подходят. Для SQLite сначала используется
возможность имеющегося SQLx, а не второй SQL-драйвер. Новые зависимости для CLI
и службы выбираются после проверки поддержки Windows Server 2016.
Bun не выбран как рабочий runtime сервера из-за более новой минимальной версии
Windows; он может применяться в инструментах будущей оболочки на Mac/CI.

Конфигурация читается в одном владельце и передаётся зависимостям явно.
Пример конфигурации не содержит настоящих учётных данных; новая CLI-сборка
не читает и не упаковывает автоматически отслеживаемые старые `.env`.
Публичная конфигурация будущего окна не включает пароль или все переменные среды.
Обновление зависимостей не должно превращаться в постороннюю миграцию всего UI.

## Проверки реализации и границы подтверждения

Нужны тесты точной границы даты, месяцев/лет и високосного года; построения пути
и старого абсолютного имени; выхода из Data, reparse point и коллизий ссылок;
сохранения новых, публичных и недоставленных писем; всех трёх результатов
файлового шага; точных SQL-id, зависимых строк, rollback и неопределённого commit;
возобновления после каждого окна сбоя, отмены и запрета второго экземпляра.

Интеграционные проверки используют отдельную MySQL 5.7-совместимую тестовую БД
по предоставленной DDL и временный Data. Проверки с инъекцией ошибок должны
подтвердить инварианты, а не только вызовы функций. Performance-проверка сравнивает
этапы и число операций на одинаковом наборе данных; фиксированное обещание
ускорения всей программы не задаётся.

Сборка переносимого ядра на Mac, Windows-сборка и запуск на Windows Server 2016
считаются разными результатами. Версия живого hMailServer и текущая схема
проверяются preflight: архив содержит DDL без строки `hm_dbversion`, поэтому
точный установленный билд 5.7 из него не определён. Дамп указывает MySQL 5.7.21,
но это не подтверждает текущую версию живого сервера.

На момент написания выполнены чтение кода/истории/DDL и синтетический замер.
Продуктовый код не изменён, сборки приложения и проверки живого сервера не
выполнялись. Следующий шаг после проверки проекта пользователем — письменный
план реализации, затем выбранный пользователем способ исполнения.
