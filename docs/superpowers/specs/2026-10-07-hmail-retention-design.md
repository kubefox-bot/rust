# Очистка hMailServer: ядро и CLI

Дата: 2026-10-07. Уточнено пользователем: ценности хранения удаляемых писем нет;
нужны прямое удаление файлов и очистка почтовой БД.

## Результат и границы

Программа работает на самом Windows Server 2016/1607 x64 с остановленным hMailServer.
Она удаляет письма старше указанного срока во всех аккаунтах и их IMAP-папках,
сохраняя аккаунты, логические IMAP-папки и более новые письма. Физические
каталоги после очистки удаляются, если пусты. Первый интерфейс — CLI;
переносимое Rust-ядро позже используется оконной оболочкой Tauri.

БД — источник возраста письма и карты файлов. Для каждой порции сначала
удаляются файлы, затем соответствующие записи. Отсутствующий файл тоже допускает
удаление старой записи. Ошибка доступа или некорректный путь сохраняет запись.

Карантин, резервное копирование, SQLite-журнал и отдельный механизм resume
не нужны. Повторный запуск той же очистки завершает работу: оставшаяся запись
выбирается вновь, отсутствие ранее удалённого файла допускает SQL-шаг.
Это продолжение очистки, а не откат или общая транзакция MySQL и файловой системы.

Ветка `update` создана локально от `main` репозитория `kubefox-bot/rust`.
Публикация изменений и запуск на настоящем сервере в текущую подготовку не входят.

## Причина медленной и некорректной работы

Существующий `file_service.rs` сначала рекурсивно читает всё дерево Data,
для каждого файла вызывает `Vec::contains` по всем выбранным именам, удаляет
последовательно и снова обходит дерево ради пустых каталогов.
Поиск даёт до O(F × K) сравнений при F файлах и K выбранных письмах.

Ошибки удаления файлов логируются, но метод может вернуть Ok. Закомментированный
SQL удаляет все старые сообщения по дате, а не только успешно обработанные id;
связанные записи также не очищаются. Результат нельзя исправить одним
раскомментированием вызова. Причина исторических SQL-ошибок без логов неизвестна.

Используем точные пути из БД, порции по первичному ключу и ограниченную
параллельность. Полные обходы дерева исключаются. Поиск файлов требует O(K)
построений путей; стоимость чтения БД и самих удалений измеряется отдельно.

Диагностический Rust-замер на Mac: 50 000 имён, 5 000 выбранных, `-O`.
Vec потребовал 237 502 500 сравнений и 397,005 мс; HashSet с построением — 1,393 мс;
построение точных путей — 1,302 мс. Это один замер в памяти без MySQL и диска;
ускорение всей программы на сервере пока не измерено.

## Отбор и пути

Дата отбора — `hm_messages.messagecreatetime`, строго `< cutoff`.
Граница фиксируется один раз на запуск. DATETIME сравнивается как локальное
время почтового сервера (`chrono::NaiveDateTime`), без автоматического объявления
UTC. CLI показывает границу. Поддерживаются положительные сроки `30d`, `1mo`,
`1y` и явное локальное время `--before`; выборы взаимно исключаются.
Для календарных месяцев и лет день ограничивается последним днём результата.

Обрабатываются письма аккаунтов: `messageaccountid > 0`, `messagetype = 2`
(Delivered), включая сохранённые черновики. Связь IMAP-папки и аккаунта
проверяется. Нарушенная связь даёт ошибку, не молчаливое исключение.
Очередь доставки, `#Public` и файлы без записи в БД не удаляются этой версией.

Путь обычного письма:

```text
Data / domain-from-account-address / local-part / first-two-GUID-characters / {GUID}.eml
```

Логические Inbox/Sent/Archive не меняют физический путь. Старое абсолютное
`messagefilename` поддерживается только внутри разрешённого Data.
Проверяются GUID-имя, компоненты, принадлежность корню, symlink/reparse point.
Настоящий Data сверяется с DataFolder установленного hMailServer.
Некорректная настройка не должна выглядеть как отсутствие всех файлов.

Для повреждённой БД вводится простой консервативный контроль: перед удалением
один SQL-проход выявляет повторяющиеся имена файлов, нормализуя регистр и
basename старых полных путей. Такие письма пропускаются с явной ошибкой,
даже если одинаковые имена оказались в разных аккаунтах.
Это защищает общий файл и более новые ссылки без индекса всей карты в памяти.
Нормализация коллизий не используется как способ поиска или удаления файлов.

## Рабочий цикл

1. Валидировать конфигурацию и поддерживаемую схему, сверить DataFolder.
   Перед изменениями проверить STOPPED через Windows SCM. В первой версии
   оператор останавливает и запускает службу.
2. Взять MySQL advisory lock для этой БД на выделенном соединении. Второй
   экземпляр завершается до удаления файлов. Освобождение ресурса принадлежит
   владельцу соединения, включая ошибку и отмену.
3. Зафиксировать cutoff и верхний messageid. Прочитать справочник аккаунтов и
   повторяющиеся имена. Выбирать кандидатов порциями по `messageid > cursor`
   и `messageid <= upper_id`, без OFFSET и сортировки всех строк по дате.
4. Проверить STOPPED перед порцией. Построить и проверить точные пути.
   Ошибки путей и повторяющиеся имена исключают соответствующие id из удаления.
5. Сгруппировать файловые операции по аккаунту/GUID-каталогу. Удалить каждую
   порцию ограниченными работниками; не создавать задачу на каждое письмо.
   Результаты: Removed, AlreadyAbsent, Failed. NotFound после проверки пути —
   AlreadyAbsent; PermissionDenied и другие ошибки — Failed.
6. Только для Removed и AlreadyAbsent в одной MySQL-транзакции удалить
   `hm_message_metadata`, `hm_messagerecipients`, затем `hm_messages`.
   Использовать bind по конкретным messageid; пустой набор не создаёт DELETE.
   Повторно сверить существенные поля строк и ожидаемое число удалений.
7. При SQL-ошибке остановить новые порции. Ошибка ответа COMMIT не считается
   подтверждённым rollback: проверить результат чтением либо вернуть
   неопределённый результат и предложить повтор той же команды.
8. Сформировать счётчики удалённых файлов, уже отсутствовавших файлов,
   удалённых сообщений и ошибок; проверить отсутствие подтверждённых id и
   связанных строк. Частичная очистка возвращает ненулевой код.

После подтверждённого SQL-шагa порции удалить пустые физические каталоги,
связанные с её допустимыми файлами: GUID-каталог, затем пустой каталог аккаунта
и домена. Пустой означает отсутствие любых записей, включая подпапки и скрытые
файлы. Используется атомарный remove_dir: DirectoryNotEmpty сохраняет каталог.
Data никогда не удаляется. Только затронутые пути проверяются без полного обхода;
неудачное или неподтверждённое удаление БД не запускает этот шаг.
Остальные ошибки каталогов входят в отчёт; завершённый SQL-шаг не откатывается.

Курсор продвигается по последней прочитанной записи, включая записи с ошибками:
одна неисправная запись не зацикливает текущий запуск. Повторная команда
начинает новый проход и повторяет оставшиеся записи.
Отмена прекращает новые задания; уже начатые файловые операции завершаются,
и допустимые результаты согласуются с БД перед выходом.

Оператор держит сервер остановленным и исключает других пишущих клиентов.
Проверки не гарантируют изоляцию от администратора, одновременно меняющего
файлы или запускающего сервер. При сбое после удаления файла в БД может
временно остаться ссылка на отсутствующее письмо; следующий запуск её удалит.
Программа не обещает восстановление содержимого или хранение истории запусков.

## Настройки и границы компонентов

Порция по умолчанию — 1 000 сообщений, допустимо 1–10 000; работники — 2,
допустимо 1–8. Предел порции ограничивает RAM и число SQL-параметров.
Внутри одной группы порядок последовательный. Прогресс агрегирован не чаще
раза в 250 мс; ошибки содержат id или путь и причину. Итог также считает
удалённые каталоги. Пустые незатронутые каталоги отдельным проходом не ищутся.
ALTER TABLE и OPTIMIZE TABLE автоматически не выполняются.

- `crates/core`: сроки хранения, пути, результаты и сценарий очистки;
  порты БД, удаления файлов и проверки остановленной службы.
- `crates/adapters`: SQLx/MySQL, файловая система, Windows SCM.
- `crates/cli`: команды preview/clean, валидированная конфигурация,
  сборка зависимостей, вывод и коды завершения.
- `src-tauri`: существующее окно сохраняется для следующего этапа;
  перенос UI и миграция Tauri 1 → 2 сейчас не выполняются.

Переиспользуются Rust, SQLx, Tokio, Chrono, Serde и подходящее логирование.
Конфигурация читается в одном владельце и явно передаётся зависимостям.
CLI не загружает старые отслеживаемые .env автоматически и не выводит секреты.
Допускается явно указанный env-файл; пример содержит только фиктивные значения.

## Проверка и текущий статус

Нужны тесты календарных границ, точных и старых абсолютных путей, запрета выхода
из Data и reparse point, повторяющихся имён, выборки всех папок аккаунтов,
сохранения новых/публичных/недоставленных сообщений, AlreadyAbsent против
PermissionDenied, точных SQL-id и зависимых строк, rollback/неопределённого
commit, повторного запуска, отмены, блокировки второго экземпляра; удаления
пустых родителей после commit, сохранения Data и непустых/скрытых подпапок.

MySQL-интеграция использует отдельную БД по предоставленной DDL и временный Data.
Сборка ядра на Mac, Windows exe и запуск на Windows Server 2016 — отдельные
проверки. Точный билд hMailServer 5.7 и живая схема проверяются preflight:
архив содержит DDL без значения hm_dbversion. Пользователь подтвердил Windows
1607 и mysql-client 5.7.21 Win64; старый дамп также указывает сервер 5.7.21.
Тестовая MySQL закреплена на 5.7.21 и digest образа; текущая версия живого
сервера проверяется отдельно через SELECT VERSION().
Rust закреплён в mise.toml на 1.98.1; Cargo.lock фиксирует зависимости.
Задачи mise: fmt, fmt:check, test, lint, check, build, db:up, db:down, test:db.

Коды CLI: 0 — завершено, 1 — частично/ошибка backend/неопределённый commit,
2 — неверные настройки или preflight, 130 — отмена. Preview не удаляет файлы
или записи и использует тот же отбор.

Сейчас выполнены чтение кода/истории/DDL и замер поиска. Продуктовый код не
изменён, сборки приложения и очистка настоящего сервера не выполнялись.
