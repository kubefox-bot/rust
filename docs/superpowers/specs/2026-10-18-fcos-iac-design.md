# FCOS: переносимая первоначальная конфигурация центра

Дата: 2026-10-18.

Статус: проект спецификации для проверки пользователем; реализация не начата.
Предыдущий MVP сохранён в `a4eea35` (`ci/hmail-control-center-mvp`);
перед подготовкой документа рабочее дерево было чистым.

## 1. Цель и границы

Добавить в монорепозиторий IaC для первоначальной подготовки Fedora CoreOS
под существующую поставку центра. Пользователь вручную создаёт ВМ, выбирает
ресурсы, подключает официальный FCOS Stable live ISO, подготавливает диск
и сеть. Общая конфигурация не зависит от Hyper-V, VMware, KVM и других
гипервизоров и может использоваться на совместимом физическом хосте.

Выбор диска, CPU, RAM, прошивки, виртуального коммутатора, статического IP,
DNS и маршрутов остаётся за оператором. Конфигурация не создаёт ВМ,
не содержит KVP, cloud metadata, имён виртуальных коммутаторов,
гипервизорных команд или жёстко заданного `/dev/sda`.

Существующая архитектура сохраняется: Rust-центр и статический Astro/Svelte
в rootless Podman + Quadlet; почтовые Rust-агенты работают отдельно на Windows.
CI/CD, публикация, registry credentials, автоматические обновления приложения,
Ansible и развёртывание на рабочих серверах не входят в эту задачу.

## 2. Выбранный подход и альтернативы

Выбран общий Butane YAML, преобразуемый официальным Butane в Ignition JSON.
Оператор передаёт JSON установщику с обычным FCOS live ISO. Это отделяет
конфигурацию гостевой ОС от способа создания и загрузки машины.

Подготовленный ISO со встроенным destination Ignition остаётся совместимым
способом доставки той же конфигурации, но его сборка и автоматический выбор
диска не нужны для первого изменения. Гипервизорные VHDX/KVP-обёртки не нужны.
Ansible потребовал бы отдельного управляющего окружения и не заменил бы
первоначальный сетевой/SSH-доступ, поэтому сейчас не добавляется.

## 3. Владение файлами

Планируемые новые файлы:

```text
iac/
  README.md
  fcos/
    config.bu
    files/
      zincati.toml
    local.example/
      README.md
    README.md
```

`iac/fcos/config.bu` — единственный исходник первоначальной настройки.
`files/zincati.toml` — принадлежащая FCOS настройка окна перезагрузки;
Butane встраивает её через local file reference. Реальный публичный SSH-ключ
оператора хранится в `iac/fcos/local/admin.pub`; этот каталог явно исключается
из Git. Пример объясняет получение публичного ключа и не содержит фиктивного
ключа, который можно принять за готовый рабочий доступ.

Сборка использует временный каталог входных файлов, объединяющий только
явно перечисленные общие файлы и публичный ключ. Она не читает весь домашний
каталог и не включает соседние приватные ключи. Простые документированные
команды достаточны; новый генератор, шаблонизатор или пакетный менеджер
в первом изменении не добавляется. При реализации способ передачи файлов
проверяется настоящим Butane, включая запуск из другого рабочего каталога.

Результат находится под `target/iac/fcos/` и не коммитится. Редактируется
Butane, а не сгенерированный JSON. `deploy/quadlet` продолжает владеть
шаблонами запуска приложения; их копий в IaC нет.

## 4. Содержимое конфигурации ОС

- Административный доступ пользователя `core` по предоставленному публичному
  SSH-ключу; пароли и приватный ключ не включаются.
- Отдельный обычный пользователь `hmail-center` с домашним каталогом в `/var/home`.
- Явные непересекающиеся subordinate UID/GID ranges для rootless Podman;
  стандартные записи других пользователей сохраняются.
- Linger для `hmail-center`, чтобы его systemd user manager запускался без
  интерактивного входа. Он не получает sudo или доступ к engine socket.
- Каталог пользовательских Quadlet с владельцем `hmail-center`.
- Zincati с periodic strategy: воскресенье, 03:00–04:00 UTC. Это исходное
  документированное окно; оператор меняет его в IaC до генерации JSON.

Podman, systemd и остальные штатные компоненты используются из FCOS;
компиляторы, Bun/Node runtime, отдельная MySQL, Ansible, Python и новые
пакетные слои ради этой подготовки не устанавливаются.

Сеть, hostname и firewall остаются в ответственности оператора и существующих
правил установки; IaC не перезаписывает сетевые профили, не выключает firewall
и не публикует дополнительные порты. Документация перечисляет требуемую
доступность SSH и HTTPS центра на 8443. Если оператор настраивает сеть в live
среде, он переносит её через `coreos-installer install --copy-network`.

Окно Zincati ограничивает время автоматических перезагрузок, но не проверяет
активные задания центра или агентов. Эта поставка не обещает согласования
перезагрузки с очисткой, отказоустойчивости одной ВМ или автоматического
восстановления прикладной БД.

## 5. Первоначальная установка

1. Оператор готовит новую машину и загружает официальный FCOS Stable live ISO
   подходящей архитектуры. В документации основной пример — x86_64; другая
   архитектура требует соответствующей ОС и поставки приложения.
2. Настраивает сеть и проверяет реальный целевой диск. Автоматического выбора
   диска или разрушительного автозапуска в нашем IaC нет.
3. На машине подготовки получает Ignition из Butane с `--strict`; отсутствие
   ключа и ошибки преобразования блокируют дальнейшие шаги.
4. Передаёт `config.ign` локальным файлом (например, на отдельном носителе)
   или через проверенный HTTPS-адрес. Для HTTP требуется закреплённый SHA-256;
   отключение проверки конфигурации не предлагается.
5. Запускает установку на явно выбранный диск с destination Ignition и при
   необходимости `--copy-network`. Документация объясняет, что диск будет
   перезаписан, и отделяет live Ignition от destination Ignition.
6. Убирает установочный ISO из загрузки, загружается с диска и проверяет
   SSH-доступ, пользователя, диапазоны UID/GID, linger, rootless/cgroup v2
   и systemd user manager.

Ignition работает один раз при первом запуске установленной ОС. Изменение
файла в Git не обновляет работающий сервер; повторный запуск Ignition на
машине с данными не является механизмом применения изменений.

## 6. Передача управления существующей поставке приложения

После подготовки ОС используется существующая
[инструкция развёртывания](../../center-deployment.md):

- перенос проверенной локальной поставки, проверка manifest/SHA-256;
- `podman load` и сверка immutable image digest;
- создание выделенного named volume `hmail-center-data`;
- интерактивный `center init` под `hmail-center`, с тем же UID mapping и томом,
  что у Quadlet; логин/пароль/recovery key не передаются через IaC;
- установка сгенерированных release Quadlet, запуск и проверка health;
- проверка доверия HTTPS в браузере оператора.

IaC не начинает центр до инициализации данных. `Pull=never` остаётся действующим
контрактом; загрузка из registry и его учётные данные не выдумываются.
Существующие health, owner mapping, `/data`, порт 8443 и build checks сохраняются.

## 7. Секреты, данные и восстановление

В Git не попадают пароли, registry tokens, приватные SSH/TLS-ключи,
recovery key, профили MySQL и копии SQLite. Публичный ключ не является
секретом, но параметры конкретной установки держим отдельно от общего исходника.

Игнорирование локальных файлов не заменяет проверку содержимого поставки.
Готовый Ignition проверяется на отсутствие посторонних входных файлов;
хеш для передачи считают по окончательному JSON.

Данные приложения и его TLS identities создаются на конкретной машине,
не в общем ISO/шаблоне. Новую машину можно подготовить тем же IaC и затем
восстановить согласованную резервную копию по
[инструкции восстановления](../../recovery.md). Копия расположенная только
внутри потерянной ВМ восстановлением не считается. Автоматический backup
и его внешнее хранилище в рамках этой задачи не реализуются.

## 8. Проверка и критерии завершения реализации

1. Настоящий официальный Butane преобразует конфигурацию с `--strict`;
   JSON проверяет официальный `ignition-validate` совместимой версии.
   Фактические версии обоих инструментов фиксируются в отчёте проверки;
   неподдерживаемая версия схемы блокирует выпуск JSON.
2. В JSON присутствуют ожидаемые пользователи, UID/GID ranges, linger,
   владельцы файлов и точная политика Zincati. SSH-ключ совпадает с входным.
3. Отсутствие ключа, неверный исходник и несовместимый инструмент завершаются
   ошибкой; не публикуется частичный JSON как готовый результат.
4. В конфигурации нет гипервизорных API, автоматического выбора диска,
   посторонних приватных файлов, фиктивных credentials или дубликатов Quadlet.
5. Документация содержит реальные команды подготовки, передачи и установки,
   проверенные пути и явную передачу управления существующей поставке.
   Из корневого README и инструкции развёртывания доступны ссылки на IaC.
6. Проводится boot smoke на доступном гипервизоре, если это возможно без
   изменения пользовательской инфраструктуры. Без него результат явно
   обозначается как проверенная конфигурация, а загрузка/SSH/rootless/reboot
   остаются NOT RUN. Одна VM-проверка не доказывает все гипервизоры.

## 9. Источники и проверенные границы

Context7 использован для официальных библиотек Butane, Fedora CoreOS и Zincati.
Подтверждены local file references, linger, перенос сетевой конфигурации
и периодические окна перезагрузки. Совместимость с конкретной ВМ ещё не проверена.

- [Butane: local files](https://coreos.github.io/butane/examples/).
- [FCOS: Ignition и первый запуск](https://github.com/coreos/fedora-coreos-docs/blob/main/modules/ROOT/pages/producing-ign.adoc).
- [FCOS: user systemd и linger](https://docs.fedoraproject.org/en-US/fedora-coreos/tutorial-user-systemd-unit-on-boot/).
- [coreos-installer: install и copy-network](https://coreos.github.io/coreos-installer/cmd/install/).
- [Zincati: periodic strategy](https://coreos.github.io/zincati/usage/updates-strategy/).

После проверки этой спецификации пользователем составляется отдельный план
реализации. Этот документ сам по себе не подтверждает создание IaC,
сборку ISO, развёртывание или проверку рабочих серверов.
