# Автоматическая доставка Astra

Центр поставляется Linux OCI-образом для FCOS + rootless Podman + Quadlet.
Исходящий доступ к GitHub и GHCR позволяет получать обновления без входящих
подключений в сеть организации. Windows-агенты продолжают обновляться вручную
через панель; эта доставка заменяет только образ центра.

Реализация в репозитории и включение доставки на конкретном сервере — разные
этапы. Публикация защищена переменной `ASTRA_DELIVERY_ENABLED=true`; её включение
допустимо после тестовой приёмки и согласования registry, репозитория и ВМ.
Фактические результаты находятся в [отчёте приёмки](center-cicd-acceptance.md).

## Путь от push до запуска

1. Push в `main` запускает `center-delivery.yml`, который вызывает `center-ci.yml`.
2. Проверки Rust, frontend, контрактов, MySQL и native Windows-сборки должны
   завершиться успешно. Проверка на Windows runner не подтверждает Server 2016.
3. OCI-образ собирается с Windows-пакетом агента той же сборки. Локальная
   проверка жизненного цикла связывается receipt с полным source SHA и hash
   release manifest. Публикация использует эти артефакты без пересборки.
4. GHCR получает проверенный image digest. Draft GitHub Release получает полный
   набор файлов и подписанный Cosign descriptor. Отдельная promotion-проверка
   сверяет актуальную `main`, подпись, sequence и состав файлов до публикации.
5. Updater на ВМ опрашивает опубликованные релизы, проверяет доверенную identity,
   repository, platform, build, sequence и совместимость schema/protocol/updater.
6. Кандидат скачивается заранее. Старый контейнер продолжает работать до drain.
7. Центр закрывает приём новых изменений, завершая уже принятую работу. После
   подтверждения готовности updater останавливает его, создаёт offline backup
   старым executable, переключает образ, проверяет запуск и открывает доступ.

`pull` не является обновлением работающего контейнера. Подмена image в Quadlet,
пересоздание контейнера и проверка результата принадлежат host updater.

## Настройки в центре

Суперадмин меняет параметры в «Настройки → Обновления». HTTP-контракт:

```text
GET   /api/v1/settings/updates
PATCH /api/v1/settings/updates
```

```json
{
  "check_interval_seconds": 60,
  "graceful_timeout_minutes": 15
}
```

Интервал проверки: 30–86400 секунд; ожидание завершения работы: 1–1440 минут.
Значения по умолчанию — 60 секунд и 15 минут. PATCH требует активную сессию и
обычную CSRF-защиту. Эта операция не меняет idle timeout сессии, но учитывается
как активность пользователя.

Параметры хранятся в `/data/update-policy.json` с приватными правами, заменяются
атомарно и входят в backup. Они доступны updater через локальный Unix socket без
пароля суперадмина и расшифровки vault. Последняя подтверждённая политика
сохраняется updater на хосте; отсутствие центра не должно сбрасывать её на defaults.

Проверка запуска кандидата имеет отдельный технический timeout 120 секунд.
Интервал discovery задаёт частоту поиска релизов; он не обещает обновление ровно
через 60 секунд после push. Время CI, публикации, передачи образа и drain
добавляется к задержке обнаружения.

## Границы управления

Обычное приложение работает с read-only rootfs и постоянным `/data` в named
volume `hmail-center-data`. Контейнер не получает socket Docker/Podman.
Host updater запускается от отдельного системного пользователя `hmail-center`,
который владеет rootless Podman и пользовательскими unit-файлами.

```text
hmail-center user
├── Podman + hmail-center.service
├── astra-updater: discovery, download, switch, recovery
└── local reboot coordinator: согласование Zincati с admission
```

Связь с центром ограничена `/run/astra-maintenance/control.sock` внутри
контейнера. Quadlet монтирует `%t/astra-maintenance`; user systemd создаёт этот
каталог с правами 0700, socket имеет права 0600. Обе стороны проверяют UID peer.
В legacy runtime без этого каталога socket отключён; такое окружение не готово
к автоматической доставке. Оно не получает скрытый HTTP API управления хостом.

Протокол — одна ограниченная строка JSON на соединение. Поддерживаются только
`begin`, `status`, `finish`, `abort`, `policy`, version 1. UUID операции владеет
maintenance: другой UUID получает conflict. Ответы не содержат профилей, ключей,
паролей и произвольного вывода системных команд.

## Graceful и backup

После `begin` новые job/enrollment/profile/account/settings mutations не
принимаются. Начатые writers и detached operations удерживают собственные permits
до завершения; закрытие вкладки не освобождает их преждевременно.

Во время draining доступны вход, отмена и reconcile существующей операции.
Неизвестный результат удалённой работы сохраняет durable slot и считается busy.
Отсутствие ответа агента не разрешает принудительную остановку центра. Когда
слоты свободны и writers завершены, `status` фиксирует ready и закрывает также
continuation writes до завершения maintenance.

Если graceful timeout истёк, обновление откладывается, gate снимается, текущая
работа продолжается. Updater не запускает очистку повторно и не убивает её ради
релиза.

Marker `/data/maintenance.json` сохраняется до закрытия/открытия gate и читается
при старте до HTTP routes. Его повреждение блокирует запуск. Marker не входит в
backup: восстановление создаёт marker нужной host transaction заново перед
стартом центра.

Offline backup выполняется только после остановки контейнера прежним образом с
теми же userns/volume параметрами. В snapshot входят SQLite, HTTPS/CA-файлы,
конфигурация центра и optional update policy. Все файлы snapshot имеют права
0600, каталог — 0700. Hash receipt связывает snapshot с transaction.

## Переключение и восстановление

Host journal атомарно сохраняет transaction и фазы:

```text
Staged → Draining → Stopped → BackedUp → Starting
       → Verified → Exposing → Committed
```

`Exposing` записывается с fsync до снятия gate. До этой границы неуспешный
кандидат можно остановить, сохранить его данные и восстановить matching backup.
После `Exposing` автоматический возврат старых данных запрещён: новая версия уже
могла принять изменения. Потеря ответа `finish` не является основанием для restore.

Перед удалением содержимого data volume сохраняется экспорт неуспешного
кандидата и проверяется matching snapshot. Восстановление не удаляет архив
кандидата и предыдущий backup. Повтор recovery после сбоя продолжает ту же
transaction; ошибка проверки оставляет систему закрытой для изменений.

`RollbackExposing` и `PreviousExposing` также записываются до открытия старой
версии после восстановления или ошибки backup. После этих фаз повторная
замена данных запрещена: recovery только подтверждает старую версию и завершает
открытие gate. Потерянный ответ `abort` не запускает restore повторно.

Место для backup и экспорта повторно проверяется после загрузки образа, до drain
и остановки работающего центра. Это учитывает место, занятое самим pull.

Recovery перед стартом центра подготавливает unit, данные и marker, выполняет
`systemctl --user daemon-reload` после выбора прежнего Quadlet, но не
запускает свой зависимый center unit из его startup dependency. Дальнейшая
проверка и commit выполняются отдельным вызовом updater. Health проверяет build
и работоспособность центра; закрытый vault после перезапуска — штатное состояние.
Суперадмин входит повторно и разблокирует технические профили.

Schema 1 сохраняется. Релиз с несовместимым протоколом, schema или минимальной
версией updater не должен останавливать установленный центр. Updater и trust
root устанавливаются отдельно; этот механизм не обновляет host executable сам.

## Первоначальная установка

1. Подготовить FCOS по [portable IaC](../iac/fcos/README.md).
2. Установить совместимую начальную сборку центра по
   [инструкции развёртывания](center-deployment.md). Сборка должна содержать
   maintenance socket и backup с приватными файлами; legacy image без этих
   возможностей нельзя сразу подключать к автоматической доставке.
3. Однократно установить проверенный updater package, Cosign, зафиксированный
   trust root, приватную host-конфигурацию и user units. Доверие проверяется до
   запуска updater. Secrets не добавляются в Git, OCI-образ и Ignition.
4. Настроить исходящий HTTPS и credentials только на чтение GitHub/GHCR, если
   репозиторий или registry приватны. Выдача и ротация этих credentials — отдельный
   эксплуатационный шаг. Они не зависят от пароля суперадмина Astra.
5. Прогнать тестовую доставку и восстановление, затем включить production
   publication и timer на согласованной ВМ.

Для существующей ВМ Ignition повторно не применяется. Установка host tooling
выполняется отдельной процедурой с сохранением прежнего Quadlet и backup данных.
Обычные последующие релизы не требуют SSH.

## Обновления FCOS

Zincati обновляет ОС, а не контейнер Astra. FleetLock coordinator на loopback
использует тот же admission и host operation lock. Окно ОС — воскресенье
03:00–04:00 UTC. Неизвестный клиент, недоступный центр или активная transaction
не дают разрешения на reboot.

Grant сохраняется до ответа coordinator и удерживает gate до подтверждения
steady-state. Это связывает reboot с graceful admission. Фактическую работу
Zincati, SELinux и rootless socket нужно доказать на тестовой FCOS ВМ: наличие
конфигурации и unit tests само по себе не является таким доказательством.

## Эксплуатация

Для диагностики от пользователя `hmail-center`:

```bash
systemctl --user status hmail-center.service
systemctl --user status astra-updater.service astra-updater.timer
journalctl --user -u astra-updater.service
~/.local/bin/astra-updater status --config ~/.config/astra-updater/config.json
```

Аварийная пауза новых попыток:

```bash
systemctl --user stop astra-updater.timer
```

Остановка timer не прерывает уже запущенную transaction. Во время изменения
образа нельзя вручную удалять marker, journal, backup или переименовывать volume.
Для длительной паузы после проверки активной операции timer можно отключить
через `disable`; возобновление — `enable --now`.

При ошибке сети или подписи прежний образ продолжает работать. При недостатке
места обновление откладывается; автоматический общий `podman prune` не выполняется.
Quarantine предотвращает повторную установку заведомо неуспешного digest.
Состояние требует диагностики; его нельзя очищать вслепую ради нового retry.

Нужно резервировать данные вне этой ВМ. Snapshot на том же диске помогает
восстановить неудачный rollout, но не защищает от потери хоста/диска. При
восстановлении сохраняются весь data volume, UID/GID/subuid/subgid mappings и
соответствующая версия образа; внутренние ключи и recovery key не публикуются в
диагностическом отчёте.

Разрешённый egress должен покрывать GitHub API/releases/assets и их CDN, GHCR
registry/blob delivery, а для ОС — источники обновлений FCOS. Подпись descriptor
проверяется офлайн через установленный trust root; host не полагается на
доступность публичного transparency log в момент обновления. Состав egress
проверяется на реальной сетевой политике при приёмке.
